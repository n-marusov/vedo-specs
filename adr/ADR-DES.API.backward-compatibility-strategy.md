# ADR-DES.API.backward-compatibility-strategy

**Дата:** 2026-05-10  
**Статус:** Принято

## Контекст

VEDO Core является продуктом, ориентированным на корпоративных клиентов, с внешними REST-интеграциями, API клиентской части на GraphQL, внутренними gRPC контрактами и SPARQL точка доступа. Клиенты и отраслевые интеграции не должны ломаться при каждом обновлении, но major versions могут требовать эволюции схем, точек доступа и контрактов.

## Решение

Принять расширенную обратную совместимость API между мажорными версиями с периодом устаревания, а внутри одной мажорной версии — со строгой совместимостью.

Корпоративные клиенты и отраслевые интеграции получают предсказуемое окно миграции — REST API предыдущей версии поддерживается минимум 12 месяцев, GraphQL устаревшие поля сохраняются не менее 9 месяцев. Это исключает нарушающие изменения без предупреждения и позволяет клиентам планировать обновления. Для on-premise клиентов доступны LTS-релизы на 2 года с кастомным бэкпортом security-фиксов.

REST API версионировать через URL path `/api/v1/`, `/api/v2/` с заголовками `Warning` и `Sunset` для устаревших версий. GraphQL изменения проводить через `@deprecated`. gRPC совместимость обеспечить по правилам Protocol Buffers (добавлять поля, удалять только с `reserved`). SPARQL точка доступа сохранять совместимость на уровне W3C-стандарта. Автоматизировать тестирование совместимости API.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Полная строгая совместимость между мажорными версиями | Слишком ограничивает эволюцию API, схемы и моделей данных |
| Отсутствие обратной совместимости в major versions | Неприемлемо для корпоративных клиентов и отраслевых интеграций |
| Версионировать GraphQL через URL | Противоречит типичной практике эволюции схемы GraphQL и усложняет API клиентской части |
| Удалять protobuf поля без `reserved` | Ломает старых клиентов и создает риск повторного использования field numbers |
| Поддерживать старые REST versions бессрочно | Увеличивает стоимость сопровождения и матрицу совместимости |

## Последствия

**Положительные последствия:**
- Внешние REST-клиенты получают минимум 12 месяцев на миграцию.
- Клиентская часть GraphQL может эволюционировать без немедленного нарушающего изменения.
- gRPC контракты остаются безопасными при соблюдении правил protobuf.
- SPARQL сохраняет предсказуемую совместимость как W3C точка доступа.

**Отрицательные последствия:**
- Одновременная поддержка REST v1 и v2 увеличивает стоимость эксплуатации и тестирования.
- Устаревшие поля GraphQL нужно сопровождать до окончания периода устаревания.
- LTS и кастомные обратные переносы могут увеличивать нагрузку на управление релизами.

**Меры снижения рисков:**
- Автоматизировать тестирование совместимости API: запуск тестов v1 API против окружений v1 и v2.
- Публиковать заголовки `Warning` и `Sunset` для устаревших версий REST.
- Документировать график устаревания и дату окончания поддержки минимум за 12 месяцев.
- Для protobuf требовать code review на field numbers, `reserved` и запрещенные изменения типов.
