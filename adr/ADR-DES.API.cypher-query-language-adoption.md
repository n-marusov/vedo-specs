# ADR-DES.API.cypher-query-language-adoption

**Дата:** 2026-05-24  
**Статус:** ПРИНЯТО

## Контекст

VEDO Core хранит граф знаний в Neo4j (primary triple store). Основной язык запросов — SPARQL 1.1 (стандарт W3C для RDF). Однако Neo4j использует CYPHER как нативный язык запросов, который для многих графовых операций (обход по связям, поиск путей, MATCH-паттерны) естественнее и производительнее SPARQL. Пользователи-аналитики, знакомые с Neo4j, запрашивают поддержку CYPHER наравне с SPARQL.

## Решение

Добавить CYPHER как второй язык запросов к графу знаний VEDO Core, наравне с SPARQL 1.1.

CYPHER обеспечивает нативный доступ к Neo4j без прослойки SPARQL-to-CYPHER трансляции, что даёт прямую производительность и полную совместимость с existing Neo4j tooling. GUI Query Builder, текстовый редактор и NL-режим поддерживаются для обоих языков с одинаковым UX.

Визуальный конструктор CYPHER: пользователь выбирает метку узла, тип связи, целевой узел и фильтры; система генерирует MATCH/RETURN запрос.

Endpoint `/api/v1/cypher` реализуется по тому же шаблону, что и `/api/v1/sparql`: read-only (только MATCH/RETURN), аутентификация, авторизация, LIMIT, timeout, rate limiting, анализ query complexity, аудит.

## Рассмотренные альтернативы

- **Транслировать SPARQL → CYPHER** — теряется производительность, семантика SPARQL-конструкций (DESCRIBE, CONSTRUCT) не имеет прямого аналога в CYPHER; увеличивает сложность поддержки и время выполнения запросов
- **Только SPARQL через SPARQL-to-CYPHER мост** — ограничивает пользователей Neo4j-экосистемы, которые привыкли к CYPHER; снижает производительность для графовых обходов
- **Только CYPHER** — теряется совместимость со стандартом W3C SPARQL и семантическими RDF-инструментами

## Последствия

**Положительные последствия:**
- Пользователи Neo4j получают нативный доступ к графу знаний
- GUI Query Builder и NL-режим работают одинаково для SPARQL и CYPHER
- Оба endpoint следуют единому шаблону безопасности
- Introspection онтологии расширяется на метки узлов и типы связей (для CYPHER)

**Отрицательные последствия:**
- Два языка — двойная поддержка: документация, автодополнение, синтаксическая валидация
- Query complexity analysis требует разной логики для SPARQL и CYPHER
- Библиотека запросов требует поля `query_type` для различия языков

**Меры снижения рисков:**
- Единый UI-компонент Query Builder с выбором языка (SPARQL/CYPHER)
- Общая introspection-схема, расширенная для обоих языков
- Rate limiting и метрики раздельные по endpoint'ам
