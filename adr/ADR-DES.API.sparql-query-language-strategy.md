# ADR-DES.API.sparql-query-language-strategy: Выбор SPARQL как языка аналитических запросов к онтологии

**Дата:** 2026-05-12  
**Статус:** Принято

## Контекст

VEDO Core хранит и обрабатывает онтологии как граф знаний. Пользователям нужен язык запросов, который поддерживает RDF-графы, фильтрацию по свойствам и классам, семантическую навигацию и работу с произвольной структурой онтологии.

Клиентская схема не может быть полностью статической: граф пользователя может содержать произвольные классы, свойства и связи. Поэтому клиентская часть должна получать схему запроса через introspection текущей онтологии.

## Требование-источник
- [api-graphql-sparql.md](requirements/REQ-FUN.API.graphql-sparql.md)

## Решение

Использовать SPARQL 1.1 как язык аналитических семантических запросов к онтологии. Навигационные сценарии фронтенда выполняются через GraphQL.

SPARQL является W3C-стандартом для RDF/OWL и понятен инженерам Semantic Web, обеспечивая полную выразительность для фильтров, агрегаций и обходов графа переменной глубины. Визуальный Query Builder снижает порог входа для аналитиков, а текстовый редактор сохраняет выразительность для опытных пользователей. Introspection через REST JSON позволяет строить GUI для произвольных онтологий без фиксированных GraphQL-типов.

Предоставить публичный REST точка доступа `/api/v1/sparql` с аутентификацией, авторизацией, read-only enforcement, timeout, лимитом результатов, обязательным `LIMIT`, rate limiting и проверкой сложности запроса. В MVP разрешить только `SELECT` и `ASK`. Реализовать GUI с визуальным Query Builder и текстовым SPARQL-редактором. Схему запроса получать через introspection текущей онтологии.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Только GraphQL | Не покрывает всю выразительность SPARQL для сложной RDF/OWL-аналитики, фильтров, агрегаций и обходов переменной глубины. |
| REST API с фиксированными точками доступа | Не покрывает все возможные комбинации классов, свойств, фильтров и семантических обходов графа. |
| Cypher как публичный язык запросов | Привязан к Neo4j, не является W3C-стандартом для RDF/OWL и хуже переносим между RDF-хранилищами. |

## Последствия

**Положительные последствия:**
- SPARQL является W3C-стандартом для RDF и понятен инженерам Semantic Web.
- Визуальный Query Builder снижает порог входа для аналитиков и бизнес-пользователей.
- Текстовый редактор сохраняет полную выразительность для опытных инженеров.
- Introspection позволяет строить GUI для произвольных онтологий без фиксированных GraphQL-типов.
- REST JSON introspection ускоряет клиентскую часть и не смешивает ontology metadata с GraphQL navigation schema.

**Отрицательные последствия:**
- Точку доступа нужно защищать от SPARQL-инъекций, DoS и чрезмерно дорогих запросов.
- Пользователей текстового режима нужно обучить базовому SPARQL.
- Требуется отдельная модель query complexity и понятные ошибки для слишком сложных запросов.
- Turtle export требует проверки RDF-совместимости bindings.

**Меры снижения рисков:**
- Разрешать только SELECT/ASK в MVP production точку доступа; DESCRIBE/CONSTRUCT оставить post-MVP возможностью с role-gated permissions, graph-size limits, запретом external IRI/federation и timeout <= 15 секунд.
- Требовать `LIMIT`, timeout, result cap, rate limiting и complexity gate.
- Логировать запросы с redaction и связывать их с user, role, trace_id и результатом security checks.
- Хранить сохранённые запросы в PostgreSQL user settings и проектировать миграционный путь к `QueryLibraryService`.
- Для Turtle export принимать только RDF-compatible bindings, а mixed/scalar SELECT results направлять в CSV/JSON.
- Документировать работу с GUI в User Guide.
