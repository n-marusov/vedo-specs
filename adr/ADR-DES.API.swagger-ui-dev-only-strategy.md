# ADR-DES.API.swagger-ui-dev-only-strategy

**Дата:** 2026-07-18  
**Статус:** Принято

## Контекст

API Gateway VEDO Core уже обслуживает OpenAPI-спецификацию в формате JSON через endpoint `/api/v1/openapi.json` (встроена через `//go:embed`). Однако разработчикам и интеграторам для комфортной работы нужен интерактивный просмотрщик — Swagger UI — который позволяет визуально изучать endpoint-ы, отправлять тестовые запросы и видеть схемы данных.

Endpoint `/api/v1/docs` сейчас реализован как редирект на `/api/v1/openapi.json` с комментарием «placeholder for future UI».

Возникает вопрос: должен ли Swagger UI быть доступен во всех окружениях, включая production?

## Требование-источник
- [swagger-ui-dev-only.md](../requirements/REQ-FUN.API.swagger-ui-dev-only.md)

## Решение

Swagger UI встраивается в бинарник API Gateway как статические файлы (HTML/JS/CSS) через `//go:embed` и активируется исключительно в dev-окружении через переменную окружения `ENABLE_SWAGGER_UI=true`. В staging и production окружениях переменная отсутствует или равна `false` — endpoint `/api/v1/docs` возвращает `404 Not Found`.

Raw-спецификация `/api/v1/openapi.json` остаётся публичной во всех окружениях, так как она используется внешними инструментами (Postman, openapi-generator, CI-проверки контрактов) и не несёт рисков безопасности сама по себе.

### Обоснование

1. **Безопасность:** Swagger UI с функцией «try-it-out» в production — это потенциальный вектор для нежелательных операций (даже при наличии аутентификации). Dev-only подход полностью исключает этот риск.
2. **Поверхность атаки:** Swagger UI добавляет клиентский JavaScript-код и дополнительные HTTP-ресурсы, увеличивая поверхность атаки. В production это неоправданно.
3. **Производительность:** В production каждый килобайт трафика и каждая миллисекунда загрузки на счету. Swagger UI добавляет ~4 MB статики.
4. **Dev Experience:** Разработчикам Swagger UI критически нужен для отладки и тестирования API. В dev-окружении нет ограничений безопасности, характерных для production.
5. **Интеграторы:** Для внешних интеграторов достаточно raw OpenAPI JSON — они используют собственные инструменты (Postman, Insomnia, генераторы SDK).

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Swagger UI во всех окружениях | Увеличивает поверхность атаки; «try-it-out» в production нежелателен |
| Только raw JSON во всех окружениях | Неудобно для разработчиков — нужен визуальный просмотрщик |
| Вынести Swagger UI в отдельный сервис | Избыточно: это статика, не требующая отдельного контейнера |
| Использовать внешний Swagger UI (editor.swagger.io) | Зависимость от внешнего сервиса; не работает в air-gapped окружении |
| Генерировать Redoc вместо Swagger UI | Redoc не поддерживает «try-it-out»; Swagger UI — индустриальный стандарт |
| Включать Swagger UI через feature flag в рантайме | Усложняет логику; env-переменная при старте проще и надёжнее |

## Последствия

**Положительные последствия:**
- Разработчики получают интерактивную документацию API без Compose-Overrides и внешних инструментов.
- Production-окружение не получает лишней поверхности атаки.
- Raw OpenAPI JSON доступен всем интеграторам без ограничений.
- Встраивание через `//go:embed` не требует дополнительных контейнеров или сервисов.

**Отрицательные последствия:**
- Размер Docker-образа API Gateway увеличится на ~4 MB за счёт статики Swagger UI.
- Требуется условная маршрутизация в `routes.go` с проверкой `ENABLE_SWAGGER_UI`.

**Меры снижения рисков:**
- Статика Swagger UI фиксируется по версии (вендорится) для воспроизводимых сборок.
- Проверка `ENABLE_SWAGGER_UI` при старте с логированием статуса.
- В docker-compose production явно указано `ENABLE_SWAGGER_UI=false` (defense in depth).
- Добавить smoke-тест: в dev `/api/v1/docs` возвращает HTML, в staging/prod — 404.
