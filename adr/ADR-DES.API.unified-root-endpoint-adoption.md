# ADR-DES.API.unified-root-endpoint-adoption

**Дата:** 2026-05-13  
**Статус:** Принято

## Контекст

Каждый микросервис VEDO Core имеет `/health` и `/ready` эндпоинты для проверки состояния, но нет единого корневого эндпоинта, который возвращает метаданные сервиса. При диагностике, service discovery, runbook-ах и поддержке приходится обращаться к разным источникам (docker-compose, документация, env) чтобы узнать версию, описание и ссылки сервиса.

При этом функциональное взаимодействие между API Gateway и внутренними сервисами выполняется через gRPC/protobuf. Корневой HTTP точка доступа `/` не является разрешением публиковать REST CRUD/search/SPARQL/commit API внутри микросервисов.

## Требование-источник
- [unified-root-endpoint.md](requirements/REQ-FUN.API.unified-root-endpoint.md)

## Решение

Все микросервисы VEDO Core должны иметь единый корневой эндпоинт `/`, возвращающий JSON с метаданными по унифицированной схеме: service, version, status, uptime_seconds, description и links.

Единая схема корневой точки доступа даёт один источник метаданных для любого сервиса в стеке, упрощает диагностику, написание CLI/runbook команд и service discovery; новым сервисам не нужно обсуждать формат — достаточно следовать зафиксированной схеме. Status и uptime сразу показывают картину здоровья без отдельной проверки работоспособности.

HTTP management surface каждого внутреннего сервиса ограничен endpoints `/`, `/health`, `/ready`; все функциональные операции — только через gRPC/protobuf; публичные REST URL реализуются на API Gateway.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Не добавлять корневой эндпоинт | Затрудняет диагностику: приходится собирать метаданные из нескольких источников |
| Разные схемы для разных сервисов | Усложняет автоматизацию, service discovery и написание runbook-ов |
| Использовать только заголовки HTTP | Менее заметно и хуже документируется, чем JSON в теле ответа |
| Добавить метаданные только в `/health` | Смешивает ответственность health check-а и метаданных; `/health` должен оставаться быстрым и лёгким |
| Версионировать через заголовок `X-Service-Version` | Недостаточно информативно: нет описания, статуса, uptime и ссылок |

## Последствия

**Положительные последствия:**
- Единый источник метаданных для любого сервиса в стеке.
- Упрощается диагностика и написание CLI/runbook команд.
- Новые сервисы следуют той же схеме без дополнительного обсуждения.
- Status и uptime дают быструю картину здоровья без вызова отдельной точки доступа health.

**Отрицательные последствия:**
- Каждый сервис должен поддерживать root точку доступа — небольшое, но обязательное изменение.
- Потребуется синхронизация версии между релизами сервисов.

**Меры снижения рисков:**
- Унифицированная схема зафиксирована в ADR и должна проверяться в API smoke-тестах.
- Версионирование сервисов автоматизировать через CI (git tag → version в Docker image label и runtime).
