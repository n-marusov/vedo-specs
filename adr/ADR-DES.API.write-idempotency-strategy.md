# ADR-DES.API.write-idempotency-strategy

**Дата:** 2026-05-17  
**Статус:** Принято

## Контекст

Повторные запросы при сетевых сбоях, client retries и таймаутах приводят к дублирующим изменениям, если write API не имеет строгой идемпотентной семантики. Ранее в артефактах было только общее указание на `Idempotency-Key` без обязательного покрытия и release-gate.

## Требование-источник

- [api-write-idempotency.md](requirements/REQ-FUN.API.write-idempotency.md)
- [api-integration.md](requirements/REQ-FUN.API.integration.md)

## Решение

Сделать идемпотентность обязательной для критичных write операций (100%) и установить минимальное покрытие для всех production write endpoints (>= 99%) с блокировкой MR при нарушении порогов.

## Рассмотренные альтернативы

- Best-effort idempotency без coverage gate — отклонено (неизмеримость).
- Идемпотентность только на стороне клиента — отклонено (сервер не контролирует консистентность).
- Идемпотентность только для REST — отклонено (GraphQL mutations также меняют состояние).

## Последствия

- **Плюсы:** устранение класса дублей при retry, предсказуемые write semantics.
- **Минусы:** дополнительные затраты на хранение idempotency keys и contract tests.
- **Смягчение:** централизованный key-store и стандартизованный тестовый набор.
