# ADR-DES.DATA.account-closure-retention-strategy

**Дата:** 2026-05-10  
**Статус:** Принято

## Контекст

VEDO Core должен поддерживать закрытие аккаунта и обработку персональных данных в двух регуляторных режимах: GDPR для европейских клиентов и 152-ФЗ для российских клиентов. Требования различаются: GDPR требует возможности полного удаления персональных данных по праву на забвение (Right to be forgotten), а 152-ФЗ допускает обезличивание и более длительное хранение отдельных категорий данных и журналов.

## Требование-источник
- [account-closure-retention.md](requirements/REQ-NFR.DATA.account-closure-retention.md)

## Решение

Принять раздельную стратегию хранения данных после закрытия аккаунта в зависимости от юрисдикции клиента: GDPR (полное удаление по праву на забвение) и 152-ФЗ (обезличивание с более длительным хранением).

Раздельная политика позволяет соблюдать оба регуляторных режима без компромиссов. Период охлаждения 30 дней защищает от случайного закрытия и даёт время на передачу онтологий. UX-защиты (предварительный просмотр, вводимое подтверждение, dry-run) делают необратимые операции безопасными и проверяемыми. Общие онтологии не удаляются при закрытии аккаунта, что предотвращает потерю данных других пользователей.

Реализовать жизненный цикл: период охлаждения (0-30 дней, аккаунт деактивирован), удаление по GDPR (до 30 дней, ПДн удаляются), обезличивание по 152-ФЗ (после 30 дней, ПДн анонимизируются), архив аудита (1-5 лет). Audit logs хранить без прямой связи с пользователем. Общие онтологии передавать владельцу или блокировать до передачи. Применять обязательные UX-защиты: предварительный просмотр, вводимое подтверждение, dry-run, задержка необратимого действия.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Единая политика удаления для GDPR и 152-ФЗ | Регуляторные требования различаются и конфликтуют по срокам и способу обработки данных |
| Немедленное удаление аккаунта без cooling-off периода | Повышает риск случайной потери доступа и не даёт времени на передачу онтологий |
| Удалять shared ontologies вместе с пользователем | Может уничтожить данные других пользователей и организаций |
| Хранить ПДн бессрочно после закрытия аккаунта | Неприемлемо для GDPR и privacy-by-design |
| Удалять audit logs сразу при GDPR request | Может конфликтовать с законными требованиями расследования и аудита; безопаснее стереть связь с пользователем |

## Последствия

**Положительные последствия:**
- Закрытие аккаунта соответствует различиям GDPR и 152-ФЗ.
- Общие онтологии защищены от удаления из-за ухода одного пользователя.
- Пользователь получает 30 дней на восстановление или исправление ошибки.
- Audit logs сохраняют forensic value без прямой связи с удалённым пользователем.

**Отрицательные последствия:**
- Требуется хранить политику юрисдикции у аккаунта или tenant.
- Необходима автоматизация отложенных задач для деактивации, анонимизации, удаления и уведомлений.
- Требуется процедура передачи владения онтологиями перед закрытием аккаунта.
- Возможны сложные кейсы, когда пользователь требует GDPR deletion, но часть данных нужна для shared ontology или audit obligations.

**Меры снижения рисков:**
- Хранить `data_retention_policy` на уровне tenant/account.
- Запускать закрытие аккаунта через очередь задач, например RabbitMQ.
- Блокировать закрытие или блокировать онтологии, где пользователь является единственным владельцем, до передачи ownership.
- Стирать связь audit logs с user ID вместо удаления самих audit records, когда закон требует хранения.
- Уведомлять резервного администратора за 7 дней до окончания периода охлаждения.
