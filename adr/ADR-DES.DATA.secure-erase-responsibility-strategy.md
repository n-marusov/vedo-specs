# ADR-DES.DATA.secure-erase-responsibility-strategy

**Дата:** 2026-05-10  
**Статус:** Принято  
**Обновлено:** 2026-05-14 (актуализация по уточнённым требованиям secure-erase — проверка криптографического удаления)

## Контекст

Некоторые клиенты VEDO Core могут требовать физическое уничтожение данных при выводе системы из эксплуатации: государственный сектор, оборонная промышленность, финансовые организации с высоким уровнем секретности или сценарии смены подрядчика инфраструктуры. Однако физическое уничтожение зависит от типа развёртывания и доступа к слою хранения, поэтому не может быть одинаковой обязанностью VEDO во всех моделях развёртывания.

Уточнённые требования расширяют контекст нормативной базой (ФСТЭК N21, ГОСТ Р 50739-95, NIST SP 800-88, GDPR, 152-ФЗ) и вводят обязательную проверку криптографического удаления после decommission с верификацией каждого компонента инфраструктуры.

## Требование-источник
- [secure-erase.md](requirements/REQ-NFR.DATA.secure-erase.md)

## Решение

Принять модель разделения ответственности за secure erase в зависимости от модели развёртывания: облачный провайдер для SaaS, VEDO по контракту для private cloud, заказчик для on-premise.

Чёткая граница ответственности устраняет ожидание, что VEDO может физически уничтожить данные на носителях, к которым не имеет доступа. Заказчики on-premise получают обязательное требование шифрования дисков (LUKS, BitLocker) и процедуру логической очистки через `vedo-cli`. Для SaaS достаточно сертификатов облачного провайдера (SOC 2, ISO 27001). Допустимые подтверждения: audit logs удаления, справка облачного провайдера, акт уничтожения комиссии заказчика.

VEDO Core гарантирует логическое удаление через `vedo-cli decommission --purge-data`. Для on-premise требовать шифрования дисков с хранением ключей отдельно от данных. Физическое уничтожение выполнять по ГОСТ Р 50739-95 или NIST SP 800-88.

После decommission и purge данных обязательна проверка криптографического удаления через `vedo-cli decommission --verify-purge`: верификация удаления ключей шифрования диска Neo4j, очистки WAL PostgreSQL, удаления RDB/AOF-файлов Redis, отсутствия tenant-специфичных путей объектов в S3/MinIO, аннулирования токенов и сессий API Gateway и исключения backup-копий tenant из политики восстановления. Максимальное время проверки — 30 минут для backup, 15 минут для S3/MinIO, 10 минут для БД, 5 минут для Redis и API Gateway.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| VEDO всегда отвечает за физическое уничтожение | Невозможно для on-premise без доступа к носителям и инфраструктуре заказчика |
| Не поддерживать secure erase вообще | Неприемлемо для госзаказчиков, регулируемых корпоративных и высокочувствительных данных |
| Делать физическое уничтожение обязательным для всех | Избыточно для SaaS и обычных корпоративных развёртываний; повышает стоимость и сложность |
| Ограничиться только soft-delete | Недостаточно для клиентов с ФСТЭК, ГОСТ или NIST SP 800-88 требованиями |
| Полагаться только на многократную перезапись | SSD/NVMe wear leveling может сохранять данные; удаление ключей шифрования надёжнее при правильной архитектуре |

## Последствия

**Положительные последствия:**
- Граница ответственности ясна для SaaS, VEDO Managed и on-premise.
- VEDO не обещает физическое уничтожение там, где не контролирует носители.
- On-premise заказчики получают процедуру и требования к развёртыванию с шифрованием по умолчанию.
- Secure erase может быть продан как отдельная managed/private-cloud услуга.

**Отрицательные последствия:**
- Для on-premise выполнение secure erase зависит от дисциплины заказчика.
- Требуется документировать и поддерживать процедуры удаления ключей, логической очистки и сбора доказательств.
- Некоторые заказчики могут требовать договорных уточнений и актов уничтожения.

**Меры снижения рисков:**
- Включить в on-premise документацию раздел secure erase и матрицу ответственности.
- Требовать шифрование данных на уровне диска или СУБД для on-premise.
- Хранить encryption keys отдельно от данных.
- Предоставлять `vedo-cli decommission --purge-data` и audit logs удаления.
- Для SaaS хранить доказательства о соответствии cloud provider: SOC 2, ISO 27001 или аналогичные сертификаты.
