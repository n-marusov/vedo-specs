# ADR-DES.INFRA.monolith-vs-microservices

**Дата:** 2026-05-08  
**Статус:** Принято

## Контекст

VEDO Core — платформа для редактирования онтологий с тремя ключевыми доменами:
1. **Graph Operations** — хранение и запросы графов до 1M триплетов
2. **Version Control** — Git-подобное версионирование (коммиты, ветки, diff, merge)
3. **Collaboration** — параллельная работа через ветки, Merge Request'ы, семантический diff

Существующие решения (Protégé) имеют монолитную архитектуру и страдают от проблем производительности при масштабировании.

## Требование-источник
- [architecture-decomposition.md](requirements/REQ-FUN.PROCESS.architecture-decomposition.md)

## Решение

Декомпозировать VEDO Core на пять микросервисов по доменному принципу: Ontology Service (Rust), Versioning Service (Rust), Auth Service (Go), Metrics Service (Python) и API Gateway.

Микросервисная архитектура позволяет независимо масштабировать CPU-интенсивные сервисы (Ontology, Versioning) и I/O-интенсивные (Auth), изолировать отказы между доменами, использовать оптимальный язык для каждой зоны ответственности и дать каждой команде domain-driven ownership без конфликтов в единой кодовой базе.

Определить API-контракты между сервисами через gRPC/protobuf, организовать распределённую трассировку через OpenTelemetry и применить Saga pattern для транзакций, затрагивающих несколько сервисов.

## Рассмотренные альтернативы

**1. Монолит (единый процесс)**
- Проблема: единая кодовая база 3+ команд, частые merge-конфликты
- Проблема: невозможность независимого масштабирования Graph Operations и Versioning
- Проблема: долгий CI/CD — любое изменение требует полной сборки

**2. Модульный монолит**
- +Проще разрабатывать, общая БД
- - Общая база данных создаёт связанность между доменами
- - Schema-миграции Version Store блокируют Ontology Service
- - Невозможно использовать разные языки для оптимальных сценариев

**3. Два сервиса (Graph + Everything)**
- - Комментирование требует WebSocket-инфраструктуры для real-time доставки
- - Versioning имеет синхронные требования к UI (< 1 сек)
- - Разные команды имеют разные компетенции

**4. Collaboration Service**
- Проблема: противоречит pure Git модели параллельной работы через ветки
- Проблема: синхронные блокировки избыточны при асинхронном разрешении конфликтов

## Последствия

**Положительные последствия:**
- Независимое масштабирование: Ontology и Versioning масштабируются раздельно
- Изолированные команды: domain-driven ownership
- Материализованный кэш: активная ветка материализуется в Neo4j, дельты хранятся в PostgreSQL
- Независимый deploy: версионирование сервисов через API-контракты

**Отрицательные последствия:**
- Сложность распределённой трассировки
- Согласованность данных между сервисами (eventual consistency)
- Сетевая задержка при межсервисных вызовах
- Множественные CI/CD-пайплайны

**Меры снижения рисков:**
- OpenTelemetry для распределённого трейсинга
- Saga pattern для distributed transactions где необходимо
- gRPC contracts с versioned proto files
