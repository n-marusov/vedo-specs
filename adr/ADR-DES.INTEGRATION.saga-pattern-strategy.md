# ADR-DES.INTEGRATION.saga-pattern-strategy

**Дата:** 2026-05-13  
**Статус:** Принято

## Контекст

VEDO Core — микросервисная архитектура с 6+ сервисами и раздельными БД (Neo4j, PostgreSQL, Redis, RabbitMQ). Несколько логических операций требуют согласованных изменений в двух или более независимых хранилищах.

В `ADR-DES.INFRA.monolith-vs-microservices` паттерн Saga упомянут как мера снижения рисков, но без детализации. Анализ межсервисных потоков выявил, какие операции действительно требуют распределённой транзакции, а какие могут обойтись согласованностью в конечном счёте (eventual consistency).

**Ключевые межсервисные потоки:**

| Операция | Сервисы | Хранилища | Saga? |
|----------|---------|-----------|-------|
| **Rollback (откат коммита)** | Versioning → Ontology → Versioning | Neo4j + PostgreSQL | **Да** |
| **Import + Auto-Commit** | Ontology → Versioning | Neo4j + PostgreSQL | **Да** |
| Access Control Update | Auth → Keycloak → Redis | PostgreSQL + IdP + Cache | Нет |
| Publish Snapshot | Publisher → Public Neo4j | Neo4j × 2 | Нет |

## Требование-источник
- [saga-pattern.md](requirements/REQ-FUN.INTEGRATION.saga-pattern.md)

## Решение

Использовать оркестрируемую Saga для двух операций, где распределённая консистентность действительно необходима: Rollback (откат коммита) и Import + Auto-Commit. API Gateway выступает оркестратором через CommandDispatcher с последовательностью шагов и компенсирующими транзакциями.

Оркестрируемая Saga даёт гарантированную консистентность между Neo4j и PostgreSQL для критичных межсервисных потоков без блокировки ресурсов (в отличие от 2PC), с детерминированным потоком, единой точкой мониторинга и явным контролем таймаутов. Для остальных потоков (publish snapshot, access control) используется eventual consistency без координации.

Каждый шаг Saga обязан быть идемпотентным через idempotency_key в gRPC metadata и проверку статуса. Общий saga_id пробрасывается во все спаны для трассировки через vedo-cli diagnose. Таймауты: шаг — 30 секунд (3 retry), вся Saga — 5 минут (принудительная компенсация), компенсация — 60 секунд (3 retry, затем P1 escalation при failed_unrecoverable).

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| **Хореографическая Saga** (каждый сервис сам публикует события и компенсации) | Подходит для сложных рабочих процессов с множеством участников, но для двух простых Saga (3 шага) оркестрация даёт детерминированный поток, единую точку мониторинга и явный контроль таймаутов |
| **2PC (двухфазный коммит)** | Требует координатора транзакций и блокировки ресурсов на время подготовки. Для микросервисной архитектуры с разными БД (Neo4j + PostgreSQL) 2PC непрактичен. Saga даёт более гибкое управление и не блокирует данные |
| **Согласованность в конечном счёте + сверка** | Приемлемо для publish snapshot и access control, но для rollback и import+commit рассинхронизация между Neo4j и version store приводит к невосстановимой потере данных или неотслеживаемым изменениям |
| **Outbox + фоновая задача** | Работает для событий в стиле «отправил-и-забыл», но не гарантирует атомарность двух мутаций в разных хранилищах. При сбое между шагами нужен компенсирующий механизм, что и есть Saga |
| **Ручная сверка** | Неприемлемо для P0 операций. Rollback и import — частые действия пользователя, не могут требовать ручного вмешательства |

## Последствия

**Положительные последствия:**
- Два критичных межсервисных потока получают гарантированную консистентность через компенсирующие транзакции.
- Оркестрация через API Gateway даёт единую точку мониторинга, логирования и контроля таймаутов.
- Saga не блокирует ресурсы (в отличие от 2PC) — данные доступны для чтения между шагами.
- Чёткое разделение: только Rollback и Import+Commit требуют Saga; остальные потоки используют согласованность в конечном счёте.
- Идемпотентность шагов позволяет безопасно повторять без дублирования.

**Отрицательные последствия:**
- API Gateway (`CommandDispatcher`) становится критическим звеном для Saga-операций.
- Каждая Saga добавляет 3-4 gRPC вызова вместо одного, увеличивая задержку.
- Необходимо хранить состояние Saga (pending/committed/cancelled).
- Компенсирующие транзакции — дополнительный код и тестирование.
- `failed_unrecoverable` состояние требует P1-эскалации и ручного восстановления.

**Меры снижения рисков:**
- Координатор Saga реализуется как слой без состояния (stateless) в API Gateway; состояние хранится в Versioning Service (PostgreSQL).
- Все шаги идемпотентны через ключ идемпотентности.
- Все Saga логируются с `saga_id` для диагностики.
- Таймаут 5 минут на всю Saga предотвращает бесконечное зависание.
- `failed_unrecoverable` обрабатывается через P1-алерт и runbook.
- Для операций, не требующих Saga (publish, access control), используется согласованность в конечном счёте без координации.
- Покрыть обе Saga приёмочными тестами с симуляцией отказа каждого шага.
