# ADR-DES.PROCESS.decommission-drill-strategy

**Дата:** 2026-05-13  
**Статус:** Принято  
**Обновлено:** 2026-05-14 (актуализация по уточнённым требованиям decommission-usability)

## Контекст

Матрица качества выявила лакуну `2.4 Эргономика × Утилизация`: были определены форматы экспорта, secure erase и retention, но не было измеримого human-factor требования, доказывающего, что администратор способен безопасно выполнить вывод из эксплуатации без помощи вендора.

Уточнённые требования decommission-usability детализируют: четыре уровня учений с разделением исполнителей, статусную модель вывода из эксплуатации, режим предварительной проверки (`vedo-cli decommission plan`), offline-доступность инструкций, обязательную изоляцию staging-кластера от production, подтверждение двумя администраторами для разрушительных операций над tenant, массовое покрытие учений (минимум 3 tenant с каноническим профилем) и эталонный профиль данных как часть поставки.

## Решение

Ввести обязательные сценарии учений по выводу из эксплуатации с разделением ответственности: CI/CD Smoke-учения (DevOps VEDO, пустой tenant, ≤ 30 мин), внутренние P0/P1-учения (канонический профиль, ≤ 4 ч), приёмочные учения (администратор заказчика, условие приёмки on-premise) и Enterprise-учения (ежегодно по запросу).

Четырёхуровневая система учений закрывает лакуну качества `2.4 Эргономика × Утилизация` измеримыми human-factor требованиями: пустой tenant проверяет pipeline после коммита, канонический профиль 1M/100K выявляет таймауты и когнитивную нагрузку оператора, а приёмочные учения с администратором заказчика доказывают, что decommission выполним без помощи вендора.

Статусная модель decommission (not_started → exporting → export_verified → restore_verified → pending_retention_expiry → crypto_erased → failed → completed) обеспечивает однозначную видимость каждого этапа с текстовым объяснением на русском языке и следующим допустимым действием. Режим предварительной проверки (`vedo-cli decommission plan --tenant`) не изменяет состояние данных и завершается ненулевым кодом при неполной конфигурации целей экспорта.

Приёмочные учения decommission выполняются администратором заказчика в изолированном staging-кластере (аналогичном production по типам узлов, объёму дисков и сетевым политикам). Учения на production-оборудовании допускаются только при соблюдении пяти условий: полный верифицированный backup, изоляция данных, инфраструктурная изоляция, защита CLI с предупреждением, режим «только чтение» для опасных фаз. Подтверждение двумя администраторами обязательно для tenant delete, tenant purge, backup delete (последняя копия) и ontology delete (единственная в tenant). Массовые учения decommission покрывают минимум 3 tenant с каноническим профилем с успешностью 100% для экспорта и purge, 95% для проверки целостности после восстановления.

VEDO Core поставляет decommission-drill-runbook.md (автор и владелец — команда VEDO, неотъемлемая часть поставки), `vedo-cli tenant seed --profile canonical` для развёртывания эталонного профиля, canonical-profile-manifest.yaml и guardrails для production-оборудования (backup verify, read-only mode, предупреждение CLI).

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Проверять только пустой tenant | Не выявляет таймауты, неполные manifest, ошибки на больших данных и когнитивную нагрузку оператора |
| Учения выполняет только DevOps VEDO | Не закрывает real-world human-factor для заказчика и vendor shutdown сценариев |
| Runbook пишет заказчик | VEDO не может гарантировать корректность и полноту процедуры |
| Данные для учений генерирует заказчик | Результаты приемки становятся несопоставимыми и невоспроизводимыми |

## Последствия

**Положительные последствия:**
- Лакуна `2.4` закрывается измеримым требованием.
- `3.4`, `4.4`, `5.4` получают prerequisite по human-factor.
- Приемка on-premise и air-gapped сценариев становится воспроизводимой.

**Отрицательные последствия:**
- Поставка усложняется: нужен генератор канонического профиля, manifest и runbook.
- Release readiness требует дополнительных доказательств учений.

**Меры снижения рисков:**
- Канонический профиль фиксируется в manifest с checksum и количеством сущностей.
- Учения с пустым tenant остаются быстрым CI/CD smoke gate, но не заменяют release validation.
