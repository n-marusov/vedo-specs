# ADR-DES.PROCESS.deployment-strategy-policy

**Дата:** 2026-05-11  
**Статус:** Принято

## Контекст

VEDO Core должен поддерживать разные стратегии развертывания для dev, staging и production. Не все заказчики имеют ресурсы для blue-green развёртывания, но production major updates и schema-changing релизы требуют безопасного пути отката. Canary релизы полезны для крупных инсталляций и A/B-тестирование, но требуют сервисной сетки и дополнительной эксплуатационной сложности.

## Требование-источник
- [deployment-strategy.md](requirements/REQ-CON.INFRA.deployment-strategy.md)

## Решение

Принять дифференцированную политику стратегий развёртывания: rolling update для dev, staging и production minor/patch; blue-green для production major updates (обязателен при достаточных ресурсах); canary — опционально для крупных инсталляций и A/B-тестирование.

Дифференциация сохраняет простоту для частых minor-обновлений через rolling update, обеспечивает безопасное переключение трафика и быстрый откат для major-версий через blue-green, и добавляет canary как опцию для крупных заказчиков без навязывания сервисной сетки всем остальным.

Rolling update оставить стратегией Helm по умолчанию; blue-green и canary включаются через values-флаги; для major-обновлений без blue-green документировать окно обслуживания и runbook отката.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Всегда rolling update | Недостаточно безопасно для production major updates и schema-changing releases |
| Всегда blue-green | Требует вдвое больше ресурсов и не всегда доступно on-premise заказчикам |
| Всегда canary | Слишком сложно, требует сервисной сетки и длительного развёртывания |
| Только ручные окна обслуживания | Увеличивает простой и ухудшает взаимодействие с заказчиком |
| Автоматическое переключение production traffic | Рискованно; production switch должен требовать ручного подтверждения |

## Последствия

**Положительные последствия:**
- Простые minor/patch updates остаются дешёвыми через rolling update.
- Major production updates получают безопасное переключение трафика и быстрый откат через blue-green.
- Canary можно включить для крупных customers без навязывания сервисная сетка всем.
- Helm chart остаётся простым по умолчанию, но поддерживает расширенные стратегии.

**Отрицательные последствия:**
- Blue-green требует примерно вдвое больше ресурсов на время переключения.
- Canary добавляет зависимость от сервисная сетка и эксплуатационную сложность.
- Нужно документировать запасной вариант, если blue-green невозможен у on-premise заказчика.

**Меры снижения рисков:**
- Rolling update остаётся стратегией Helm по умолчанию.
- Blue-green включается через `bluegreen.enabled=true`.
- Canary выключен по умолчанию через `canary.enabled=false`.
- Переключение production-трафика и откат выполняются ручными заданиями.
- Для major updates без blue-green требуется maintenance window и rollback runbook.
