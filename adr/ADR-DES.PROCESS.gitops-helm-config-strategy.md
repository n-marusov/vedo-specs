# ADR-DES.PROCESS.gitops-helm-config-strategy

**Дата:** 2026-05-11  
**Статус:** Принято

## Контекст

VEDO Core разворачивается в нескольких окружениях: dev, staging и production. Окружения отличаются количеством реплик, лимитами ресурсов, ingress-хостами, топологией БД, режимом Redis Cluster, мониторингом, логированием, SSL и настройками резервного копирования. Нужен воспроизводимый и проверяемый способ управлять конфигурацией без хранения секретов в Git.

## Требование-источник
- [environment-configuration.md](requirements/REQ-CON.INFRA.environment-configuration.md)

## Решение

Использовать GitOps с единым Helm chart и файлами values для каждого окружения: `helm-chart/values.yaml` (умолчания), `k8s/dev/values.yaml`, `k8s/staging/values.yaml`, `k8s/prod/values.yaml`; секреты передавать через masked-переменные GitLab CI/CD, Kubernetes Secrets или external secrets operator.

Подход фиксирует несекретную конфигурацию в Git с полным аудиторским следом, делает различия между dev, staging и production явными и воспроизводимыми, сохраняет единый Helm chart для всех сред и оставляет секреты за пределами репозитория.

Применять конфигурацию через `helm upgrade --values k8s/<env>/values.yaml` в CI/CD; валидировать values в CI; для production использовать external secrets operator (AWS Secrets Manager, HashiCorp Vault или аналог).

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Ручная настройка окружений через kubectl | Нет аудиторского следа, высокий риск расхождения конфигураций между окружениями |
| Один файл values для всех сред | Смешивает настройки dev/staging/production и повышает риск случайной неправильной настройки production |
| Хранить секреты в файлах values | Неприемлемо по требованиям безопасности и противоречит правилу no secrets in Git |
| Управлять конфигурацией только через CI variables | Плохо масштабируется для сложных настроек Helm и ухудшает проверяемость изменений |
| Отдельные Helm charts для каждой среды | Дублирование шаблонов и риск расхождения поведения |

## Последствия

**Положительные последствия:**
- Несекретная конфигурация получает аудиторский след в Git и проходит code review.
- Различия между dev, staging и production явно видны в отдельных файлах values.
- Helm chart остаётся единым для всех сред.
- Секреты остаются вне Git.
- GitLab CI применяет конфигурацию воспроизводимо.

**Отрицательные последствия:**
- Нужно поддерживать дисциплину ревью для изменений файлов values.
- При большом количестве окружений может вырасти число файлов values.
- External secrets operator добавляет инфраструктурную зависимость для production.

**Меры снижения рисков:**
- Валидировать Helm values в CI.
- Документировать обязательные поля для dev, staging и production.
- Использовать masked-переменные GitLab для простых секретов и внешнее хранилище секретов для production.
- Запрещать secrets in Git через lint и сканирование секретов.
