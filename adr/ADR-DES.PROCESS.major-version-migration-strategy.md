# ADR-DES.PROCESS.major-version-migration-strategy

**Дата:** 2026-05-10  
**Статус:** Принято

## Контекст

VEDO Core хранит данные в нескольких связанных хранилищах: TBox и ABox в Neo4j, Version Store в PostgreSQL, LFS-объекты в S3/MinIO-compatible storage и аудит в observability/log storage. Мажорная версия может менять схему БД, формат коммитов, API точки доступа и форматы импорта/экспорта, поэтому major upgrade не может быть обычным rolling развёртыванием без формальной миграционной процедуры.

## Решение

Принять формальную процедуру миграции мажорной версии с обязательными фазами: карта миграции, резервное копирование перед миграцией, тестовая миграция, проверка целостности, согласование окна, проверка совместимости API, производственная миграция, послемиграционный мониторинг и документированный план отката.

Формальная процедура превращает мажорное обновление из рискованного события в управляемый процесс с известными фазами, ответственными и артефактами. Резервное копирование, проверки целостности и откат становятся обязательной частью готовности релиза. API-клиенты получают явное окно совместимости (12 месяцев REST, 9 месяцев GraphQL). Blue-green развёртывание снижает риск для критических развёртываний.

Выполнять последовательное обновление `n-2 → n-1 → n`, прямой переход через несколько мажорных версий не поддерживать. Blue-green предпочтителен, in-place допустим при отсутствии второго окружения. Резервное копирование перед миграцией обязательно для всех компонентов. Откат в течение 60 минут после обновления (RTO 30-60 мин, потеря данных до 60 мин). REST API предыдущей мажорной версии поддерживать минимум 12 месяцев через `/api/v1/` с заголовками устаревания.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Rolling deploy без миграционного окна | Не покрывает обратно несовместимые изменения схемы БД, API и формата коммитов |
| Только in-place migration | Увеличивает простой и усложняет быстрый откат для критических/корпоративных развёртываний |
| Только blue-green migration | Не всегда доступна для on-premise или окружений без ресурсов под вторую площадку |
| Поддержка прямого обновления через несколько мажорных версий | Сильно увеличивает матрицу совместимости и риск потери данных |
| Миграция по остаточному принципу без пробного прогона | Нельзя заранее оценить простой и проверить целостность на данных, приближенных к производственным |
| Мажорная миграция без окна совместимости API | Ломает корпоративные интеграции и не дает клиентам времени на переход |
| Полный откат через несколько дней как стандартная опция | Требует сложной двунаправленной миграции и создает высокий риск потери данных |

## Последствия

**Положительные последствия:**
- Мажорное обновление становится управляемым процессом с известными фазами, ответственными и артефактами.
- Резервное копирование, проверки целостности и откат становятся обязательной частью готовности релиза.
- Заказчики получают понятные ожидания по простою, уведомлениям и поддерживаемым путям обновления.
- Blue-green снижает риск для критических развёртываний, а in-place остается доступным запасной вариант для ограниченных окружений.
- API-клиенты получают явное окно совместимости и график устаревания.
- Rollback пользовательских данных имеет фиксированные RTO/RPO границы.

**Отрицательные последствия:**
- Major релиз требует больше подготовки: Migration Map, sandbox environment, runbook, restore testing.
- Эксплуатация становится сложнее для on-premise и private cloud развёртываний.
- Последовательный upgrade `n-2 -> n-1 -> n` может увеличить длительность обновления для заказчиков, пропустивших major versions.
- Одновременная поддержка старых API и новой major версии увеличивает стоимость тестирования и эксплуатации.
- Быстрый rollback major version может потерять до 60 минут пользовательской работы.

**Меры снижения рисков:**
- Автоматизировать миграционный тестовый конвейер: поднятие тестового окружения, запуск `migrate-major.sh`, `verify-integrity.sh`, фиксация простоя.
- Автоматизировать тестирование совместимости API: запуск тестов v1 API против окружений v1 и v2.
- Требовать примечания к релизу, runbook и инструкции по откату как обязательные документы мажорного релиза.
- Использовать backup policy из `ADR-DES.INFRA.backup-policy-strategy` как prerequisite для major migration.
- Использовать read-only mode перед rollback данных и уведомлять пользователей о backup/upgrade/rollback timestamps.
- Применять флаги возможностей, canary развёртывание, shadow mode и Grafana dashboards для раннего обнаружения проблем.
- Для on-premise явно документировать ответственность заказчика и поддерживаемые пути обновления.
