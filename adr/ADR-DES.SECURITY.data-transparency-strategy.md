# ADR-DES.SECURITY.data-transparency-strategy — Стратегия прозрачности передачи данных LLM-провайдерам

**Статус:** ПРЕДЛОЖЕНО
**Дата:** 2026-07-16

## Контекст

Стратегия роутинга LLM-запросов (`ADR-DES.API.llm-policy-router-strategy`) определяет техническую сторону: какой провайдер, для какой онтологии, с consent или без. Consent-диалог перед первым NL-запросом уже описан в `REQ-USR.UI.external-llm-consent`.

Однако остались нераскрытыми аспекты прозрачности:

1. **Позиция VEDO по гарантиям:** Может ли VEDO гарантировать, что провайдер не использует данные для обучения?
2. **Жизненный цикл согласия:** Как пользователь отзывает consent после его предоставления?
3. **Изменение состава провайдеров:** Как уведомлять пользователей при добавлении/удалении провайдера?
4. **Документирование:** Где и как описана передача данных для compliance (GDPR Articles 13-14)?

**Samsung incident (2023):** Инженеры использовали ChatGPT, не зная о передаче данных. Урок: клиент должен **знать** и **сознательно принимать** факт передачи.

**Реалистичная позиция VEDO (архитектурное решение):**
> В SaaS данные передаются внешнему LLM-провайдеру. Это архитектурный факт. VEDO **не даёт ложных гарантий** о неиспользовании данных для обучения — такие гарантии от стороннего провайдера являются юридической фикцией. Единственная альтернатива для полного контроля — on-premise с локальной LLM.

Эта позиция зафиксирована в `REQ-FUN.DOC.llm-privacy-policy` и `REQ-BIZ.SUP.tier-data-transparency`.

## Требование-источник

- `REQ-USR.UI.consent-withdrawal` — отзыв согласия (новое, дополняет `REQ-USR.UI.external-llm-consent`)
- `REQ-USR.UI.provider-change-notification` — уведомление о смене провайдеров (новое)
- `REQ-FUN.DOC.llm-privacy-policy` — раздел в документации (новое)
- `REQ-BIZ.SUP.tier-data-transparency` — различие по тарифам (новое)

Остальные аспекты (consent-диалог, выбор провайдера, on-premise как альтернатива, аудит) уже покрыты `ADR-DES.API.llm-policy-router-strategy` и связанными REQ Блока 1.1.

## Решение

Дополнить существующую стратегию (`llm-policy-router-strategy`) четырьмя новыми элементами:

### 1. Позиция о гарантиях (Privacy Policy)

VEDO явно декларирует в privacy policy и документации:

> «VEDO Hub SaaS передаёт данные онтологии внешним LLM-провайдерам (OpenAI, Anthropic, Google). Это необходимо для работы AI-функций. VEDO не может гарантировать, что провайдеры не используют данные для обучения моделей — это определяется политикой самого провайдера. Если вам нужен полный контроль над данными, используйте VEDO Hub on-premise с локальной LLM.»

Документация (`REQ-FUN.DOC.llm-privacy-policy`) и тарифная страница (`REQ-BIZ.SUP.tier-data-transparency`) явно отражают эту позицию.

### 2. Отзыв согласия (Consent Withdrawal)

Дополняет механизм consent из `llm-policy-router-strategy`:

```
Настройки → Конфиденциальность → «Отозвать согласие»
  → Диалог подтверждения
  → AI-функции блокированы
  → Аудит (granted/withdrawn)
  → Повторное согласие доступно
```

**Отличие от существующего consent:** Существующий consent работает на уровне сессии (до закрытия вкладки). Отзыв — на уровне аккаунта (персистентный, до повторного согласия). Реализация: `REQ-USR.UI.consent-withdrawal`.

### 3. Уведомление о смене провайдеров

При добавлении или удалении LLM-провайдера все активные пользователи получают уведомление (in-app banner на 7 дней + email). Содержит: название провайдера, ссылку на privacy policy, дату изменения. Реализация: `REQ-USR.UI.provider-change-notification`.

### 4. Тарифные различия

| План | Подход |
|------|--------|
| **Community** | Явное информирование; данные публичных онтологий |
| **Pro / Team** | Consent + информирование; включает приватные онтологии |
| **Enterprise** | Индивидуальное соглашение; приоритетная опция on-premise |
| **On-premise** | Локальная LLM; данные не покидают периметр |

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Гарантировать «провайдер не использует данные» | Юридическая фикция — VEDO не контролирует политику стороннего провайдера |
| Не информировать о передаче данных | Samsung incident (2023); нарушение GDPR Articles 13-14 |
| Блокировать AI-функции для всех приватных онтологий | Делает AI-функции бесполезными в SaaS |
| Не уведомлять о смене провайдеров | Пользователи должны знать, кому передаются их данные |

## Последствия

**Положительные:**
- Доверие через честность — клиенты знают реальное положение дел
- Юридическая защита — VEDO явно декларирует ограничения, не давая ложных гарантий
- Гибкость — клиент выбирает между SaaS (удобство) и on-premise (контроль)

**Отрицательные:**
- Часть клиентов может выбрать on-premise или отказаться от AI-функций
- Необходимость поддерживать документацию в актуальном состоянии

**Риски:** Изменение политики провайдера (начал использовать данные для обучения).
**Смягчение:** Мониторинг политик провайдеров, немедленное уведомление клиентов.
