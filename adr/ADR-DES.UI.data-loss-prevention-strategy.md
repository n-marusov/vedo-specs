# ADR-DES.UI.data-loss-prevention-strategy

**Дата:** 2026-05-10  
**Статус:** Принято

## Контекст

VEDO Core хранит и редактирует онтологии, где знания являются основным активом. UX-дефекты, которые приводят к потере введённых данных, скрытому несохранению или ложному сообщению об успехе, являются критичными для доверия к продукту и блокируют MVP.

## Требование-источник
- [data-loss-prevention.md](requirements/REQ-NFR.UI.data-loss-prevention.md)

## Решение

Использовать двухуровневую архитектуру защиты от потери данных: локальный Draft Store на клиентской части и подтверждённое server-side persistence через read-after-write.

Draft Store защищает пользовательский ввод при сбое вкладки, accidental reload и потере сети, не требуя серверного API для черновиков в MVP. Read-after-write делает save-состояние проверяемым и исключает ложный success при рассинхронизации кэша и серверной части. Единый UI state machine (`draft`, `saving`, `persisted`, `failed`, `stale`) уменьшает дублирование логики в формах и упрощает восстановление после ошибок.

Draft Store хранить по составному ключу `user_id + ontology_id + entity_type + entity_id/form_id`. Серверная часть остаётся источником истины; локальный draft не считается сохранённым состоянием домена. Browser lifecycle hooks (`beforeunload`, route guards) подключить к Draft Store. При remote change показывать restore/overwrite/discard flow.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Только серверное сохранение без локального Draft Store | Не покрывает сбой вкладки, accidental reload и потерю незавершённой формы |
| Серверные черновики для всех форм | Усложняет MVP отдельным API и lifecycle для draft-сущностей |
| Чистый optimistic update без read-after-write | Создаёт риск ложного success при рассинхронизации cache/серверной части |

## Последствия

**Положительные последствия:**
- Единый Draft Store уменьшает дублирование логики в формах.
- Read-after-write делает save-состояние проверяемым и снижает риск ложного success.
- UI получает явную модель состояний для ошибок, восстановления и повторной отправки.

**Отрицательные последствия:**
- Нужно проектировать миграцию и очистку draft schema.
- Появляется конфликт `local draft` vs `remote changed entity`.
- Local storage нельзя использовать для секретов и чувствительных токенов.

**Меры снижения рисков:**
- Хранить только пользовательский ввод формы без credentials.
- Версионировать draft payload.
- При remote change показывать restore/overwrite/discard flow.
