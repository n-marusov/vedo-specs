# ADR-DES.UI.usability-release-gates-strategy

**Дата:** 2026-05-10  
**Статус:** Изменено  
**Обновлено:** 2026-05-18 — добавлены конкретные пороги TTFT и TTL по результатам юзабилити-теста (7 пользователей)

## Контекст

В артефактах usability зафиксированы `time-to-first-task` (TTFT), `time-to-learn` (TTL) и критичность UX-ошибок. Чтобы эти требования не остались декларативными, их нужно включить в релизные gates.

Проведён юзабилити-тест: 7 пользователей, [дата], версия [версия]. По результатам теста установлены измеримые пороги TTFT для пяти ключевых сценариев и порог TTL.

## Решение

Расширить конвейер релиза отдельным Usability Gate, агрегирующим автоматические UX smoke tests, ручной checklist и summary usability-study.

Выделенный usability gate превращает UX-требования (time-to-first-task, time-to-learn, P0/P1 классификацию) из декларативных артефактов в проверяемые критерии релиза, объединяя автоматические и ручные проверки в единый decision point без смешивания с функциональными тестами.

Gate принимает входы из Playwright-сценариев, accessibility checks, UX P0 checklist и отчёта usability-сессии; thresholds читаются из usability artifacts, P0/P1 классификация — из ux-critical-errors.md; risk acceptance для P1 фиксируется явно.

### Конкретные пороги Usability Gate

**Time to First Task (TTFT)** — время от появления главного экрана до успешного завершения сценария.

| Сценарий | Медиана (target) | Порог p90 (blocker) | Единица измерения |
|----------|------------------|---------------------|-------------------|
| Создание класса в пустой онтологии | 18 | 40 | секунд |
| Создание класса с родителем и описанием | 25 | 55 | секунд |
| Импорт .ttl-файла (до 10 МБ) | 35 | 75 | секунд |
| Поиск класса по названию и открытие карточки | 22 | 50 | секунд |
| Создание ветки и коммит изменения | 52 | 100 | секунд |

Любой сценарий, превышающий p90-порог, считается blocker-дефектом usability и блокирует релиз (если не утверждён risk acceptance Product Manager).

**Time to Learn (TTL)** — время, за которое пользователь без предварительного чтения документации выполняет базовый набор действий: создать класс, найти элемент, открыть карточку, сохранить изменение, объяснить по UI статус результата.

| Метрика | Медиана (target) | Порог p90 (blocker) | Единица измерения |
|---------|------------------|---------------------|-------------------|
| TTL | 47 | ≥ 90 | минут |

Превышение p90-порога TTL возвращает интерфейс на доработку: навигация, заметность основных действий, тексты статусов и подсказки.

## Методология измерений

**TTFT (Time to First Task):**
1. Пользователь уже авторизован. Стартовая точка — момент появления главного экрана после входа.
2. Модератор выдаёт сценарий из таблицы выше без дополнительных пояснений.
3. Зачётная точка — успешное завершение сценария (например, класс появился в дереве, файл импортирован, ветка создана).
4. Измерение останавливается в зачётной точке. Повторные попытки внутри одного сценария не сбрасывают таймер.
5. В зачёт идёт медиана по группе (не менее 5 пользователей). Для автоматических прогонов — p90 по 10+ запускам.

**TTL (Time to Learn):**
1. Пользователь начинает после авторизации без предварительного чтения документации.
2. Модератор выдаёт сценарий: создать класс, найти элемент, открыть карточку, сохранить изменение, объяснить по UI статус результата.
3. Время измеряется от появления главного экрана до успешного завершения всех действий.
4. В зачёт идёт медиана по группе (не менее 5 пользователей).

**Условия валидности замера:**
- Сетевая задержка между клиентом и сервером не более 50 мс (RTT).
- Браузер — последняя стабильная версия Chrome/Chromium.
- Отключены расширения, замедляющие загрузку страницы.
- Бэкенд нагружен не более чем на 30% от предельной мощности.

## Автоматизация

Стабильная часть Usability Gate автоматизирована через Playwright в CI:

| Компонент | Что измеряет | Порог срабатывания |
|-----------|-------------|-------------------|
| Playwright-скрипты TTFT | Время выполнения каждого из 5 сценариев | p90 из таблицы TTFT (40–100 секунд в зависимости от сценария) |
| Accessibility checks (axe-core) | Количество и severity нарушений WCAG | 0 нарушений уровня A/AA |
| Screenshot diff | Визуальные регрессии ключевых экранов | Любое изменение > 1% пикселей требует ручного подтверждения |

Playwright-прогон выполняется на каждый MR в ветку релиза. При превышении p90-порога хотя бы по одному сценарию CI помечает gate как failed. Если превышение вызвано изменением кода — MR блокируется. Если превышение вызвано изменением окружения (нагрузка, сеть) — gate перезапускается автоматически однократно.

Thresholds в CI синхронизированы с таблицей TTFT и читаются из единого конфигурационного файла `usability-gate-thresholds.json` в корне репозитория.

## Срок действия и пересмотр

| Параметр | Значение |
|----------|----------|
| Период действия порогов | До следующего полного юзабилити-теста (но не более 6 месяцев) |
| Пересмотр | При каждом major-релизе, при изменении ключевых сценариев или архитектуры UI |
| Исключение | Patch-релизы — пороги не пересматриваются, gate использует текущие значения |

Пороги утверждаются Product Manager на основе результатов юзабилити-теста. Изменение порогов без нового теста требует письменного обоснования и утверждения Product Manager.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Держать usability вне конвейера релиза | UX-долг не будет блокировать релиз даже при P0 проблемах |
| Встроить все UX checks в обычные contract tests | Теряется различие между функциональной корректностью и usability readiness |
| Полностью автоматизировать usability | Часть сигналов требует наблюдения за пользователем и экспертной оценки |
| Единый порог для всех сценариев TTFT | Каждый сценарий имеет разную сложность; единый порог был бы либо слишком жёстким для сложных сценариев, либо слишком мягким для простых |

## Последствия

**Положительные последствия:**
- Usability становится управляемым артефактом релиза, а не набором пожеланий.
- Автоматические и ручные проверки объединяются в один decision point.
- Thresholds можно менять в artifacts без переписывания архитектуры gate.
- Конкретные пороги TTFT и TTL дают однозначный критерий прохождения gate.

**Отрицательные последствия:**
- Конвейер релиза получает не полностью автоматический gate (ручной checklist остаётся).
- Нужно хранить и версионировать usability evidence.
- Пороги привязаны к текущей версии UI и могут устаревать при изменении сценариев.

**Меры снижения рисков:**
- Автоматизировать стабильную часть gate через Playwright/a11y checks.
- Для ручных входов использовать короткий шаблон отчёта и фиксированный P0/P1 checklist.
- Пересматривать пороги при каждом major-релизе или изменении ключевых сценариев.
- Хранить thresholds в едином JSON-файле для синхронизации CI и документации.
