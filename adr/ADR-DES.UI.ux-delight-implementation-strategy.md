# ADR-DES.UI.ux-delight-implementation-strategy

**Дата:** 2026-05-23  
**Статус:** ПРИНЯТО

## Контекст

В `human/artifacts/requirements/REQ-USR.UI.delight-features.md` зафиксирован UX Delight как обязательная часть качества продукта: мгновенная отзывчивость, предсказание действий пользователя, клавиатурное мастерство, безопасные destructive-flow и эмоционально-позитивный характер интерфейса.

Без единой реализации эти требования будут внедряться фрагментарно по компонентам, что приведёт к расхождению UX-поведения, деградации производительности на больших онтологиях и нестабильной приоритизации между "функционально работает" и "приятно и быстро работает".

## Решение

Принять **Delight-by-default implementation strategy**: UX Delight реализуется как системный слой интерфейса с обязательными runtime-бюджетами, общими interaction-паттернами и релизной приоритизацией P0/P1/P2.

Стратегия закрепляет, что `D-01..D-05`, `D-14`, `D-17`, `D-19`, `D-28`, `D-29` являются release-blocking для MVP и проверяются как часть definition of done для UI-фич. Для них вводится единая инфраструктура:  
- **Latency budget layer:** p95 интеракций `<100 мс`, deferred progress indicator после `200 мс`.
- **Optimistic mutation layer:** единый контракт optimistic update + rollback + визуальный сигнал успеха/ошибки.
- **Command layer:** палитра команд и глобальный поиск как first-class API для действий UI.
- **Safe destructive layer:** обязательный impact preview перед удалением + пути отката.
- **Adaptive motion layer:** анимации включены по умолчанию, но отключаются/упрощаются при больших батчах (например, `>50` узлов) или при риске деградации FPS.

Функции P1/P2 внедряются итеративно, но не должны нарушать бюджеты P0 по скорости и стабильности.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Внедрять delight-фичи локально в каждом модуле | Невозможно обеспечить консистентные пороги скорости и одинаковые UX-паттерны |
| Отложить весь Delight до post-MVP | Риск повторения сценария Protégé: функционально, но без продуктовой любви и низкий stickiness |
| Делать анимации без адаптивного деградационного режима | На крупных графах ухудшается производительность и растёт когнитивная нагрузка |

## Последствия

**Положительные последствия:**
- UX Delight становится инженерным контрактом, а не субъективным пожеланием.
- Product/UX/Frontend/QA работают по единому P0/P1/P2 backlog и gate-критериям.
- Уменьшается вариативность поведения UI между модулями (дерево, граф, редактор, поиск, diff).

**Отрицательные последствия:**
- Нужны дополнительные runtime-метрики и e2e-проверки для интеракций.
- Выше стоимость изменений в UI: фича должна проходить через общие слои (latency/optimistic/command/safety).
- Возможны конфликты между визуальной выразительностью и performance budget.

**Меры снижения рисков:**
- Ввести общий `delight telemetry dashboard` (p95 input latency, spinner-after-200ms rate, optimistic rollback rate, command usage).
- Закрепить дизайн-токены и motion-профили в shared UI layer с regression-тестами.
- Для P2-анимаций применять feature flags и progressive rollout с мониторингом FPS и error rate.
