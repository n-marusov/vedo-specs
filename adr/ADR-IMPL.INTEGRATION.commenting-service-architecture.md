# ADR-IMPL.INTEGRATION.commenting-service-architecture

**Дата:** 2026-05-18  
**Статус:** Принято

## Предшественник
- `ADR-IMPL.STACK.collaboration-go-strategy` (удалён)

## Контекст

В исходной архитектуре предполагался Collaboration Service, отвечающий за:
- WebSocket-хаб для real-time коллаборации
- Pessimistic locks (блокировки узлов) для предотвращения конфликтов
- Presence (отображение онлайн-пользователей)
- Комментарии к сущностям онтологии

После применения Git-подобной модели версионирования (ветки, коммиты, слияния) блокировки узлов стали не нужны — параллельная работа возможна через ветки без синхронных блокировок. Presence признан не критичным для MVP и отложен на post-MVP.

Единственная real-time функция, востребованная уже на MVP — **комментарии к сущностям онтологии** в формате онлайн-чата. Комментарии не влияют на версионирование, не сохраняются в коммитах и должны доставляться подписанным клиентам через WebSocket.

- [collaboration.md](requirements/REQ-FUN.INTEGRATION.collaboration.md)
- [backend-service-stack.md](requirements/REQ-CON.STACK.backend-service-stack.md)

## Решение

Создать **Commenting Service** как отдельный микросервис вместо Collaboration Service.

### 1. Технологический стек

| Компонент | Выбор | Обоснование |
|-----------|-------|-------------|
| Язык | Go | Эффективная работа с тысячами WebSocket-соединений через горутины |
| WebSocket | `gorilla/websocket` | Стандартная библиотека Go для WebSocket |
| Хранение | PostgreSQL | Отдельная БД (или отдельная схема в общей Support DB) |
| Брокер (масштабирование) | Redis Pub/Sub | Для рассылки сообщений между репликами (опционально — sticky sessions для MVP) |

### 2. Функции, входящие в Commenting Service (MVP)

- Создание комментария к любой сущности: онтологии, классу, свойству, индивиду, коммиту, Merge Request'у
- Ответы на комментарии (вложенные нити)
- Редактирование и удаление своих комментариев
- Упоминания пользователей (`@username`)
- WebSocket-доставка новых комментариев всем подписанным клиентам
- Подписка на комментарии к конкретной сущности (при открытии страницы)
- REST API для CRUD-операций (проксируется через API Gateway)
- WebSocket endpoint: `wss://<host>/ws/comments`

### 3. Функции, исключённые из Commenting Service (не нужны)

- Блокировки узлов (pessimistic locks) — не требуются при Git-подобной модели веток
- Presence (онлайн-статусы) — отложено на post-MVP
- Real-time редактирование онтологии — не поддерживается, изменения через коммиты
- WebSocket-трансляция изменений онтологии — не поддерживается

### 4. Хранение данных

| Данные | Хранилище | Схема |
|--------|-----------|-------|
| Комментарии, нити, метаданные | PostgreSQL | Отдельная БД `commenting` |
| Привязка к сущностям | Поля `entity_type VARCHAR` + `entity_id UUID` | Без внешних ключей (foreign keys) к другим сервисам |
| Информация о пользователях | Кэш (ID, username) | Периодическая синхронизация с Auth Service |

Слабая связанность (no foreign keys на другие сервисы) обеспечивает независимость Commenting Service — изменение схемы онтологии или версионирования не требует миграции комментариев.

### 5. Масштабирование

- **MVP:** sticky sessions — WebSocket-соединение привязано к конкретной реплике.
- **Post-MVP:** Redis Pub/Sub для рассылки сообщений между репликами при горизонтальном масштабировании.

## API

**REST (через API Gateway):**

```
POST   /api/v1/comments              — создать комментарий
GET    /api/v1/comments?entity_type=X&entity_id=Y — получить комментарии сущности
PUT    /api/v1/comments/:id          — редактировать свой комментарий
DELETE /api/v1/comments/:id          — удалить свой комментарий
```

**WebSocket:**

```
wss://<host>/ws/comments
```

Первое сообщение после установки соединения — аутентификация:
```json
{"type": "auth", "token": "<JWT>"}
```

Далее:
```json
{"type": "subscribe", "entity_type": "class", "entity_id": "<UUID>"}
{"type": "comment", "entity_type": "class", "entity_id": "<UUID>", "content": "Текст", "parent_id": "<UUID|null>"}
```

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| **A: Оставить Collaboration Service, вырезав locks и presence** | Сервис остаётся переусложнённым и несёт технический долг: код блокировок и присутствия уже спроектирован, но не нужен. Проще создать новый сервис с нулевым техническим долгом. |
| **B: Добавить комментарии в API Gateway** | API Gateway оптимизирован для HTTP-запросов (request-response), а не для тысяч долгоживущих WebSocket-соединений. Смешение ответственности усложняет масштабирование и тестирование. |
| **C: Использовать внешний сервис (Disqus, Talkyard)** | Данные уходят на сторонний сервер — неприемлемо для on-premise и Enterprise-клиентов. Невозможна привязка к сущностям онтологии (классы, свойства, коммиты). Нет контроля над схемой данных. |
| **D: Хранить комментарии в Versioning Service вместе с коммитами** | Комментарии не являются частью версионирования. Их хранение в Version Store загрязняет модель данных и усложняет миграции. |

## Последствия

**Положительные последствия:**
- Commenting Service имеет одну ответственность — это упрощает разработку, тестирование и поддержку.
- Независимое масштабирование: WebSocket-соединения не влияют на вычислительные сервисы (Ontology, Versioning).
- Go обеспечивает эффективную работу с тысячами WebSocket-соединений через горутины.
- Слабая связанность (entity_type + entity_id без foreign keys) позволяет изменять другие сервисы без миграции комментариев.
- Redis Pub/Sub даёт путь к горизонтальному масштабированию без перепроектирования.

**Отрицательные последствия:**
- Добавляется ещё один микросервис — операционная сложность (развёртывание, мониторинг, резервное копирование).
- Необходима синхронизация данных о пользователях (для валидации @mentions).
- Sticky sessions усложняют балансировку на этапе MVP (если Redis Pub/Sub не внедрён сразу).

**Меры снижения рисков:**
- Использовать Redis Pub/Sub для рассылки сообщений между репликами (можно внедрить с первого дня, sticky sessions — fallback).
- Кэшировать информацию о пользователях (ID, username) с периодической синхронизацией из Auth Service.
- Включить Commenting Service в общий конвейер CI/CD и мониторинг (Grafana, Loki, Tempo).
- Резервное копирование PostgreSQL — по общей политике VEDO Core.
