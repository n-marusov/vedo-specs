# ADR-IMPL.PROCESS.repository-layout-strategy

**Дата:** 2026-05-19
**Статус:** Принято

## Контекст

Необходимо определить стратегию размещения исходного кода сервисов (API Gateway, Ontology, Versioning, Auth, Metrics, Ticket, Publisher, Public Browse, Commenting, Frontend).

Базовая структура проекта уже указывает на единый workspace (`llm/src/`), но требовалось явное архитектурное решение: использовать монорепозиторий или разделять сервисы по отдельным репозиториям.

Ключевые вводные:
- Основной объём кода сервисов генерируется автоматически
- Нет требований по разделению прав доступа между командами/репозиториями
- Нужно быстро обеспечить согласованность версий контрактов, SDK и CI-шаблонов между сервисами

## Решение

Принять **monorepo-стратегию** для всех сервисов VEDO Core и хранить их в одном репозитории в структуре `services/`.

Основания выбора:
- Автогенерация кода эффективнее в едином репозитории: один pipeline генерации, меньше дублирования шаблонов и инфраструктуры
- При отсутствии требований к разграничению доступа multi-repo не даёт обязательной выгоды
- Monorepo сразу решает согласованность версий: изменения контрактов, сервисов и связанного tooling обновляются атомарно в одном commit/MR
- Упрощается bootstrap локальной разработки и CI/CD: единые правила lint/test/build и повторное использование pipeline templates

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Отдельный репозиторий на каждый сервис | Избыточная операционная сложность (N репозиториев, N pipeline-настроек), сложнее синхронизировать версии контрактов и генераторов |
| Гибрид: core сервисы в monorepo, edge сервисы в отдельных репозиториях | Усложняет governance и release-процесс без явной пользы при текущих требованиях |
| Полный multi-repo с централизованным registry артефактов | Добавляет инфраструктурные зависимости и задержки на публикацию/подтягивание версий, не оправдано для автогенерируемого слоя |

## Последствия

**Положительные последствия:**
- Атомарные изменения контрактов и всех затронутых сервисов в одном MR
- Стабильная согласованность версий без ручной координации между репозиториями
- Ниже стоимость сопровождения генерации и CI/CD
- Быстрый старт новых сервисов через единые шаблоны

**Отрицательные последствия:**
- Рост размера репозитория и времени некоторых CI jobs
- Нужна дисциплина по границам сервисов внутри одного репозитория

**Меры снижения рисков:**
- Path-based CI triggers и selective builds/test по изменённым директориям
- CODEOWNERS и review-правила по каталогам сервисов
- Кэширование зависимостей/сборок и инкрементальные проверки
