# ADR-IMPL.SECURITY.parser-query-fuzz-gates-mandate

**Дата:** 2026-05-17
**Статус:** Принято

## Контекст

VEDO Core принимает пользовательский ввод в четырёх критических компонентах, каждый из которых подвержен superlinear деградации (квадратичной, экспоненциальной) при определённых входных данных:

1. **Ontology Service** — парсеры Turtle, RDF/XML, JSON-LD, OWL/XML: stack overflow при глубокой рекурсии, OOM при больших литералах, экспоненциальное время при специфических конструкциях
2. **SPARQL endpoint** — SPARQL 1.1 query engine: property paths (экспоненциальный blowup), Cartesian product (OOM), nested optional + NOT EXISTS (superlinear деградация)
3. **API Gateway** — GraphQL парсер: глубокая вложенность, alias flooding, N+1 запросы
4. **Regex валидаторы** — валидация IRI, e-mail, URI: ReDoS через catastrophic backtracking

**Индустриальные инциденты:**

| Компания | Год | Уязвимость | Ущерб |
|----------|-----|------------|-------|
| **Cloudflare** | 2019 | ReDoS в HTTP/2 HPACK decoder — регулярное выражение с экспоненциальным временем | WAF отключён глобально, утечка данных через память |
| **Stack Overflow** | 2016 | Catastrophic backtracking в валидаторе markdown — регулярное выражение с вложенными квантификаторами | DoS сайта на 34 минуты, потеря дохода |
| **GitLab** | 2022 | ReDoS в валидаторе URL — ввод 20K символов вызывал задержку 30+ секунд | Замедление работы API, timeout ошибки |
| **Node.js** | 2020 | ReDoS в валидаторе HTTP заголовков — злонамеренный header приводил к CPU 100% | DoS всех Node.js серверов под нагрузкой |

**Почему существующие практики недостаточны:**

1. **Unit tests** — не ловят superlinear поведение, так как требуют специфических входных данных (глубокая вложенность, точные ReDoS-паттерны), которые разработчик не включает в обычные тесты.
2. **Code review** — superlinear деградация часто не очевидна: рекурсивный парсер выглядит корректно на обычных данных, но экспоненциально деградирует при специфическом AST.
3. **Integration tests** — используют небольшие онтологии (2-5 классов), не выявляя деградацию на 200K триплетах с глубокой вложенностью.
4. **Manual QA** — не масштабируется для тысяч вариантов malformed input.

**Почему это архитектурное решение:**

- Требует изменения CI/CD pipeline (новые stage: fuzz, performance, ReDoS)
- Вводит runtime protection механизмы во все сервисы (таймауты, лимиты, complexity limits)
- Влияет на 4 компонента (Ontology Service, SPARQL, GraphQL, Regex валидаторы)
- Меняет production поведение (новые error codes, сценарии отказа)
- Имеет архитектурные альтернативы (только runtime, только fuzzing, только monitoring)

## Решение

Внедрить трёхуровневую защиту: **шлюзы фаззинг- и нагрузочного тестирования** в CI (обнаружение регрессий до релиза), **защиту во время выполнения** в промышленной среде (ограничение ущерба) и **наблюдаемость** (выявление атак в реальном времени). Комбинация всех трёх уровней обязательна — ни один из них в отдельности не даёт достаточной защиты.

---

**Уровень 1: Шлюзы в CI**

Четыре категории профилей нагрузки (19 профилей) для тестирования:

| Категория | Профили | Описание |
|-----------|---------|----------|
| **Парсеры** | P1–P6 | Глубокая вложенность, большие литералы, много пространств имён, бланк-ноды, некорректный ввод, катастрофический перебор |
| **SPARQL** | Q1–Q6 | Глубокие пути свойств, вложенные optional + NOT EXISTS, декартово произведение, union из многих частей, ReDoS-шаблоны, ORDER BY + DISTINCT + LIMIT |
| **GraphQL** | G1–G4 | Глубокая вложенность, переполнение псевдонимами, перекрытие пакетных запросов, дорогие вычисляемые поля |
| **Регулярные выражения** | R1–R3 | ReDoS-шаблоны, длинный ввод, нормализация Unicode |

|---------|-----------|-------|-------------|

| Время ЦП | SPARQL Q1/Q2/Q5 | > +100% от базовой линии | ❌ Блокировать релиз |
| Время ЦП | SPARQL Q3/Q4/Q6 | > +20% от базовой линии | ❌ Блокировать релиз |
| Время ЦП | GraphQL | > +50% от базовой линии | ❌ Блокировать релиз |
| Задержка p95 | Все | > +100% (2×) | ⚠️ Мягкая блокировка (нужно одобрение) |
| Задержка p99 | Все | > +200% (3×) | ⚠️ Мягкая блокировка |
| Память | Все | > +100% или >2 ГБ | ❌ Блокировать релиз |
| Аварийное завершение/OOM | Все | Любое | ❌ Блокировать релиз |
| Тайм-аут ReDoS | Регулярные выражения | > 1 секунда | ❌ Блокировать релиз |

**Уровень 2: Защита во время выполнения (промышленная среда)**

### 2.3 Плавная деградация

При превышении любого лимита времени выполнения сервис возвращает структурированную ошибку и продолжает обработку других запросов.

**Принципы:**
1. **Никакой паники и аварийного завершения** — нарушение лимита не должно ронять сервис
2. **Изоляция запросов** — превышение лимита в одном запросе не влияет на другие
3. **Структурированный ответ** — ошибка возвращается в формате, понятном клиенту
4. **Логирование WARN** — каждое нарушение лимита пишется в структурированный журнал
5. **Метрики** — каждое нарушение лимита увеличивает счётчик Prometheus

**Форматы ответа:**

```
REST (JSON):
{
  "error": {
    "code": "SPARQL_TIMEOUT",
    "message": "Выполнение SPARQL-запроса превысило лимит 30с",
    "limit": 30,
    "unit": "seconds",
    "limit_type": "timeout",
    "component": "sparql-endpoint",
    "request_id": "req-abc123"
  }
}

GraphQL (расширение):
{
  "data": null,
  "errors": [{
    "message": "Глубина запроса 15 превышает лимит 10",
    "extensions": {
      "code": "GRAPHQL_DEPTH_LIMIT_EXCEEDED",
      "limit": 10,
      "actual": 15,
      "limit_type": "depth"
    }
  }]
}
```

**Поведение по типу лимита:**

| Тип лимита | Статус HTTP | Формат ответа | Поведение клиента | Влияние на сервис |
|-----------|-------------|-----------------|---------------------|-------------------|
| Тайм-аут | 503 | `{code, message, limit}` | Повторить с экспоненциальной паузой | Нет — задача `tokio` отменена |
| Размер входа | 413 | `{code, message, limit, actual}` | Уменьшить размер тела запроса | Нет — отклонение до обработки |
| Усечение результата | 200 + заголовок `Warning` | Усечённые данные + `SPARQL_RESULT_TRUNCATED` | Проверить заголовок предупреждения | Нет — запрос завершён |
| Глубина/сложность | 400 | Расширение GraphQL `{code, limit, actual}` | Упростить запрос | Нет — отклонение до выполнения |
| Память | 503 | `{code, message, limit}` | Повторить с более простым запросом | Память освобождена, выполнен возврат ресурсов |
| Рекурсия | 422 | `{code, message, limit, actual}` | Упростить входные данные | Нет — разбор прерван |

### 2.4 Реестр кодов ошибок

| Код ошибки | Статус HTTP | Расширение GraphQL | Описание | Когда возникает |
|-----------|-------------|------------------|----------|----------------|
| `SPARQL_TIMEOUT` | 503 | `{code, limit: 30}` | SPARQL-запрос превысил тайм-аут 30с | Сложный путь свойства, декартово произведение |
| `GRAPHQL_TIMEOUT` | 400 | `{code, limit: 10}` | GraphQL-запрос превысил тайм-аут 10с | Обработчик поля с внешним вызовом |
| `PARSE_TIMEOUT` | 503 | `{code, limit: 60}` | Парсинг онтологии превысил 60с | Turtle/RDF/XML с глубокой вложенностью |
| `REGEX_TIMEOUT` | 400 | `{code, limit: 1}` | Выполнение шаблона превысило 1с | ReDoS-шаблон на длинном входе |
| `REQUEST_TIMEOUT` | 503 | `{code, limit: 120}` | Полный HTTP-запрос превысил 120с | Медленный внешний обработчик поля |
| `INPUT_TOO_LARGE` | 413 | `{code, limit, actual}` | Размер входных данных превышен | Файл >100 МБ, вход для шаблона >10k |
| `SPARQL_QUERY_TOO_LONG` | 413 | `{code, limit: 10000, actual}` | SPARQL-запрос превысил 10k символов | Сгенерированный/вставленный запрос |
| `GRAPHQL_PAYLOAD_TOO_LARGE` | 413 | `{code, limit: 10000, actual}` | Тело GraphQL превысило 10k символов | Пакетный запрос с множеством операций |
| `IRI_TOO_LONG` | 400 | `{code, limit: 2048}` | IRI превышает 2048 символов | Слишком длинный IRI при импорте |
| `SPARQL_RESULT_TRUNCATED` | 200 | Заголовок Warning | Результат обрезан до 10k записей | Онтология с >10k результатов |
| `GRAPHQL_TOO_MANY_NODES` | 400 | `{code, limit: 5000}` | GraphQL-ответ превысил 5000 узлов | Переполнение псевдонимами, N+1 |
| `EXPORT_TRUNCATED` | 200 | Заголовок Warning | Выгрузка обрезана до 10 МБ | Большая онтология при выгрузке Turtle |
| `GRAPHQL_DEPTH_LIMIT_EXCEEDED` | 400 | `{code, limit: 10, actual}` | Превышена глубина GraphQL | Глубокая вложенность запроса |
| `GRAPHQL_COMPLEXITY_LIMIT_EXCEEDED` | 400 | `{code, limit: 1000, actual}` | Сложность GraphQL превышена | Дорогие вычисляемые поля |
| `SPARQL_PATH_TOO_LONG` | 400 | `{code, limit: 10, actual}` | Путь свойства >10 шагов | Экспоненциальный путь свойства |
| `PARSER_RECURSION_LIMIT` | 422 | `{code, limit: 1000}` | Глубина рекурсии превышена (1000) | Вложенные конструкции в Turtle/RDF/XML |
| `QUERY_MEMORY_LIMIT` | 503 | `{code, limit: 500}` | Память на запрос превысила 500 МБ | Декартово произведение, большой набор результатов |
| `REQUEST_CPU_LIMIT` | 503 | `{code, limit: 2}` | Время ЦП превысило 2 сек | Медленный запрос, медленный разбор |
| `PARSER_STACK_OVERFLOW` | 500 | `{code}` | Переполнение стека в парсере | Глубокая рекурсия (должна отсекаться лимитом рекурсии) |

### 2.5 Настройка лимитов

**SaaS (фиксированные лимиты):**
- Все лимиты времени выполнения заданы в коде как константы
- Изменение лимита требует заявки на слияние + релиз
- Единые лимиты для всех арендаторов

**Корпоративное локальное развёртывание (значения Helm):**

```yaml
# helm/values.yaml
runtime_limits:
  # Тайм-ауты
  sparql_timeout_seconds: 30
  graphql_timeout_seconds: 10
  parse_timeout_seconds: 60
  regex_timeout_seconds: 1
  request_timeout_seconds: 120

  # Лимиты размера входа
  max_input_size_mb: 100
  max_sparql_query_chars: 10000
  max_graphql_payload_chars: 10000
  max_regex_input_chars: 10000
  max_iri_length: 2048

  # Лимиты результата
  sparql_result_limit: 10000
  graphql_max_nodes: 5000
  export_size_limit_mb: 10

  # Лимиты сложности
  graphql_depth_limit: 10
  graphql_complexity_limit: 1000
  sparql_property_path_depth: 10
  parser_recursion_depth: 1000

  # Лимиты ресурсов
  memory_per_query_mb: 500
  cpu_per_request_seconds: 2

  # Переопределения для корпоративных арендаторов
  enterprise_overrides:
    - tenant_id: "enterprise-1"
      sparql_timeout_seconds: 120
      graphql_depth_limit: 20
      max_input_size_mb: 500
      sparql_result_limit: 100000
      memory_per_query_mb: 2000
```

**Изолированный контур (без внешней сети):**
- Лимиты читаются из локального YAML-файла при старте сервиса
- Горячая перезагрузка через SIGHUP для лимитов времени выполнения (без перезапуска)
- Аудит изменений: каждое применение переопределения логируется с `WARN`

### 2.6 Наблюдаемость (расширенная)

**Алерты (Prometheus + Alertmanager):**

| Название оповещения | Условие | Критичность | Реакция |
|-----------|-----------|----------|----------|
| `HighTimeoutRate` | `rate(runtime_limit_violations_total{code=~".*_TIMEOUT"}[5m]) > 0.01` | P2 | Проверить, не увеличила ли недавняя поставка сложность запросов |
| `HighInputSizeViolations` | `rate(runtime_limit_violations_total{limit_type="size"}[5m]) > 0.05` | P3 | Возможна неверная настройка клиента или автоматизированный инструмент |
| `ParserCrash` | `rate(runtime_limit_violations_total{code="PARSER_STACK_OVERFLOW"}[5m]) > 0` | P0 | Немедленное расследование: в парсере есть дефект |
| `MemoryNearLimit` | `memory_usage_bytes / 500_MB > 0.8` | P1 | Потребление памяти на запрос приближается к лимиту |
| `HighTruncationRate` | `rate(runtime_limit_violations_total{code="SPARQL_RESULT_TRUNCATED"}[5m]) > 0.1` | P2 | Много запросов возвращают усечённые результаты — рассмотреть увеличение лимита |
| `GraphQLDepthSpike` | `rate(runtime_limit_violations_total{code="GRAPHQL_DEPTH_LIMIT_EXCEEDED"}[5m]) > 10` | P3 | Возможна автоматизированная проверка глубины |

**Панели Grafana:**
- **Нарушения по кодам ошибок** — составная столбчатая диаграмма (последние 24 часа)
- **Нарушения по типу лимита** — круговая диаграмма (тайм-аут / размер / глубина / память)
- **Тренд доли тайм-аутов** — временной ряд с порогами P0/P1/P2
- **Потребление памяти по компонентам** — индикаторы по подам сервисов
- **Основные источники нарушений** — таблица по арендатору/узлу API/компоненту
- **Аудит переопределений лимитов** — таблица корпоративных переопределений с отметками времени

**CI интеграция:**

| Тип теста | Триггер | Блокирует MR? | Длительность |
|-----------|---------|---------------|--------------|
| Фаззинг (парсер, SPARQL, GraphQL) | Ручной (MR) + авто (тег релиза) | ❌ Нет (ручной) | 5–30 мин |
| Нагрузочные тесты (парсер, SPARQL, GraphQL) | Авто (каждый MR) | ✅ Да | 2–5 мин |
| Проверка ReDoS | Авто (каждый MR) | ✅ Да | 30 сек – 2 мин |
| Обновление базовой линии | По расписанию (еженедельно) | ❌ Нет | 10–15 мин |

## Рассмотренные альтернативы

**Альтернатива A (базовая):** Только проверка кода + модульные тесты

| Достоинства | Недостатки |
|-------------|------------|
| Нулевая стоимость внедрения | Не выявляет сверхлинейную деградацию — рекурсивный парсер выглядит корректно в модульном тесте |
| Не требует изменений в CI/CD | Проверка кода находит ReDoS примерно в 40% случаев (эмпирические данные) |
| Не замедляет разработку | Не масштабируется: тысячи вариантов некорректного ввода |

**Причина отклонения:** Существующие практики не дают измеримой гарантии, что сверхлинейная регрессия не попадёт в промышленную среду. Для рисков уровня P0 (аварийное завершение, OOM) полагаться только на интуицию разработчика неприемлемо.

**Альтернатива Б:** Только защита во время выполнения (без фаззинга в CI)

| Достоинства | Недостатки |
|-------------|------------|
| Защищает промышленную среду от 0-day | Обнаруживает проблемы постфактум — регрессия уже в релизе |
| Минимальное влияние на разработку | Не даёт метрики "какие парсеры действительно безопасны" |
| Единая точка конфигурации | Не ловит деградацию, не достигающую тайм-аута (например, +80% по времени ЦП) |

**Причина отклонения:** Защита во время выполнения ограничивает ущерб, но не предотвращает регрессии. Без шлюзов CI сверхлинейная деградация накапливается между релизами.

**Альтернатива В:** Только наблюдаемость (выявление постфактум)

| Достоинства | Недостатки |
|-------------|------------|
| Выявляет атаки в промышленной среде | Инцидент уже произошёл — данные скомпрометированы |
| Покрывает все классы конечных точек API | Не различает атаку и регрессию кода |
| Минимальная стоимость внедрения | Не подходит для P0-рисков (аварийное завершение, OOM) |

**Причина отклонения:** Наблюдаемость выявляет, но не предотвращает. Для рисков аварийного завершения/OOM требуется упреждающая защита.

**Альтернатива Г:** Полный фаззинг на каждый MR

| Достоинства | Недостатки |
|-------------|------------|
| Максимальная уверенность в безопасности | Фаззинг-тесты занимают часы — неприемлемо для CI |
| Обнаружение даже редких шаблонов | Блокирует разработку: каждый MR ждёт фаззинг |
| Полное покрытие путей выполнения кода | Избыточно для изменений вне парсеров |

**Причина отклонения:** Фаззинг-тесты выполняются часами (в зависимости от корпуса). Запуск на каждый MR делает конвейер неприемлемо медленным. Решение: фаззинг вручную (MR), автоматически (тег релиза).

**Альтернатива Д:** Внешний межсетевой экран уровня API (Cloudflare, AWS WAF)

| Достоинства | Недостатки |
|-------------|------------|
| Нулевая разработка защиты во время выполнения | Не работает для локального и изолированного развёртывания |
| Защита от ReDoS на уровне HTTP | Не защищает внутренние парсеры (Rust) за шлюзом |
| Обновляемые сигнатуры | Не контролируем пороги и коды ошибок |

**Причина отклонения:** VEDO Core обязан поддерживать локальное и изолированное развёртывание. Внешние сервисы недоступны в этих сценариях. Кроме того, WAF не защищает от деградации внутри парсеров (Rust) после авторизации.

## Последствия

**Положительные последствия:**

- Сверхлинейные регрессии обнаруживаются до релиза — не в промышленной среде
- Защита во время выполнения ограничивает ущерб от новых уязвимостей нулевого дня
- CI обеспечивает воспроизводимую базовую линию производительности для каждого компонента
- Аудит безопасности парсеров становится измеримым (метрики, пороги, история)
- Соответствие OWASP ASVS V5 (проверка, очистка, кодирование)
- Комбинированная защита (CI + защита во время выполнения + наблюдаемость) покрывает полный жизненный цикл уязвимости

**Отрицательные последствия и меры снижения:**

| Последствие | Описание | Мера снижения |
|-------------|----------|---------------|
| Конвейер CI становится медленнее | +5–30 мин (фаззинг вручную), +2–5 мин (нагрузка автоматически) | Фаззинг только вручную для MR (не блокирует). Параллельный запуск стадий |
| Разработка фаззинг-тестов | ~10–20% накладных затрат на критичные парсеры | YAML-шаблоны профилей нагрузки. Постепенное внедрение: парсер → SPARQL → GraphQL → шаблоны |
| Ложные срабатывания | Нагрузочный тест падает, но регрессии нет | Автоматический повтор (3 попытки). Пороги вместо абсолютных значений. Наблюдение за долей ложных срабатываний |
| Лимиты времени выполнения режут легитимные запросы | Онтология >10k результатов, сложный SPARQL-запрос | Лимиты настраиваются через конфигурацию (переопределения Helm для корпоративного развёртывания). Плавная деградация (200 + `SPARQL_RESULT_TRUNCATED`, а не ошибка) |
| Сложность разбора инцидента | Непонятно, это регрессия или изменение данных | Базовая линия на чистой ветке `main`. Плановое сканирование регрессий с отчётом различий |

**Карта соответствия:**

| Стандарт | Требование | Реализация |
|----------|------------|------------|
| **OWASP ASVS 5.1.1** | "Input validation must be performed on all input" | Защита во время выполнения + проверка ReDoS для всех строковых входов |
| **OWASP ASVS 5.2.3** | "Parser must handle malformed input gracefully" | Фаззинг-тесты P5 (некорректный ввод парсера) |
| **OWASP ASVS 5.3.1** | "Output encoding must prevent injection" | Лимит результата SPARQL, лимит глубины GraphQL |
| **OWASP ASVS 12.1.1** | "DoS protection must limit resource consumption" | Все механизмы защиты во время выполнения (тайм-аут, память, ЦП) |
| **SOC2 CC7.1** | "Monitoring — выявление аномальной активности" | 12 метрик Prometheus, 6 оповещений P0–P3 |
| **SOC2 CC6.1** | "Logical access controls" | Исключения для gRPC/health — только авторизованные запросы проходят |
