# ADR-IMPL.SECURITY.vedo-cli-credentials-strategy

**Дата:** 2026-05-18  
**Статус:** Принято

## Контекст

`vedo-cli` для выполнения backup/restore операций требуется доступ к S3/MinIO-compatible storage. Учётные данные (access key, secret key, endpoint) критичны для безопасности — их хранение в конфигурационных файлах или plain-text аргументах команд недопустимо.

Требуется единая стратегия получения credentials, которая работает во всех сценариях развёртывания VEDO Core:
- **SaaS / cloud** — deployment в AWS, Yandex Cloud и т.д.
- **On-premise** — корпоративный дата-центр с собственным Vault.
- **Air-gapped** — изолированный контур без доступа к внешним сервисам.
- **CI/CD** — автоматические pipeline без интерактивного ввода.

## Требование-источник

- `human/artifacts/requirements/REQ-FUN.INFRA.vedo-cli-specification.md` (REQ-VC-SECRETS-001)

## Решение

Принять цепочку разрешения credentials с приоритетом: **HashiCorp Vault → AWS Secrets Manager → переменные окружения → plain-text файл (аварийный fallback)**.

Каждый последующий источник используется, только если предыдущий не доступен (не настроен). Это обеспечивает бесшовную работу во всех сценариях: Vault для on-premise, AWS Secrets Manager для cloud, переменные окружения для CI/CD, plain-text файл для air-gapped без Vault.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| Только переменные окружения | Не подходит для on-premise с Vault: администрирование секретов рассредоточено, нет единого audit trail. |
| Только Vault | Не подходит для cloud/SaaS: лишняя инфраструктурная зависимость, усложнение развёртывания. |
| Только конфигурационный файл | Секреты в файле — высокий риск утечки через репозиторий, backup, логи. |
| Интерактивный ввод (prompt) | Неприменим для CI/CD и автоматизированных сценариев. |
| Встроенный механизм Go (embed) | Невозможно менять credentials без пересборки бинарного артефакта. |

## Последствия

**Положительные последствия:**
- Единая цепочка разрешения покрывает все сценарии развёртывания без дублирования логики.
- Приоритет Vault для on-premise обеспечивает единый audit trail доступа к секретам.
- AWS Secrets Manager — нативный механизм для cloud-деплоймента (без дополнительной инфраструктуры).
- Переменные окружения — универсальный fallback для CI/CD и dev.
- Аварийный fallback (plain-text) только для air-gapped, где Vault недоступен.

**Отрицательные последствия:**
- Поддержка трёх механизмов получения секретов увеличивает поверхность тестирования.
- Vault и AWS Secrets Manager требуют разных библиотек и механизмов аутентификации.
- В air-gapped среде без Vault администратор должен вручную управлять файлом credentials.

**Меры снижения рисков:**
- Использовать Go-библиотеки с единым интерфейсом (interface), чтобы переключение источника было прозрачным для бизнес-логики.
- Все источники credentials реализовать как имплементации общего `CredentialsProvider` интерфейса.
- Покрыть каждый источник unit-тестами и интеграционным тестом цепочки разрешения.
- Перед каждой операцией backup выполнять pre-flight check: `credential provider → storage connectivity → start backup`.

## Уточнение (Amended 2026-05-19): Vault в docker-compose

**Vault (HashiCorp Vault) НЕ входит в `docker-compose.yaml` на milestone 001 (локальная разработка).**

| Окружение | Использовать Vault? | Механизм хранения токенов / секретов |
|-----------|---------------------|--------------------------------------|
| **Локальная разработка (docker-compose)** | ❌ НЕТ | Файл `~/.vedo/config.yaml` или `VEDO_CLI_TOKEN` env |
| **CI/CD (GitLab CI)** | ✅ ДА | Vault (через `secrets:`) или GitLab CI variables |
| **Production (SaaS, post-MVP)** | ✅ ДА | Vault (отдельный кластер) |
| **On-premise Enterprise** | ⚠️ Опционально (выбор заказчика) | Vault или файл с усиленными правами (`chmod 600`) |

**Обоснование:**
- Milestone 001 ориентирован на fast onboarding: разработчик должен запустить `docker compose up` и начать писать код, а не разбираться с инициализацией Vault, unseal-процедурой и управлением корневым токеном.
- Для локальной разработки цепочка разрешения credentials сокращается до: `переменные окружения → ~/.vedo/config.yaml`. Vault и AWS Secrets Manager исключаются.
- В CI/CD Vault остаётся предпочтительным источником, но допускается fallback на masked CI variables.
- Цепочка разрешения для local dev НЕ заменяет production-цепочку. При деплое в production Vault настраивается отдельно и не входит в базовый compose-файл.
