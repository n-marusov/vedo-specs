# ADR-IMPL.STACK.antora-docs-adoption

**Дата:** 2026-05-11  
**Статус:** Принято

## Контекст

VEDO Core требует несколько классов документации: пользовательские инструкции, административные и on-premise runbooks, руководства по развертыванию в изолированном контуре, API-документацию, архитектурные справочники, ADR, release notes и LTS-документацию для корпоративных клиентов. Документация должна быть русскоязычной по умолчанию, версионируемой, собираться в CI, работать как статический сайт и быть пригодной для offline-поставки в air-gapped environments.

## Требование-источник
- [documentation-tool.md](requirements/REQ-CON.STACK.documentation-tool.md)

## Решение

Использовать Antora как основной генератор сайта документации: документация пишется на AsciiDoc (русский язык), хранится по подходу docs-as-code в `docs/antora/`, собирается в статический сайт и может поставляться без внешних зависимостей для корпоративных/on-premise и air-gapped заказчиков.

Antora обеспечивает версионирование документации по релизам, модульную структуру (пользовательская, административная, развёртывание, API), cross-references между модулями, сборку в CI и пригодность для offline-поставки — все требования корпоративной документации закрываются одним инструментом.

Исходные файлы документации организованы в четыре компонента в `docs/antora/`:
- `user-guide/` — конечные пользователи (инженеры знаний, аналитики)
- `developer-guide/` — разработчики и архитекторы
- `admin-guide/` — DevOps, администраторы, support
- `integrator-guide/` — разработчики-интеграторы

Каждый компонент содержит `antora.yml`, `modules/ROOT/nav.adoc` и AsciiDoc-страницы в `modules/ROOT/pages/`.

Включить в MVP: краткое руководство пользователя, административное руководство, API Guide, Air-Gap Deployment Guide, Backup & Restore Guide и Incident Diagnosis Guide; добавить в CI сборку Antora, link checker и spell/style lint.

## Инструкция для агента

Для автоматического обновления Antora-документации при изменении артефактов проекта используется `docs/antora/update.md`. Агент должен следовать этой инструкции: инвентаризация изменений → определение затрагиваемых компонентов → обновление AsciiDoc-страниц → проверка сборки → проверка целостности.

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| MkDocs | Прост в использовании, но Markdown слабее для больших технических документов, переиспользования фрагментов, attributes и сложных cross-references |
| Docusaurus | Хорош для developer portal, но React/MDX добавляет лишнюю frontend-зависимость и больше ориентирован на web-порталы, чем на versioned enterprise docs |
| Sphinx | Зрелый инструмент, но Python/RST менее естественны для многоязычной продуктовой документации и команды, уже использующей AsciiDoc-compatible docs подход |
| Только Markdown в репозитории | Недостаточно для версионированной документации, модульной структуры и offline-поставки статического сайта |

## Последствия

**Положительные последствия:**
- Единый docs-as-code конвейер для пользовательской, административной, развёртывания и архитектурной документации.
- Версионирование документации по релизам и LTS/on-premise версиям.
- AsciiDoc поддерживает includes, attributes, admonitions и cross-references.
- Статический сайт можно поставлять в air-gapped environments.
- CI может проверять сборку документации и broken links.

**Отрицательные последствия:**
- Команде нужно принять AsciiDoc conventions и Antora component/version structure.
- В CI появляется отдельный шаг сборки документации.
- Нужно поддерживать навигацию, playbook и структуру модулей документации.

**Меры снижения рисков:**
- Добавить минимальный Antora playbook и style guide для документации.
- Включить Antora build и link checks в CI.
- Включить spell/style lint и проверку командных snippets в documentation CI.
- Хранить user/admin/развёртывания/API документацию отдельными Antora modules, чтобы не смешивать аудитории.
