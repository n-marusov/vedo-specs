# ADR-IMPL.STACK.ticketing-language-strategy

**Дата:** 2026-05-18  
**Статус:** Принято

## Контекст

Подсистема тикетов VEDO Core включает несколько типов нагрузки:
- синхронный пользовательский контур (создание/чтение/обновление тикетов через HTTP);
- асинхронный контур телеметрии (события алертов, логи, дедупликация);
- интеграционный контур (очередь синхронизации и вебхуки внешних систем);
- контур уведомлений (email, встроенные уведомления, каналы эскалации P0/P1);
- контур классификации и нормализации текста.

Для этой подсистемы нужен стек, который даёт:
- предсказуемую задержку в API и фоновых обработчиках;
- простую эксплуатацию в Kubernetes и в on-premise средах;
- быстрый цикл доработок правил классификации;
- независимое масштабирование вычислительной части классификатора и прикладной части API.

## Решение

Принять смешанную языковую стратегию для подсистемы тикетов:
- **Go** — для API сервиса тикетов, слушателя телеметрии, синхронизатора и модуля уведомлений.
- **Python** — для классификатора (правила, нормализация, опциональное подключение модели).

Обоснование выбора:

1. **Go для прикладного и интеграционного контура**
- Высокая пропускная способность и низкие накладные расходы для HTTP/вебхуков/воркеров.
- Простой параллелизм (горутины) для обработки очередей, повторных попыток и идемпотентности.
- Единообразие со стеком существующего `Auth Service` (Go), что упрощает поддержку.
- Удобная поставка единым бинарным файлом для корпоративных установок.

2. **Python для классификатора**
- Быстрое развитие правил классификации и обработки текста.
- Широкая экосистема для анализа текстов и интеграции с моделями при необходимости.
- Возможность развивать классификацию независимо от API и синхронизации.

3. **Граница ответственности между языками**
- Go отвечает за жизненный цикл тикета, целостность состояния и интеграции.
- Python отвечает за рекомендацию категории/приоритета и дедупликационную сигнатуру.
- В случае недоступности Python-классификатора система продолжает работу по детерминированным правилам в Go (режим деградации).

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|--------------|--------------------|
| **A: Реализовать всю подсистему на Go** | Усложняется и замедляется развитие классификации текста; выше стоимость изменения правил и экспериментов с моделями. |
| **B: Реализовать всю подсистему на Python** | Хуже предсказуемость задержек и потребления ресурсов для высоконагруженного API/вебхуков/очередей; выше операционные риски для P0/P1 маршрутизации. |
| **C: Реализовать всё на Rust** | Избыточная сложность и стоимость разработки для задач интеграции и прикладной логики тикетов; более долгий цикл изменений в правилах классификации. |
| **D: Использовать только внешнюю модель без собственного классификатора** | Потеря контроля над качеством, воспроизводимостью и доступностью; риск зависимости от внешнего поставщика и тарифов. |

## Последствия

**Положительные последствия:**
- Производительный и устойчивый операционный контур тикетов на Go.
- Быстрое развитие классификации и правил на Python.
- Независимое масштабирование API и классификатора.
- Снижение риска vendor lock-in за счёт локальных правил и управляемой интеграции моделей.

**Отрицательные последствия:**
- Два стека увеличивают сложность сопровождения (сборка, наблюдаемость, компетенции команды).
- Появляется межсервисная граница между API и классификатором.

**Меры снижения рисков:**
- Контракт между Go и Python фиксировать версионированной схемой запроса/ответа.
- Ввести таймауты и аварийный режим «правила без классификатора».
- Покрыть интеграцию контрактными и нагрузочными тестами.
- Унифицировать метрики, логи и трассировку через OpenTelemetry.
