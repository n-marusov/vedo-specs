# ADR-IMPL.STACK.vedo-cli-language-strategy

**Дата:** 2026-05-18  
**Статус:** Принято

## Контекст

`vedo-cli` — единая административная CLI-утилита экосистемы VEDO Core. Ключевые требования к языку реализации:

- **Single binary** — запуск без рантайма на рабочей станции оператора, в CI/CD и air-gapped окружениях.
- **Кроссплатформенность** — Linux, macOS, Windows (администраторы онтологий могут работать с Windows).
- **Производительность** — backup/restore крупных графов (до 1M триплетов), параллельные операции (dump, upload, checksum).
- **Богатая стандартная библиотека** — HTTP-клиенты, архивирование (tar/gzip), криптография, работа с файловой системой.
- **Экосистема CLI** — фреймворки для построения команд (Cobra, Urfave/cli), автодополнение, man-страницы.
- **Единый стек** — желательно использовать язык, уже присутствующий в экосистеме VEDO Core.

Язык реализации не был зафиксирован на этапе проектирования.

## Требование-источник

- `human/artifacts/requirements/REQ-FUN.INFRA.vedo-cli-specification.md`

## Решение

Принять **Go** как язык реализации `vedo-cli`.

## Рассмотренные альтернативы

**1. Rust (используется в Ontology Service и Versioning Service)**
- + Единый стек с двумя ключевыми сервисами.
- + Максимальная производительность.
- − Компиляция под 3 ОС × 2 архитектуры = 6 бинарных сборок; кросс-компиляция требует настройки toolchain под каждую цель.
- − Стандартная библиотека Rust беднее для CLI-задач: нет встроенного HTTP-клиента (reqwest — сторонняя зависимость), нет удобного tar/gzip (flate2/tar — отдельные крейты).
- − Время компиляции: каждая сборка занимает минуты, что замедляет CI/CD для CLI (в отличие от сервисов, которые собираются реже).
- − Избыточен для I/O-bound CLI: vedo-cli в основном выполняет orchestration (вызовы API, чтение/запись потоков, запуск команд ОС), а не CPU-bound вычисления.

**2. Python (используется в Metrics Service)**
- + Быстрая разработка, богатая экосистема.
- − Требует установленного Python-рантайма (нет single binary без PyInstaller/Nuitka, которые добавляют сложность).
- − Низкая производительность для потоковой обработки больших данных (dump/restore).
- − Зависимости (aio-pika, httpx и т.д.) увеличивают размер и сложность распространения.
- − Не подходит для air-gapped распространения: нужно тащить рантайм + зависимости.

**3. TypeScript/Node.js**
- + Единый стек с фронтендом.
- − Требует Node.js рантайм или сложную упаковку (pkg, SEA).
- − Не подходит для air-gapped и embedded-сценариев.
- − Event-loop модель может блокироваться при потоковой обработке.

**4. Go (выбран)**

| Критерий | Go | Rust | Python | Node.js |
|----------|:--:|:----:|:------:|:-------:|
| Single binary | ✓ | ✓ | ✗ | ✗ |
| Кроссплатформенная компиляция | `GOOS=linux/darwin/windows GOARCH=amd64/arm64` одной командой | Требует настройки target + linkers | N/A (нужен рантайм) | N/A (нужен рантайм) |
| Стандартная библиотека для CLI | `net/http`, `archive/tar`, `compress/gzip`, `crypto/*`, `os/exec` — всё встроено | Беднее: reqwest, flate2, tar — сторонние крейты | Богатая, но без рантайма бесполезна | Богатая, но без рантайма бесполезна |
| CLI-фреймворки | Cobra, urfave/cli — стандарт индустрии | clap — хорош, но беднее экосистема | click, typer — есть | commander, yargs — есть |
| Производительность I/O | высокая (горутины для параллельных потоков) | высокая | средняя | средняя |
| Производительность CPU | средняя | высокая | низкая | низкая |
| Время компиляции | секунды | минуты | N/A | N/A |
| Уже в стеке VEDO | Auth Service | Ontology + Versioning | Metrics | Frontend |

## Последствия

**Положительные последствия:**
- Одна команда `GOOS=linux GOARCH=amd64 go build` для любой целевой платформы.
- Single binary без внешних зависимостей — идеально для air-gapped распространения.
- Стандартная библиотека Go покрывает 90% потребностей CLI (HTTP, tar/gzip, crypto, JSON, exec).
- Горутины естественны для параллельных операций (dump Neo4j + dump PostgreSQL одновременно).
- Cobra/urfave-cli — де-факто стандарт для многоуровневых CLI (как `vedo-cli backup create --full`, `vedo-cli diagnose trace`).
- Go уже используется в Auth Service — команда имеет компетенции.

**Отрицательные последствия:**
- Разные языки для CLI (Go) и сервисов (Rust, Python) — требуется поддержка нескольких toolchain.
- Библиотеки для RDF/OWL в Go беднее, чем в Java/Rust — но vedo-cli не выполняет RDF-операции напрямую (только экспорт canonical Turtle через API).
- Go-бинар крупнее (~15-20 MB) по сравнению с нативным кодом Rust (~5-10 MB) — некритично для CLI.

**Меры снижения рисков:**
- Cобрать Go-команду из существующих разработчиков Auth Service или выделить отдельного инженера.
- Использовать Go workspace, если в проекте появятся другие Go-компоненты.
- Покрыть vedo-cli интеграционными тестами в CI (запуск команд, проверка exit codes, проверка JSON-вывода).
- Хранить `go.mod` и Makefile в корне `llm/src/vedo-cli/`.
