# ADR-IMPL.STACK.version-control-rust-strategy

**Дата:** 2026-05-09
**Статус:** Принято

## Контекст

Versioning Service — compute-intensive сервис для коммитов, веток, diff, merge. Алгоритмы diff для больших онтологий требуют оптимального использования CPU и памяти.

## Требование-источник
- [backend-service-stack.md](requirements/REQ-CON.STACK.backend-service-stack.md)

## Решение

Реализовать Versioning Service на Rust с тем же async runtime, что и Ontology Service.

Rust обеспечивает быстрые diff/merge-алгоритмы с оптимальным использованием CPU и памяти без GC-пауз — прямое преимущество для compute-intensive операций версионирования; единый стек с Ontology Service даёт общий инструментарий через cargo workspace.

Разместить оба Rust-сервиса в одном cargo workspace для переиспользования кода, протоколов и toolchain.

Versioning Service отвечает за:
- Хранение и применение семантических дельт (триплетный diff)
- Управление ветками и Merge Request'ами
- Семантическое сравнение версий (Semantic Diff)
- Координацию материализованного состояния в Neo4j

Для обеспечения производительности чтения (G1) Versioning Service поддерживает механизм материализации: текущее состояние активной ветки поддерживается в Neo4j синхронно при каждом коммите. При переключении ветки состояние Neo4j перестраивается из дельт.

## Рассмотренные альтернативы

- **Go** — достаточно быстрая компиляция, но GC overhead для diff-алгоритмов
- **Java** — хорошая производительность, но высокое потребление памяти
- **Python** — медленная для CPU-bound операций diff/merge

## Последствия

- Общий инструментарий с Ontology Service (cargo workspace)
- Потенциально использовать тот же async runtime
- Кривая обучения для команды
- Быстрые diff/merge операции
