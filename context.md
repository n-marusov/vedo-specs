# Контекст проекта

## Что делает система

**VEDO** — **V**irtual **E**nvironment for **D**eveloping **O**ntologies (Виртуальная среда для разработки онтологий). *Visual Editor for Distributed Ontologies* (Визуальный редактор для распределенных онтологий).

VEDO Core — веб-платформа для многопользовательского редактирования онтологий (графов знаний) с поддержкой до 1 млн аксиом. Заменяет десктопный Protégé на облачный редактор с Git-подобным версионированием и параллельной работой через ветки.

Ключевые возможности:
- Отклик интерфейса < 1 сек (p95) при работе с крупными онтологиями; p99: < 2 сек
- Git-подобное управление версиями (коммиты, ветки, слияния, diff) через собственный Versioning Service
- Коллаборация (блокировки узлов, комментарии, уведомления) через WebSocket
- REST API для интеграции с отраслевыми решениями
- Импорт/экспорт в форматах Turtle, RDF/XML, OWL

## Пользователи

| Профиль | Роль | Что делает |
|---------|------|------------|
| **Инженер знаний** | Прямой пользователь | Создаёт классы, свойства, индивиды; фиксирует изменения; рецензирует онтологию |
| **ИТ-архитектор** | Стратегический владелец | Моделирует структуры; настраивает интеграции; экспортирует онтологии |
| **Разработчик** | API-пользователь | Интегрирует через REST API; автоматизирует импорт/экспорт |
| **Аналитик данных** | Читатель | Просматривает граф; фильтрует классы; не меняет онтологию |
| **DevOps-инженер** | Эксплуатация | Разворачивает; настраивает мониторинг; бэкапит |
| **Owner** | Владелец группы или онтологии | Управляет членством, назначает роли, передаёт владение и удаляет группу/онтологию в пределах политики |
| **Maintainer** | Ведущий инженер знаний | Управляет рабочим процессом онтологии: рецензирует Ontology Merge Request, выполняет merge в защищённую ветку, настраивает правила approval без управления членством |

## Модель организации работы

VEDO Core использует GitLab-like модель многокомандной работы:
- **Group** — контейнер для команд, департаментов и вложенных групп.
- **Project** — аналог GitLab Project: платформенная сущность-контейнер для совместной работы над одной онтологией. Базовая единица работы, доступа и независимого версионирования; один Project содержит ровно одну Ontology (1:1) и имеет собственный Git-like репозиторий.
- **Ontology** — содержимое Project: граф понятий (TBox/ABox, классы, свойства, индивиды, аксиомы). Вне Project не существует; группировка нескольких онтологий выполняется через иерархию Group, а не через упаковку в один Project.
- **Membership** наследуется по иерархии групп и проектов; если у пользователя есть несколько ролей через наследование и прямое членство, применяется максимальная роль.
- **Owner** управляет членством Project: добавляет и удаляет участников, назначает и меняет роли, передаёт владение.
- **Maintainer** не управляет членством; он отвечает за рабочий процесс Project (и его paired Ontology), protected branches и рецензирование изменений.
- Visibility работает как в GitLab (`Private`, `Internal`, `Public`) и хранится на Project. Публичный Project (и его Ontology) и публикация snapshot — разные функции.

## Бизнес-контекст

Текущие проблемы (Protégé):
- Зависания при работе с большими онтологиями (45 сек на открытие класса с 500 дочерними элементами)
- Невозможность совместной работы (файловый обмен по email)
- Потеря изменений в Git из-за нестабильной сериализации RDF/XML
- Отсутствие механизма рецензирования

Целевая аудитория: команды в нефтегазовой, фармацевтической, финансовой отраслях.

## Технологический стек (утверждён)

### Frontend
- **Vue 3** с Composition API, TypeScript
- **pnpm** для управления зависимостями
- **Apollo Client** для GraphQL (управление состоянием, кэширование)
- **Vite** для сборки
- **Naive UI** или PrimeVue (UI-библиотека)
- **Pencil.dev** для wireframes и дизайн-спецификаций
- **@vue-flow/core** для визуализации графов

### Backend-сервисы (микросервисы)
- **Rust**: Ontology Service, Versioning Service (производительность, отсутствие GC)
- **Go**: Collaboration Service, Auth Service (goroutines, I/O)
- **Python**: Metrics Service, Notification Service (аналитика, aio-pika)

### Слой данных
- **Neo4j** — primary Triple Store (графы)
- **PostgreSQL + JSONB** — Version Store (коммиты, ветки)
- **Redis Cluster** — кэш и блокировки
- **RabbitMQ** — message queue (опционально Kafka)

### Наблюдаемость
- **OpenTelemetry** (унифицированный сбор трейсов, метрик, логов)
- **Grafana** (Tempo, Prometheus, Loki)

### Взаимодействие API
- **gRPC** — внутренние вызовы между сервисами
- **REST (JSON)** — внешний API
- **WebSocket** — realtime коллаборация
- **GraphQL** — опционально для фронтенда

## Инфраструктура

- Контейнеризация (Docker)
- Helm-чарты для развёртывания
- Планируется Kubernetes
- Интеграция с Keycloak для аутентификации
- **OAuth Providers**: Поддержка авторизации через российские OAuth провайдеры (ЕСИА/Госуслуги, Яндекс, VK) и Google

## Целевые показатели масштаба и производительности

- До 1 млн аксиом в онтологии
- Единица масштаба для SLA, QA benchmarks, capacity planning и Enterprise licensing: Canonical Workload Profile из `human/artifacts/requirements/REQ-NFR.PERF.canonical-workload-profile.md`
- До 10 одновременных пользователей
- Отклик интерфейса < 1 сек
- Экспорт 100 000 триплетов за 10 сек
- p95 latency: 120ms, p99: 250ms
