## Назначение

Объявить абсолютный запрет прямых записей в хранилище онтологии как первоклассное архитектурное ограничение. Инвариант гарантирует, что каждое изменение состояния онтологии проходит через конвейер версионирования (branch → commit → MR → review → merge) и фиксируется в аудируемом журнале коммитов.

## Требование

**Никто не пишет напрямую в хранилище онтологии (Neo4j) — ни люди, ни AI-агенты, ни администраторы. Запрет распространяется на ABox и TBox.**

Единственный допустимый путь мутации состояния онтологии:

```
branch → commit → MR → review → merge
```

**Область действия (Scope):**

- Прямые записи в Neo4j через CRUD-эндпоинты ontology-service (классы, свойства, индивиды, аксиомы) запрещены.
- Импорт/экспорт являются операциями, порождающими коммиты, а не прямыми записями.
- Внутренние обработчики вызывают versioning-service; они никогда не пишут в хранилище напрямую.

**Инвариант для REST:**

- REST write-эндпоинты работают с branch-local снимками (`branch snapshots`), никогда с живой онтологией.
- Каждая мутация ДОЛЖНА быть залогированным коммитом с аудиторским следом (кто, что, когда, ветка).

**Инвариант для внешних AI-агентов:**

- Внешние AI-агенты подчиняются тому же инварианту; capability scopes ограничивают их действия, но не отменяют инвариант.
- AI-агенты интегрируются через платформенный API (F6), а не как внутренние акторы.

## Механизм принуждения (Enforcement)

1. **M10 (MR workflow)** — обязательный enforcement backbone: MR-жизненный цикл (iid, PUT merge, state_event, /diffs) становится единственным путём применения изменений к основной ветке.
2. **Versioning pipeline** — каждая мутация проходит через commit в ветку; merge применяет коммиты к целевому состоянию.
3. **Capability scopes** — для нечеловеческих акторов: `read`, `propose:abox`, `propose:tbox`, `mr:create`, `publish:restricted`. Запрещены: `write:direct`, `merge:self`, `publish:public` (требует человека).
4. **Code guardrails** — текущий код, нарушающий инвариант, помечается deprecation-предупреждениями до полной миграции в M10.

## Критерии приёмки

1. Не существует пути мутации состояния онтологии вне конвейера версионирования.
2. Каждая мутация фиксируется в аудируемом журнале коммитов (кто, что, когда, ветка).
3. REST write-эндпоинты работают с branch-local снимками, а не с живой онтологией.
4. Внешние AI-агенты не имеют capability scope для прямой записи (`write:direct`).
5. Нарушения инварианта в текущем коде задокументированы и помечены для миграции в M10.

## Обоснование (Rationale)

Исследовательская сессия 2026-08-01 выявила, что текущий код нарушает инвариант: ontology-service выполняет прямые CRUD-записи в Neo4j без branch/commit; versioning и CRUD разъединены (commit пишет дельту в PostgreSQL и НЕ применяет её к Neo4j; только checkout пересоздаёт состояние). Без инварианта отсутствует аудиторский след, риск повреждения данных и невозможность Git-парадигмы отката. Данное ограничение фиксирует целевое состояние до реализации M10.
