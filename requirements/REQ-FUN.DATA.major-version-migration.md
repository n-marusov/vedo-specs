## Что фиксирует артефакт

Этот артефакт закрывает вопрос M2.1: «Какой процесс миграции данных при обновлении мажорной версии?».

Для VEDO Core мажорные версии требуют формальной процедуры миграции данных. Процесс включает подготовку Migration Map, полный бэкап, тестовую миграцию в изолированной среде, проверку целостности, согласование окна, production migration, post-migration checks и rollback plan.

## Основная политика

Мажорная версия означает обратно несовместимые изменения: схема БД, формат коммитов, API endpoints. Миграция данных для major update обязательна и может включать даунтайм.

Предпочтительный подход к production migration: blue-green. In-place migration допустима как fallback, если нет второго окружения.

Максимальный даунтайм для Enterprise/SLA сценария: 2 часа в согласованном окне обслуживания.

Миграция через несколько мажорных версий напрямую не поддерживается. Если заказчик пропустил одну мажорную версию, он должен выполнять последовательное обновление: `n-2 -> n-1 -> n`.

## Ответ заказчику

«VEDO Core поддерживает миграцию данных между мажорными версиями. Процесс включает предварительное тестирование в изолированной среде, полное резервное копирование всех компонентов, согласование окна миграции, максимальный даунтайм 2 часа, документированный план отката RTO 2 часа. Blue-green при наличии второго окружения может обеспечить миграцию без даунтайма. Миграция через несколько мажорных версий, например 1.0 -> 3.0, не поддерживается; требуется последовательное обновление 1.0 -> 2.0 -> 3.0».

## Migration Environment Requirements (дополнение)

### Обязательные компоненты для миграции

| Компонент | Требование | Причина |
|-----------|------------|---------|
| **Staging-окружение** | Обязательно (см. `migration-runbook.md`) | Тест migration без риска для production |
| **Зеркало production (структура)** | Идентичные версии софта, конфигурации | Репрезентативный тест |
| **Анонимизированные данные** | Объём ≥ 10% production (или ≥ 100K триплетов) | Выявление проблем производительности |
| **Backup pre-migration** | Обязателен (full backup перед миграцией на production) | Возможность rollback |
| **Rollback plan** | Документирован и протестирован на staging | Быстрое восстановление |

### Запрещённые практики

- Миграция в production без предварительного теста на staging ❌
- Использование production-данных в staging без анонимизации ❌
- Отсутствие rollback плана ❌
- Пропуск pre-migration backup ❌

### Исключения (требуют письменного approval)

| Сценарий | Кто утверждает | Условия |
|----------|----------------|---------|
| Hotfix миграция (без staging) | CTO + Security Lead | Критический баг, production недоступен |
| Migration с данными < 10K триплетов | Tech Lead | Малый объём, низкий риск |
| Migration на пустом tenant (новый клиент) | Tech Lead | production-данных нет |
