## 1. Базовая модель совместной работы

VEDO Core использует **Git-подобную модель** для параллельной работы над онтологиями. Это означает:

- **Параллельная работа** — только через ветки (feature branches).
- **Блокировки узлов (pessimistic locks) — отсутствуют.**
- **Совместное редактирование в одной ветке в реальном времени — не поддерживается.**
- **Конфликты разрешаются асинхронно** — при слиянии (merge) веток через семантический diff.

## 2. Комментирование сущностей в реальном времени

### 2.1. Назначение

Пользователи должны иметь возможность обсуждать любые элементы онтологии (классы, свойства, индивиды, коммиты, Merge Request'ы) в **режиме, приближенном к онлайн-чату**: комментарии появляются без необходимости перезагрузки страницы, а все участники проекта видят их в реальном времени.

**Ключевое отличие от версионирования:** Комментарии **не сохраняются в коммитах**, не создают новые версии онтологии и не влияют на историю изменений. Они являются отдельным слоем данных, привязанным к сущностям.

### 2.2. Функциональные требования

| ID | Требование | Приоритет |
|----|------------|-----------|
| **C-01** | Пользователь может оставить комментарий к любой сущности: онтологии, классу, свойству (ObjectProperty / DatatypeProperty), индивиду, коммиту, Merge Request'у. | P0 |
| **C-02** | Комментарий сохраняет автора, временную метку и текст (с поддержкой Markdown: жирный шрифт, курсив, списки, ссылки, вставка кода). | P0 |
| **C-03** | Пользователь может ответить на существующий комментарий, создавая вложенную нить (thread) обсуждения. | P0 |
| **C-04** | Пользователь может редактировать **свой** комментарий в течение 15 минут после создания. После этого редактирование запрещено (остаётся только удаление или скрытие). | P1 |
| **C-05** | Пользователь может удалить **свой** комментарий. Удалённый комментарий заменяется меткой «[удалено]», но нить обсуждения сохраняется. | P1 |
| **C-06** | Все участники проекта (имеющие доступ к онтологии) видят все комментарии к сущностям этой онтологии. Ограничения доступа наследуются от прав на саму сущность. | P0 |
| **C-07** | Пользователь может упомянуть другого участника через `@username`. Упомянутый пользователь получает уведомление (email, in‑app, и при включённом WebSocket — мгновенно). | P0 |
| **C-08** | Пользователь может отметить комментарий как «разрешённый» (resolved). Это полезно для ревью: после исправления замечания Maintainer может закрыть обсуждение. | P1 |
| **C-09** | Комментарии к сущностям онтологии (классам, свойствам, индивидам) **видны во всех ветках**. Если комментарий оставлен в ветке `feature/A`, он не появится в `main` до слияния ветки. **Исключение:** коммиты и Merge Request'ы привязаны к конкретной ветке. | P0 |
| **C-10** | При слиянии ветки все комментарии, оставленные в ней к сущностям (классам, свойствам и т.д.), переносятся в целевую ветку (например, `main`) и становятся видны всем. | P1 |
| **C-11** | Пользователь может подписаться на комментарии к конкретной сущности (например, к классу). При добавлении нового комментария подписанный пользователь получает уведомление. | P2 |
| **C-12** | Пользователь может просматривать все комментарии по проекту в единой ленте (аналогично чату), отсортированные по времени, с фильтрацией по сущности, автору, статусу (разрешён/не разрешён). | P1 |

| ID | Требование | Приоритет |
|----|------------|-----------|
| **C-13** | Система предоставляет WebSocket-соединение для доставки новых комментариев в реальном времени. | P0 |

| ID | Требование | Приоритет |

## 3. Workflow совместной работы

### 3.1. Роли и ответственность

| Роль | Обязанности | Права на ветки | Права на комментарии |
|------|-------------|----------------|---------------------|
| **Viewer** | Просмотр онтологий, комментирование | Только чтение всех веток | Чтение всех комментариев, создание новых, ответы, упоминания |
| **Editor** | Создание и редактирование сущностей в своих ветках | Чтение/запись в feature-ветках, чтение `main` | Чтение всех комментариев, создание, ответы, упоминания, редактирование/удаление своих комментариев (15 минут) |
| **Maintainer** | Ревью и слияние Merge Request'ов | Чтение/запись в `main` (через Merge Request), утверждение слияний | Дополнительно: возможность разрешать (resolve) комментарии, редактировать/удалять любые комментарии (в рамках ревью) |
| **Owner** | Управление доступом и членством | Все права | Все права + возможность скрыть любой комментарий без возможности восстановления (модерация) |

### 3.2. Типовой workflow с комментариями

1. **Editor** создаёт ветку от `main` (например, `feature/update-powerplant`).
2. **Editor** вносит изменения и оставляет комментарии к классам (обсуждая логику моделирования).
3. **Editor** создаёт Merge Request (MR) в `main`.
4. **Maintainer** ревьюит изменения через семантический diff и оставляет комментарии прямо в MR (с привязкой к конкретным строкам diff).
5. **Editor** отвечает на комментарии, при необходимости исправляет код и пушит новые коммиты.
6. При конфликте с `main` — **Editor** разрешает конфликт в своей ветке.
7. **Maintainer** утверждает MR и выполняет слияние.
8. Комментарии из ветки, привязанные к сущностям (классам, свойствам), переносятся в `main` (вместе с изменениями). Комментарии, привязанные к коммитам или к MR, остаются в историческом контексте.

### 3.3. Запрещённые операции

- Редактирование `main` напрямую (только через Merge Request).
- Принудительное слияние без ревью (protected branch).
- Редактирование комментария другого пользователя (кроме Maintainer в рамках модерации).
- Удаление нити обсуждения без явного подтверждения (каскадное удаление корневого комментария удаляет все ответы с предупреждением).

## 4. Уведомления

### 4.1. Типы уведомлений

| Событие | Каналы | Получатели |
|---------|--------|-------------|
| Создание Merge Request | Email, WebSocket (опционально), In‑app | Maintainer'ы |
| Новый комментарий к сущности | Email, WebSocket (если активен), In‑app | Все участники, подписанные на сущность |
| @mentions | Email, WebSocket (обязательно), In‑app, (SMS/Push — опционально для Enterprise) | Упомянутый пользователь |
| Ответ на комментарий | Email, WebSocket, In‑app | Автор исходного комментария |
| Слияние MR | WebSocket, In‑app, Email (опционально) | Автор MR |
| Отклонение MR | WebSocket, In‑app, Email (опционально) | Автор MR |
| Разрешение (resolve) комментария | WebSocket, In‑app | Автор комментария |

### 4.2. Подписки

| ID | Требование | Приоритет |
|----|------------|-----------|
| **C-21** | Пользователь может подписаться на получение уведомлений о новых комментариях к конкретной сущности (онтологии, классу, свойству, индивиду, коммиту, MR). | P1 |
| **C-22** | Пользователь автоматически подписывается на сущность, если он: создал её, упомянут в комментарии к ней, является автором MR или комментария. | P1 |

## 5. Управление конфликтами

### 5.1. Типы конфликтов (при слиянии веток)

| Тип конфликта | Пример | Способ разрешения |
|---------------|--------|---------------------|
| **Структурный** | Класс переименован в одной ветке, удалён в другой | Выбор варианта (ours/theirs) или ручное объединение |
| **Атрибутивный** | У одного и того же свойства изменён domain | Семантический diff с предложением объединить |
| **Ссылочный** | Индивид, на который ссылаются, удалён | Предупреждение, предложение создать или перелинковать |

### 5.2. Алгоритм разрешения конфликтов

1. Система вычисляет дельту между версиями на уровне триплетов.
2. Конфликтующие изменения подсвечиваются в UI.
3. Пользователю предлагаются варианты:
   - **Принять моё** (сохранить изменения из текущей ветки)
   - **Принять их** (взять изменения из целевой ветки)
   - **Объединить вручную** (редактирование спорных триплетов)
4. После разрешения всех конфликтов создаётся коммит слияния.

### 5.3. Требования к семантическому diff

- Diff должен показывать изменения в терминах онтологии, а не в структуре сериализации.
- Подсветка: добавленные сущности (зелёный), удалённые (красный), изменённые (жёлтый).
- Для изменённых сущностей показывать: какие атрибуты/связи изменились и значения до/после.

## 6. Комментарии и обсуждения (дополнительные требования)

### 6.1. Уровни видимости комментариев

| Уровень | Кто видит | Где используется |
|---------|-----------|-------------------|
| **public** | Все пользователи с доступом к онтологии | Общие замечания |
| **team** | Участники проекта/онтологии | Внутрикомандное обсуждение |
| **reviewers_only** | Только Maintainer'ы | Замечания к Merge Request |
| **private** | Только автор | Черновики, личные заметки |

### 6.2. Привязка комментариев

Комментарии могут быть привязаны к:
- Коммиту (обсуждение конкретного изменения)
- Merge Request'у (обсуждение всего набора изменений)
- Классу, свойству или индивиду (обсуждение сущности)

### 6.3. Отслеживание прочтения (опционально)

- Каждый комментарий может иметь статус прочтения для каждого участника (не обязательно для MVP).
- `@mentions` создают уведомления и помечают комментарий как требующий внимания.

### 7.2. Метрики качества совместной работы

Метрики **«95% правок без конфликтов»** и **«ложных конфликтов = 0»** измеряются по правилу, описанному в `human/artifacts/requirements/REQ-FUN.INTEGRATION.collaboration-quality-metrics.md`.

**Краткая спецификация:**

| Параметр | Значение |
|----------|----------|
| Период измерения | 30 дней или не менее 10 000 операций редактирования |
| Workload | Canonical Workload Profile (1M axioms / 100k individuals) |
| Количество параллельных редакторов | 5 (в разных ветках) |
| Цель по отсутствию конфликтов | ≥ 95% операций не требуют ручного разрешения конфликта |
| Цель по ложным конфликтам | 0% (система не должна маркировать как конфликт семантически совместимые изменения) |
| CI gate | `false-conflict-test` с k6 workload и анализом collaboration logs |

## 8. Ограничения и исключения

| № | Ограничение | Причина |
|---|-------------|---------|
| 1 | **Нет блокировок узлов** | Параллельная работа только через ветки (Git-подобная модель) |
| 2 | **Нет real-time presence** | Система не показывает, кто сейчас просматривает/редактирует онтологию |
| 3 | **Нет автоматического слияния при конфликтах** | Требуется ручное разрешение через UI семантического diff |
| 4 | **Комментарии не сохраняются в коммитах** | Комментарии — отдельный слой данных, не влияющий на версионирование |
| 5 | **Нет голосований в MR** | Только утверждение/отклонение Maintainer'ом |
| 6 | **Нет реакции на комментарии (лайки, эмодзи)** | В MVP не поддерживается (может быть добавлено в post-MVP) |
