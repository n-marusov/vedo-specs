## Назначение

Определить требования к функциональности создания проекта в рамках группы организации. Проект является контейнером для онтологии (1:1 Project ↔ Ontology) и основным объектом разграничения доступа.

## Требования

### 1. Каноническое поле name

1.1. При создании проекта каноническим полем для имени является `name`.
1.2. Поле `label` может временно приниматься как fallback для обратной совместимости, но не должно использоваться в новых реализациях.
1.3. В API Gateway поле `name` имеет приоритет; если `name` пуст, используется `label` с логированием предупреждения.

### 2. Обязательность group_id

2.1. Проект создаётся внутри группы (поле `group_id` обязательно).
2.2. `group_id` должен ссылаться на существующий ScopeNode типа `group`.
2.3. Если `group_id` не указан или указывает на несуществующую группу, система возвращает ошибку.

### 3. Интерфейс создания

3.1. Создание проекта выполняется через отдельную страницу (page), а не через диалог (dialog).
3.2. Страница создания проекта доступна по пути `/dashboard/projects/new`.
3.3. Страница содержит:
    - Селектор группы с человеко-читаемыми названиями (не ID)
    - Поле ввода названия проекта
    - Превью URL/slug проекта (авто-генерация из названия)
    - Поле описания (опционально)
    - Выбор уровня видимости (Private / Internal / Public)

### 4. Выбор группы

4.1. Селектор группы загружает список доступных групп через `listGroups()`.
4.2. Группы отображаются человеко-читаемыми названиями, не UUID.
4.3. Выбор группы обязателен — без выбранной группы форма не отправляется.

### 5. Видимость

5.1. Visibility выбирается при создании проекта.
5.2. Значение по умолчанию — `Private`.
5.3. Visibility сохраняется на Project scope; paired Ontology наследует её через 1:1-связь.
5.4. Проект не может быть более публичным, чем родительская группа (enforcement на backend).
5.5. Если visibility не указан явно, наследуется от родительской группы.

### 6. Процесс создания на backend

6.1. auth-service атомарно создаёт:
    - ScopeNode типа `project` с `parent_id = group_id`
    - Paired Ontology с UUID v4 (`ontology_id`)
    - Owner membership для инициатора
    - Audit event `project.created`
6.2. При ошибке создания Ontology выполняется компенсирующая очистка (удаление ScopeNode).
6.3. Валидируется роль пользователя в родительской группе (требуется Maintainer или Owner).

### 7. Обратная связь (Toast)

7.1. После успешного создания показывается Toast-уведомление об успехе.
7.2. При ошибке показывается Toast-уведомление об ошибке с описанием причины.
7.3. Выполняется redirect в `/project/:id/workspace` после успешного создания.

### 8. API-контракт

8.1. `POST /api/v1/projects` принимает: `name` (string, required), `description` (string, optional), `group_id` (UUID, required), `visibility` (string, optional).
8.2. Ответ `201 Created` содержит: `id`, `name`, `type`, `parent_id`, `visibility`, `ontology_id`.

## Критерии приёмки

1. `New project` на ProjectsPage открывает `/dashboard/projects/new`, а не диалог.
2. Селектор группы показывает человеко-читаемые названия, не ID.
3. Frontend отправляет canonical JSON: `name`, `description`, `group_id`, `visibility`.
4. API Gateway принимает `name`; `label` только как deprecated fallback.
5. Backend создаёт проект под группой с paired Ontology UUID v4.
6. Visibility сохраняется на проекте и не может превышать видимость родительской группы.
7. Пользователь становится Owner созданного проекта.
8. После успеха показывается Toast и redirect на `/project/:id/workspace`.
9. Проект отображается в списке с человеко-читаемым `name`.
