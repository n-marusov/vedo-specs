# Время генерации NL→OWL для онтологии из 10 классов

| Атрибут | Значение |
|---------|----------|
| **ID** | REQ-NFR.AI.generation-latency |
| **Уровень** | NFR |
| **Атрибут качества** | Performance |
| **Приоритет** | P0 |
| **Статус** | ЧЕРНОВИК |
| **Источник** | Уточнение стейкхолдера по вопросу 1.2 матрицы качества M2 |

---

## Назначение

Определить допустимые значения времени генерации NL→OWL онтологии для интерактивного использования.

## Требование

Время генерации NL→OWL онтологии из 10 классов должно быть приемлемым для интерактивного использования.

**Метрика:** Время от отправки NL-описания до отображения предпросмотра (включая LLM-вызов, валидацию, рендеринг).

**Пороговые значения (многомерное распределение latency):**

| Окружение | p50 | p95 | p99 |
|-----------|-----|-----|-----|
| **SaaS (внешний LLM)** | ≤ 10 сек | ≤ 20 сек | ≤ 30 сек |
| **On-premise (локальная LLM)** | ≤ 20 сек | ≤ 40 сек | ≤ 60 сек |

Разница в пороговых значениях обусловлена тем, что локальные LLM могут иметь меньшую вычислительную мощность и более высокую latency, чем облачные провайдеры.

**Метод верификации:**

1. Автоматическое измерение времени в тестовом окружении (CI/CD).
2. Мониторинг в production через OpenTelemetry (span `nl_to_owl.generation`).

## Критерии приёмки

1. Метрики времени генерации собираются в production через OpenTelemetry.
2. Алерт срабатывает при p95 > порогового значения в течение 5-минутного окна.
3. В UI отображается прогресс-бар с этапами генерации (см. `REQ-USR.AI.generation-progress`).
4. При превышении тайм-аута (p99 × 2) система возвращает ошибку с предложением упростить описание.
5. Пороговые значения конфигурируются для on-premise через переменные окружения.
