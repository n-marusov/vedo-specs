## Потери по типам данных

| Тип данных | Потеря при rollback через 1 час | Потеря при rollback через 1 день |
|------------|----------------------------------|-----------------------------------|
| TBox, схема | Новая схема откатится к старой | Полная потеря без миграции |
| ABox, новые индивиды | Потеря всех изменений за час | Массовая потеря |
| ABox, измененные индивиды | Потеря всех изменений за час | Массовая потеря |
| Коммиты, Git-история | Потеря коммитов за час | Массовая потеря |
| Метаданные версионирования | Потеря за час | Массовая потеря |
| LFS-объекты | Не теряются, хранятся отдельно | Не теряются, хранятся отдельно |

## RPO при rollback

Если окно между upgrade и rollback меньше 1 часа, потеря данных не превышает 1 часа работы пользователей.

Если окно больше 4 часов, rollback практически невозможен без консультации с заказчиком.

## Итоговая таблица возможностей

| Сценарий | Rollback возможен? | Макс. потеря данных | Необходимые условия | RTO |
|----------|--------------------|---------------------|---------------------|-----|
| Rollback до 1 часа после обновления | Да | 0-60 минут работы | Полный backup перед обновлением | 30-60 минут |
| Rollback через 2-4 часа | Возможен, но сложно | 2-4 часа работы | Детальный лог изменений, консультация с заказчиком | 2-3 часа |
| Rollback более чем через 24 часа | Нет, кроме отдельных классов | Месяцы работы | Нет | Нет |
| Частичный rollback коммита данных | Да, на уровне Git-like версионирования | Только изменения после коммита | Данные в Version Store | 10-30 минут |
| Rollback кода без изменения схемы БД | Да | Нет | Минорная версия, схема БД не менялась | 5 минут |
