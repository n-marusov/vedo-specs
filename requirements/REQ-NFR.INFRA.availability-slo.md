## Контекст

SLO доступности — целевой уровень доступности системы, выраженный в процентах времени, когда система была полностью функциональна, не считая плановых простоев.

Формула расчёта:

```text
Availability = (Uptime - Downtime) / Uptime * 100%
```

## Решение

Основной SLO доступности для MVP SaaS: 99.9%.

Enterprise production SLO: 99.95%.

Premium Enterprise SLO: 99.99% только по отдельному согласованию и при отдельной архитектуре высокой доступности.

Внутренний quarterly objective команды VEDO: 99.95%.

## Целевые уровни

| Этап | SLO | Допустимый простой в месяц | Допустимый простой в год | Контекст |
|------|-----|----------------------------|--------------------------|----------|
| MVP SaaS | 99.9% | ~43 минуты | ~8.8 часов | Базовый уровень для старта, малого бизнеса и не критичных проектов |
| Enterprise production | 99.95% | ~22 минуты | ~4.4 часа | Высокая доступность для крупных корпораций |
| Quarterly Objective | 99.95% | ~22 минуты | ~4.4 часа | Внутренняя цель команды VEDO |
| Premium Enterprise | 99.99% | ~4.3 минуты | ~52 минуты | Критичные системы; требует multi-AZ / active-active / multi-region архитектуры |

## Почему 99.9% достаточно для MVP

| Причина | Пояснение |
|---------|-----------|
| MVP не требует пяти девяток | На ранних стадиях важнее функциональность и скорость изменений, чем 99.99% uptime |
| Стоимость простоев невысока | Для малого бизнеса потеря за час простоя существенно ниже, чем для крупных Enterprise-клиентов |
| Проще архитектура | 99.9% достижимы с одним кластером и резервным копированием; 99.95% требует multi-AZ и автоматического failover |
| Реалистично для небольшой команды | 99.95% обычно требует круглосуточной дежурной службы |

## Почему 99.95% является Enterprise-целью

| Причина | Пояснение |
|---------|-----------|
| Контрактные обязательства | Крупные клиенты включают требования к availability в SLA |
| Высокая стоимость простоя | Для Enterprise час простоя может стоить миллионы рублей: потеря выручки, штрафы, простой команд |
| Ожидания рынка | Enterprise-продукт должен быть доступен 99.95%+ |

## Соответствие SLO и RTO

| SLO | RTO при полном отказе | Архитектурные требования |
|-----|----------------------|--------------------------|
| 99.9% | 4 часа | Один регион, один кластер, резервные копии |
| 99.95% | 2 часа | Multi-AZ, автоматический failover, холодный резерв |
| 99.99% | 30 минут | Active-active cluster, multi-region |

## Плановое обслуживание

Плановые простои не входят в SLO при соблюдении политики обслуживания.

Blue-green deployment не считается простоем, если переключение происходит без остановки сервиса.

Плановое обслуживание БД и миграции должны выполняться вне рабочего времени с уведомлением за 7 дней.

```yaml
maintenance_policy:
  windows:
    - "Sunday 02:00-04:00 UTC"
  notification: "7 days before"
  max_duration: "2 hours per month"
```

## Мониторинг

Метрика Prometheus:

```prometheus
probe_success{job="vedo-health"}
avg_over_time(probe_success[30d]) * 100
```

Grafana SLO dashboard должен показывать:
- Доступность за текущий месяц.
- Оставшийся error budget.
- Следующее окно обслуживания.

Пример:

```text
SLO Dashboard
- Current month availability: 99.94%
- Error budget remaining: 23 minutes
- Next maintenance window: 2025-05-12 02:00 UTC (est. 15 min)
```

## Объяснение для заказчиков

VEDO Core предоставляет следующие SLO доступности:
- SaaS standard: 99.9%, примерно 43 минуты простоя в месяц.
- Enterprise SLA по запросу: 99.95%, примерно 22 минуты простоя в месяц.
- Premium Enterprise dedicated installation: 99.99% по согласованию.

Для MVP ориентируемся на 99.9%. При Enterprise-контрактах VEDO обязуется соблюдать 99.95% при соответствующей архитектуре: multi-AZ, failover и резервирование. Метрики доступности публикуются в Grafana и передаются в отчётности заказчику.
