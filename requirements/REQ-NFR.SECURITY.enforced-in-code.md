# Enforcement границ безопасности в коде, а не в системном промпте

| Атрибут | Значение |
|---------|----------|
| **ID** | REQ-NFR.SECURITY.enforced-in-code |
| **Уровень** | NFR |
| **Атрибут качества** | Security |
| **Приоритет** | P0 |
| **Статус** | ЧЕРНОВИК |
| **Источник** | Принцип secure-by-code, не secure-by-prompt ( архитектура систем с LLM-агентами) |

---

## Назначение

Запретить полагаться на текстовые инструкции в системном промпте как на границу безопасности. LLM может проигнорировать инструкцию, забыть её из-за сжатия контекста (compaction) или потерять при multi-turn / chain-of-tools. Поэтому критические ограничения (роль, доступ к данным, выбор инструментов, типы разрешённых write-операций) обязаны быть реализованы в коде и инфраструктуре — как точечный enforcement, а не как текст в промпте.

> Контр-пример из отрасли: агент с правилом «Никогда не удаляй данные без явной просьбы» в системном промпте нарушил его и удалил прод-БД и бэкапы. Инструкция «Не делай ничего, пока я не скажу» была съедена механизмом compaction, что привело к удалению 200 писем.

## Требование

Каждое ограничение безопасности LLM-компонентов VEDO (document-extractor, NL→OWL, AI-suggestions, NL→SPARQL/CYPHER) должно быть реализовано как детерминированный кодовый контроль. Системный промпт (`REQ-NFR.SECURITY.system-prompt-hardening`) и фильтры промпт-инъекций (`REQ-NFR.SECURITY.prompt-filter-blacklist`, `prompt-structure-detection`) — дублирующие soft-слои, но не единственная и не первичная граница.

**Что обязано быть в коде/инфраструктуре, а не в промпте:**

| Граница | Кодовый enforcement |
|---|---|
| Роль LLM и список разрешённых функций | Allow-list инструментов, фиксация в коде роутера LLM-вызовов |
| Доступ к данным онтологии | RBAC policy engine + scoped credentials, см. `REQ-NFR.SECURITY.llm-tool-least-privilege` |
| Типы разрешённых write-операций | Запрет LLM применять изменения без HITL, см. `REQ-NFR.SECURITY.llm-write-human-approval` |
| Доступ к внешним системам/инструментам | Запрет на исходящие вызовы за пределы allow-list; allow-list enforcement в сетевой политике и коде, а не в промпте |
| Лимиты автономии | Bounded autonomy в коде, см. `REQ-NFR.SECURITY.llm-excessive-agency-control` |

**Запрещённые шаблоны:**
- Принятие инженерами и ревью безопасности утверждения «правило прописано в системном промпте» как достаточного контроля.
- Зависимость от промпта для единственного уровня защиты критического ресурса (бэкапов, БД, прод-конфигураций).

## Критерии приёмки

1. Каждая LLM-driven write-операция имеет кодовый enforcement (HITL, allow-list, scoped credentials) — отсутствие enforcement при наличии только текста в промпте признаётся дефектом безопасности P0.
2. Threat-модель для каждого LLM-компонента явно перечисляет кодовые enforcement-контроли, не полагающиеся на промпт.
3. CI-gate (`REQ-NFR.SECURITY.authorization-regression-gates`) блокирует изменения LLM-конфигурации при отсутствии или откате кодовых enforcement-контролей.
4. Системный промпт и фильтры промпт-инъекций в threat-модели отмечены как «дублирующий soft-слой», а не как граница.
5. В документации по безопасности зафиксировано: промпт не может быть единственным слоем защиты критических данных и операций.
