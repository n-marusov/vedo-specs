# Проверка сторонних данных на indirect prompt injection

| Атрибут | Значение |
|---------|----------|
| **ID** | REQ-NFR.SECURITY.llm-content-screening |
| **Уровень** | NFR |
| **Атрибут качества** | Security |
| **Приоритет** | P1 |
| **Статус** | ЧЕРНОВИК |
| **Источник** | Defense in Depth, слой 2 — Content Security (indirect prompt injection) |

---

## Назначение

Сторонние данные, поступающие в контекст LLM (загружаемые документы для doc-extract, текст онтологии при NL-запросах, контент из интеграций), должны проверяться на наличие скрытых инструкций — indirect prompt injection. В отличие от direct injection (статья Слой 1, обрабатывается `REQ-NFR.SECURITY.prompt-filter-blacklist` / `prompt-structure-detection`), здесь угроза приходит из неконтролируемого контента, который LLM читает как часть своей задачи.

Это **слой 2** стратегии Defense in Depth. Слой 1 — Input Security (`prompt-filter-blacklist`, `prompt-structure-detection`, `nl-query-length-limit`). Слой 3 — Action Security (`REQ-NFR.SECURITY.llm-output-screening`).

## Требование

### 1. Источник скрининга

| Источник данных | Что проверяется |
|---|---|
| Загруженные документы (PDF, DOCX, MD, JSON, XML, CSV) для doc-extract | Встроенные инструкции вида «ignore previous», «act as», JSON-внедрения, текст disguised как системные промпты; поверх существующих `doc-extract-security`-проверок (макросы, XXE, ...) |
| Контент онтологии при NL-запросе (если ТBox/ABox-фрагмент передаётся в LLM) | Текст комментариев, rdfs:label, описаний,псевдо-инструкции на естественном языке |
| Контент интеграций (collaboration, ticket-sync, document-extractor из external-источников) | Любой неконтролируемый текстовый payload, попадающий в LLM-контекст |

### 2. Привязка к хэшу и перекэширование

- Результат скрининга кэшируется и привязывается к хэшу контента (`SHA-256` от подготовленного для LLM payload). При изменении контента (даже минорном) проверка запускается заново — закэшированный «allow» не используется.
- Изменение контента онтологии → новый хэш → обязательная повторная проверка перед следующим LLM-вызовом.

### 3. Детекторы и пороги

- Используются несколько независимых моделей-классификаторов, для разных языков контента. Запрет полагаться на единую модель.
- Совпадение с паттернами из чёрного списка (`prompt-filter-blacklist`) внутри контента — отдельный сигнал (блокировка или sandbox согласно `REQ-NFR.SECURITY.sandbox-mode`).
- Порог срабатывания и действие (block / sandbox / accept с warning) конфигурируется администратором, hot-reload.

### 4. Что НЕ считается выполнением

- Проверка только входящего NL-запроса пользователя (это слой 1, не покрывает indirect injection из документов).
- Проверка одного и того же контента однократно без привязки к хэшу (между версиями контента проверка не переиспользуется).

## Критерии приёмки

1. Все источники стороннего контента (документы, онтология, интеграции) перечислены в политике скрининга; для каждого указан детектор.
2. Результат скрининга кэшируется с явной привязкой к `SHA-256(content)`; изменение контента форсирует повторную проверку (тест: модификация 1 байта → повторный скрининг).
3. В скрининге задействовано ≥ 2 независимых классификаторов; конфигурация allows выбирать разные модели для разных языков.
4. Блокировка/срабатывания логируются в audit аналогично `REQ-NFR.SECURITY.prompt-audit` (поля: `source`, `content_hash`, `detector`, `matched_pattern`, `action`).
5. Покрытие проверяется тестом из `REQ-NFR.PROCESS.prompt-injection-tests`: ≥ 5 кейсов indirect injection через документы/контент.
6. Изменение heur/порогов требует re-run regression suite в CI; gate п.5 `prompt-injection-tests` блокирует регрессию.
