# Стратегия fail-mode для внешних LLM-зависимостей

| Атрибут | Значение |
|---------|----------|
| **ID** | REQ-NFR.SECURITY.llm-dependency-fail-mode |
| **Уровень** | NFR |
| **Атрибут качества** | Reliability |
| **Приоритет** | P1 |
| **Статус** | ЧЕРНОВИК |
| **Источник** | Принцип fail closed / fail open / degrade как продуктовое решение (security + legal), не инженерное ad-hoc |

---

## Назначение

Выбор режима реакции на недоступность внешней LLM-зависимости (LLM-провайдер, классификатор, локальная модель) — это продуктовое решение, принятое совместно безопасниками и юристами, а не инженером в момент написания кода. Это требование фиксирует policy.fail_mode для каждого LLM-компонента и типа операции.

В отличие от `REQ-NFR.INFRA.fault-scenarios` (отказы Rust/Go-сервисов и баз данных) и `REQ-FUN.OPS.circuit-breaker-config` (общая конфигурация circuit breaker), данное требование специфицирует стратегию отказа для LLM-провайдеров относительно критичности операции.

## Требование

### 1. Классификация режимов

| Режим | Когда применимо | Поведение при недоступности зависимости |
|---|---|---|
| **Fail closed** | Критичные операции безопасности/комплаенса: классификатор промпт-инъекций (`REQ-NFR.SECURITY.prompt-filter-blacklist`), детектор PII/canary (`REQ-NFR.SECURITY.llm-output-screening`), проверка контента (`llm-content-screening`), policy engine для destructive-операций | Зависимость недоступна → операция блокируется; альтернатива не запускается. Риск пропустить угрозу выше риска отказа сервиса |
| **Degrade** | Некритичные enrich-функции с понятным базовым поведением: NL→Cypher с locally hosted fallback, synonyms/typofix для поиска, локальные LLM подмены при недоступности внешней | Зависимость недоступна → переход на локальную модель или упрощённый путь; функция работает, но хуже |
| **Fail open** | Декоративные/quality-only функции, падение которых пользователь не должен замечать: персональные AI-подсказки связей (показываем top-usages как fallback), personalized ranking | Зависимость недоступна → функция отключается тихо; пользователь видит базовый опыт |

### 2. Обязательная фиксация

- Каждая LLM-функция имеет explicit `policy.fail_mode` в конфигурации (`fail_closed | degrade | fail_open`), заданный не инженером ad-hoc, а зафиксированный политикой.
- Политика утверждена совместно Security Lead и юр. командой; в `ADR` отражено обоснование выбора.
- Изменение fail_mode конкретной функции с `fail_closed` на любой более лояльный режим требует переутверждения Security Lead + Legal.

### 3. Целевые значения

| Тип LLM-функции | Default `fail_mode` | Обоснование |
|---|---|---|
| Классификатор промпт-инъекций (вход) | fail_closed | Пропустить инъекцию недопустимо (см. контр-пример: агент удалил БД после обхода фильтра) |
| Output security (PII/canary) для Internal/Private | fail_closed | Утечка private-данных недопустима |
| `ApplySequence` doc-extract (write) | fail_closed по LLM-зависимости (HITL покрывает write-side см. `llm-write-human-approval`); preview недоступен → задача приостановлена |
| NL→Cypher для поиска | degrade — fallback на локальную модель или raw user query (без synonyms) | Поиск не должен быть пустым |
| AI-подсказки связей (Public онтологии) | fail_open — топ-usage вместо персонализированных | Пользователь не замечает недоступности |
| AI-подсказки связей (Internal/Private) | degrade на локальную модель (если доступна), иначе fail_open согласно `REQ-NFR.SECURITY.suggestion-privacy` | Сначала приватность, потомUX-деградация |

### 4. Что НЕ считается выполнением

- Дефолт без explicit policy (решение инженера по факту недоступности при разработке).
- Один режим для всех LLM-функций без классификации.
- Зависимость только от `REQ-FUN.OPS.circuit-breaker-config` без policy-классификации безопасности операции.

## Критерии приёмки

1. Реестр LLM-функций содержит колонку `policy.fail_mode` для каждой строки; значения — из фиксированного списка `fail_closed | degrade | fail_open`.
2. Никакая LLM-функция, классифицированная как destructive/security (см. `llm-write-human-approval`, output-screening), не имеет режим `fail_open`/`degrade` без явного подтверждения Security Lead + Legal (ADR на повторное разрешение).
3. `REQ-NFR.INFRA.fault-scenarios` обновлён строкой для failure LLM-провайдера/классификатора с указанием режима отказа согласно настоящему требованию.
4. CI-gate `REQ-NFR.SECURITY.authorization-regression-gates` блокирует merge PR, добавляющий LLM-функцию без explicit `fail_mode` в конфигурации.
5. Тест `REQ-NFR.PROCESS.preprod-release-gates` включает chaos-сценарий «недоступность классификатора промпт-инъекций → операции блокируются» (fail-closed contract).
