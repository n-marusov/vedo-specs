## Назначение

Исходящие ответы LLM (sequence операций doc-extract, сгенерированные SPARQL/CYPHER-запросы, текстовые ответы пользователю) проверяются на утечку данных и на выход за пределы разрешённых действий. Слой 3 стратегии Defense in Depth; слои 1–2 покрывают вход и контент (`prompt-filter-blacklist`, `REQ-NFR.SECURITY.llm-content-screening`).

## Требование

### 1. PII / sensitive data detection в ответе

- Ответ LLM сканируется на присутствие PII (email, телефоны, платёжные данные, секреты, ключи, идентификаторы пользователей), не релевантных для задачи.
- Срабатывание → маскирование или отбрасывание ответа с причиной в audit (см. `REQ-NFR.SECURITY.audit-masking`, `prompt-audit`).
- Для Internal/Private онтологий сканирование обязательно; для Public — по политике администратора.

### 2. Canary tokens

- В контексте онтологий/документов при передаче LLM внедряются canary-токены (уникальные маркеры, не валидные для рабочего контента, но технически неотличимые от real-данных из вида LLM).
- Ответ LLM проверяется на наличие canary: если > заданного порога canary-токенов «утечки» из исходного контекста в отражённой форме — ответ блокируется как подозрительный на дамп private-контекста.
- Канарейки внедряются в payload перед LLM-вызовом; наличие канарейки в ответе — индикатор leak.

### 3. Allow-list действий в ответе

- Sequence, возвращаемое doc-extractor, валидируется по JSON Schema (см. `REQ-FUN.API.doc-extract-sequence-schema`) — но, дополнительно, типы операций сверяются с кодовым allow-listом разрешённых CRUD-действий над онтологией (см. `REQ-NFR.SECURITY.enforced-in-code`, `REQ-NFR.SECURITY.llm-tool-least-privilege`).
- Сгенерированные SPARQL/CYPHER-запросы разбираются AST-парсером и проверяются на отсутствие prohibited-конструкций (`DELETE`, `REMOVE`, `DROP`, `CREATE INDEX`, изменения схемы без прав) — для read-only контекстов NL-запроса.
- Любой тип операции / Cypher-конструкции не из allow-list → последовательность/запрос отклоняется детерминированно кодом, до исполнительного слоя.

## Критерии приёмки

1. В тестах `REQ-NFR.PROCESS.prompt-injection-tests` ≥ 3 кейса «LLM возвращает PII исходного контекста» → блокировка/маскирование.
2. ≥ 3 кейса «LLM в ответе повторяет canary-токен» → блокировка как подозрительный leak.
3. Сгенерированный Cypher с `DELETE/DROP/...` для read-only контекста → отклонён кодом, не полагаясь на промпт.
4. Все проверки имеют audit-запись (поля: `output_action`, `detector`, `blocked_reason`, `trace_id`).
5. Конфигурация детекторов и allow-list обновляется администратором без перезапуска, hot-reload; изменения логируются.
6. CI-gate блокирует регрессию: новый элемент allow-list/query-prohibition снят без review → билд падает.
