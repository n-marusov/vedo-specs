# Принцип минимальных привилегий и изоляции инструментов для LLM-компонентов

| Атрибут | Значение |
|---------|----------|
| **ID** | REQ-NFR.SECURITY.llm-tool-least-privilege |
| **Уровень** | NFR |
| **Атрибут качества** | Security |
| **Приоритет** | P0 |
| **Статус** | ЧЕРНОВИК |
| **Источник** | Принцип least privilege + tool isolation (security in code, не в промпте) |

---

## Назначение

LLM-компоненты VEDO (document-extractor, NL→OWL, AI-suggestions, NL→SPARQL/CYPHER) не должны получать общих привилегий (общий root-token, общий сервис-аккаунт, общий доступ ко всей БД и бэкапам). Доступ — per-tool, scoped, с минимальными правами, изолированными между инструментами. Allow-list инструментов enforcement-ится в коде, а не в системном промпте.

> Контр-пример из отрасли (Pocket OS): один root-токен Railway давал полный доступ ко всей инфраструктуре (БД + бэкапы + API). Из-за отсутствия разграничения ролей один неверный шаг агента уничтожил прод-БД и бэкапы. Бэкапы лежали в той же системе с тем же токеном, к которому у агента был доступ.

## Требование

### 1. Scoped per-tool credentials

| Ресурс | Политика |
|---|---|
| БД Neo4j (онто-данные) | Отдельный scoped-токен только для операций, требуемых LLM-компонентом (read-only — для NL-запросов; scoped write через `ApplySequence` — для doc-extract) |
| Бэкапы | Бэкапы хранятся в отдельной системе с отдельными правами, к которой у LLM-компонентов и сервисов, ими оркестрирующих, нет доступа. См. `REQ-NFR.DATA.backup-storage` |
| LLM-провайдеры | Отдельные API-ключи per-провайдер, per-тип-операции; ключ не reused между suggestions и doc-extract |
| Файловое хранилище | Временный access only (doc-extract scratch storage), TTL ≤ 24 часа, см. `REQ-NFR.SECURITY.doc-extract-security` |
| Сетевые endpointы | LLM-компоненты ограничены сетевой политикой до allow-list endpointов; запрещены произвольные исходящие вызовы |

### 2. Запрет общих root-credentials

- Общий root/admin токен, дающий доступ одновременно к БД, бэкапам, конфигурациям и API, запрещён для использования каким-либо LLM-компонентом или сервисом, который инициирует LLM-вызовы.
- Бэкапы не должны быть достижимы через тот же токен, что и прод-БД.
- Бэкапы не должны быть достижимы из сервиса, который инициирует LLM-вызовы (document-extractor, ai-orchestration-service).

### 3. Allow-list инструментов — кодовый enforcement

- Список инструментов, доступных LLM-компоненту (schema генерации sequence, разрешённые операции `ApplySequence`, разрешённые типы Cypher-запросов), фиксируется в коде роутера LLM-вызовов и протобуфе контрактов, а не в системном промпте.
- Любой tool-call, не входящий в allow-list, отклоняется детерминированно кодом (не текстом инструкции LLM).
- См. `REQ-NFR.SECURITY.enforced-in-code`.

## Критерии приёмки

1. У каждого LLM-компонента в реестре секретов перечислены отдельные scoped-credentials на каждый используемый ресурс; общих root-credentials нет.
2. Сервисы, инициирующие LLM-вызовы (document-extractor, ai-orchestration-service), не имеют доступа к системе бэкапов (проверяется сетевой политикой и RBAC-аудитом).
3. Allow-list инструментов зафиксирован в коде (контракты gRPC, конфигурация роутера LLM); тест `REQ-NFR.SECURITY.authorization-regression-gates` включает негативные кейсы «LLM запросил non-allowlisted tool → отклонено кодом».
4. Threat-модель каждого LLM-компонента явно описывает blast-radius scoped-credentials и не допускает доступа к бэкапам.
5. Code review gate блокирует добавление общего root/admin-токена к LLM-компоненту.
