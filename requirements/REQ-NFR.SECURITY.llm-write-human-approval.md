# Human-in-the-loop для LLM-сгенерированных изменений данных

| Атрибут | Значение |
|---------|----------|
| **ID** | REQ-NFR.SECURITY.llm-write-human-approval |
| **Уровень** | NFR |
| **Атрибут качества** | Security |
| **Приоритет** | P0 |
| **Статус** | ЧЕРНОВИК |
| **Источник** | Принцип Human-in-the-loop для необратимых действий (security in code) |

---

## Назначение

Любая LLM-driven операция, изменяющая онтологию (применение AI-подсказок, утверждение извлечённой из документа структуры, применение LLM-сгенерированной миграции), требует явного подтверждения человеком в интерфейсе/системе, которую LLM не контролирует. Подтверждение происходит до выполнения транзакции; LLM не может сама инициировать и завершить destructive-операцию.

> Контр-пример из отрасли (домашний сервер): агент получил доступ «оптимизировать» систему — начал переписывать конфиги и удалять unit-файлы, что привело к падению сервера. Правильное решение — система-прокси перехватывает вызовы к критическим инструментам и блокирует их до подтверждения оператором в отдельной панели.

## Требование

### Cut-across принцип

Каждая LLM-driven write-операция в онтологию обязана:
1. Возвращать **preview** изменений до выполнения (decoded для пользователя без знания OWL, где возможно).
2. Требовать явного подтверждения пользователем в UI/CLI, отдельном от процесса генерации LLM.
3. Применяться атомарно в одной транзакции после подтверждения с обязательным созданием коммита (история версий — единственный источник правды).
4. Поддерживать undo/rollback для каждой операции.

LLM-компонент не получает прав напрямую исполнять destructive-операции без HITL. Это кодовый enforcement, не инструкция в промпте (см. `REQ-NFR.SECURITY.enforced-in-code`).

### Конкретные реализации (не дубликаты, а иллюстрации принципа)

| LLM-функция | Конкретное требование HITL |
|---|---|
| AI-подсказки связей | `REQ-USR.UI.suggestion-confirmation` (явное Apply / Dismiss) |
| Извлечение онтологии из документа | `REQ-FUN.API.doc-extract-flow` (preview → confirm-extraction → атомарный commit) |
| Опасные действия в UI (удаление класса, массовый импорт) | `REQ-USR.UI.dangerous-actions-recovery` (preview → confirm → execute → undo) |
| Будущие LLM-write функции | Обязаны повторить ту же структуру preview → confirm → commit; что фиксируется в данном cut-across требовании |

### Канал подтверждения

- Интерфейс подтверждения не контролируется LLM-компонентом: подтверждение приходит от пользователя через фронтенд, после чего применяется сервисом, отличным от LLM-генератора (обычно ontology-service).
- LLM-компонент только возвращает candidate-операции; исполнение инициируется отдельным вызовом подтверждения (`/confirm-*` endpoint), авторизованным пользователем.

## Критерии приёмки

1. Реестр LLM-driven write-операций в VEDO существует и каждая запись ссылается на конкретное FUN/USR-требование с HITL-шагом; LLM-функции без HITL-требования признаются дефектом безопасности P0.
2. Любая LLM-driven write-операция возвращает preview до выполнения; прямой LLM→write-flow без preview блокируется кодом.
3. Подтверждение приходит через endpoint/UI, отличный от того, который инициировал генерацию; FLOW-тест в `REQ-FUN.PROCESS.e2e-testing` покрывает «LLM сгенерировал → нет подтверждения → данные не изменены».
4. Каждое применение создаёт коммит в versioning-service; компоновка «LLM-генерация → commit» без подтверждения отсутствует.
5. Code review gate блокирует добавление LLM-driven write-endpoint, не имеющего парного confirm-endpoint с HITL.
