## Назначение

VEDO Core использует упрощённую модель организации, основанную на концепциях GitLab: `Group`, `Project`, `Members`. В VEDO Core аналогом GitLab Project является **Project**. **Ontology** — содержимое Project (граф понятий: TBox/ABox, классы, свойства, индивиды, аксиомы). Соответствие 1:1: один Project содержит ровно одну Ontology.

## Структура

### Group

Group представляет команду, отдел или департамент. Группы могут быть вложенными, как в GitLab.

Примеры:
- `Команда разработки продуктовой онтологии`
- `Департамент управления рисками`

### Project

Project — платформенная сущность-контейнер для совместной работы над одной онтологией. Project является аналогом GitLab Project.

Правила:
- Project находится внутри Group или Subgroup.
- Один Project содержит ровно одну Ontology (1:1).
- Membership, visibility и ABAC policies хранятся на Project.
- Один Project имеет один внутренний Git-like репозиторий, содержащий историю изменений его Ontology.
- Идея “Project содержит несколько онтологий” не используется — для группировки применяйте иерархию Group.

### Ontology

Ontology — содержимое Project (TBox, ABox, настройки, история изменений и рабочие правила). Вне Project не существует.

Правила:
- Ontology находится внутри Project (одна на Project).
- Одна Ontology соответствует одному внутреннему Git-like репозиторию, принадлежащему её Project.
- Идея “Project содержит несколько онтологий” не используется — для группировки применяйте иерархию Group.

## Роли

Базовые роли:
- **Viewer** — просматривает дерево классов, свойства, индивидов и граф.
- **Editor** — всё, что у Viewer, плюс создание, изменение и удаление элементов при наличии соответствующих прав.
- **Maintainer** — управляет рабочим процессом Project: protected branches, Ontology Merge Request (OMR), approval rules, merge в `main`.
- **Owner** — управляет владением и членством.

## Управление членством

Членством управляет **Owner**.

Owner может:
- добавлять пользователей в Group или Project;
- удалять пользователей из Group или Project;
- назначать роли;
- менять роли;
- передавать ownership;
- удалять Group или Project, если это разрешено политикой.

Maintainer не управляет членством. Maintainer может управлять рабочим процессом Project (и его paired Ontology), но не добавляет и не удаляет участников и не назначает роли.

## Наследование ролей

Роли наследуются по иерархии Group/Subgroup/Project.

Если пользователь получает роль несколькими путями, применяется максимальная роль, как в GitLab.

## Visibility

Visibility работает как в GitLab и хранится на Project; Ontology наследует видимость через 1:1-связь. Поддерживаются режимы:
- `Private`
- `Internal`
- `Public`

Публичный Project (и его Ontology) и публикация snapshot — разные функции.

Пример: публичный Project (и его Ontology) может использоваться как sandbox, чтобы внешние пользователи могли изучить полный интерфейс. Публикация snapshot остаётся отдельным read-only сценарием быстрого просмотра опубликованного состояния.

## Protected main и Ontology Merge Request

`main` защищена.

Editor может напрямую коммитить в `main` только там, где у него есть полноценное право `write`.

Если доступ ограничен `write_with_approval`, изменение идёт через GitLab-like workflow:
1. Система создаёт временную ветку `proposal/...`.
2. Создаётся Ontology Merge Request.
3. Maintainer получает уведомление.
4. Maintainer смотрит semantic diff и impact.
5. Maintainer комментирует, просит исправить, принимает или отклоняет.
6. При принятии ветка сливается в `main`.
7. При отклонении proposal-ветка удаляется без влияния на `main`.

## Атрибутные права

Атрибутные права могут расширять и ограничивать базовые роли.

При конфликте действует правило **most specific wins**: более специфичное правило на свойстве или классе ограничивает более общее право на уровне Project.

Атрибутные права задаются не строковыми масками, а семантическими паттернами по графу:
- по URI prefix;
- по annotation value;
- по parent class / type;
- по relationship (`rdfs:domain`, `rdfs:range`, ObjectProperty).

Интерфейс администратора должен быть визуальным конструктором политик. Система может хранить и исполнять правила как ограниченный SPARQL-like graph pattern.
