## Назначение

VEDO Core использует упрощённую модель организации, основанную на концепциях GitLab: `Group`, `Project`, `Members`. В VEDO Core аналогом GitLab Project является **Ontology**.

## Структура

### Group

Group представляет команду, отдел или департамент. Группы могут быть вложенными, как в GitLab.

Примеры:
- `Команда разработки продуктовой онтологии`
- `Департамент управления рисками`

### Ontology

Ontology — базовая единица работы, доступа и независимого версионирования. Ontology является аналогом GitLab Project.

Правила:
- Ontology находится внутри Group или Subgroup.
- Ontology содержит TBox, ABox, настройки, историю изменений и рабочие правила.
- Одна Ontology соответствует одному внутреннему Git-like репозиторию.
- Идея “Project содержит несколько онтологий” не используется.

## Роли

Базовые роли:
- **Viewer** — просматривает дерево классов, свойства, индивидов и граф.
- **Editor** — всё, что у Viewer, плюс создание, изменение и удаление элементов при наличии соответствующих прав.
- **Maintainer** — управляет рабочим процессом онтологии: protected branches, Ontology Merge Request, approval rules, merge в `main`.
- **Owner** — управляет владением и членством.

## Управление членством

Членством управляет **Owner**.

Owner может:
- добавлять пользователей в Group или Ontology;
- удалять пользователей из Group или Ontology;
- назначать роли;
- менять роли;
- передавать ownership;
- удалять Group или Ontology, если это разрешено политикой.

Maintainer не управляет членством. Maintainer может управлять рабочим процессом онтологии, но не добавляет и не удаляет участников и не назначает роли.

## Наследование ролей

Роли наследуются по иерархии Group/Subgroup/Ontology.

Если пользователь получает роль несколькими путями, применяется максимальная роль, как в GitLab.

## Visibility

Поддерживаются режимы видимости как в GitLab:
- `Private`
- `Internal`
- `Public`

Публичная Ontology и публикация snapshot — разные функции.

Пример: публичная Ontology может использоваться как sandbox, чтобы внешние пользователи могли изучить полный интерфейс. Публикация snapshot остаётся отдельным read-only сценарием быстрого просмотра опубликованного состояния.

## Protected main и Ontology Merge Request

`main` защищена.

Editor может напрямую коммитить в `main` только там, где у него есть полноценное право `write`.

Если доступ ограничен `write_with_approval`, изменение идёт через GitLab-like workflow:
1. Система создаёт временную ветку `proposal/...`.
2. Создаётся Ontology Merge Request.
3. Maintainer получает уведомление.
4. Maintainer смотрит semantic diff и impact.
5. Maintainer комментирует, просит исправить, принимает или отклоняет.
6. При принятии ветка сливается в `main`.
7. При отклонении proposal-ветка удаляется без влияния на `main`.

## Атрибутные права

Атрибутные права могут расширять и ограничивать базовые роли.

При конфликте действует правило **most specific wins**: более специфичное правило на свойстве или классе ограничивает более общее право на уровне онтологии.

Атрибутные права задаются не строковыми масками, а семантическими паттернами по графу:
- по URI prefix;
- по annotation value;
- по parent class / type;
- по relationship (`rdfs:domain`, `rdfs:range`, ObjectProperty).

Интерфейс администратора должен быть визуальным конструктором политик. Система может хранить и исполнять правила как ограниченный SPARQL-like graph pattern.
