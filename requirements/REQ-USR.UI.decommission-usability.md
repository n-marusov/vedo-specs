## Назначение

Описывает измеримые human-factor требования к сценариям вывода из эксплуатации (decommission), закрывающие лакуну `2.4 Эргономика × Утилизация` и восстанавливающие иерархию ячеек `3.4`, `4.4`, `5.4`.

Лакуна: в артефактах есть требования к форматам экспорта, secure erase, backup retention и vendor retirement, но отсутствует измеримое требование к человеческому фактору сценария вывода из эксплуатации. Администратор может иметь технические команды, но не иметь проверяемого сценария, который подтверждает, что он способен выполнить decommission без потери данных, ошибок последовательности, непонимания статусов и обращения в поддержку.

## Пользовательские роли

| Роль | Описание | Тип drill |
|------|----------|-----------|
| **DevOps VEDO** | Инженер платформы VEDO, отвечающий за pipeline и релизы | CI/CD Smoke Drill (пустой tenant), Внутренний P0/P1 Drill (канонический профиль) |
| **Администратор заказчика** | Оператор с базовой подготовкой на стороне клиента (не разработчик сервиса) | Приемочный Decommission Drill (канонический профиль — on-premise), Периодический Enterprise Drill (снимок prod) |
| **Наблюдатель (Observer)** | Инженер платформы VEDO или senior DevOps | Заполняет чек-лист, фиксирует ошибки, замеряет время; не подсказывает, не выполняет действия |
| **L2/L3 поддержка** | Разработчики сервисов, DRI | Не участвует в drill; drill считается проваленным при эскалации |

## Профили tenant для drill

В соответствии с решением о дифференцированных лимитах:

| Профиль tenant | Объём данных | Целевое время | Статус валидации | Исполнитель | Применение |
|----------------|-------------|---------------|-------------------|-------------|------------|
| **Канонический профиль** | 1M аксиом / 100K индивидов | ≤ 4 часов | Базовый, обязательный для релиза | DevOps VEDO + Администратор заказчика | Валидация P0/P1 runbook и приёмочный decommission. Закрывает `1.3`, `2.4`, `3.3`, `5.2` |
| **Пустой tenant** | 0 данных | ≤ 30 минут | Дополнительный, для CI/CD | DevOps VEDO | Быстрая проверка pipeline, CLI, скриптов после каждого коммита в main |
| **Продуктивный снимок** | Анонимизированный production snapshot | ≤ 4 часов | Рекомендованный, по запросу enterprise | Администратор заказчика | Ежегодная проверка DRP на инфраструктуре заказчика |

## Распределение ответственности за выполнение drill

| Тип drill | Исполнитель | Периодичность | Цель | Покрываемые ячейки |
|-----------|-------------|---------------|------|--------------------|
| **CI/CD Smoke Drill** (пустой tenant) | DevOps VEDO | Каждый коммит в `main` | Валидация pipeline и скриптов развёртывания | `1.1`, `5.1` |
| **Внутренний P0/P1 Drill** (канонический профиль) | DevOps VEDO | Перед каждым production-релизом | Обязательная проверка runbook (restore, migration, decommission) | `1.3`, `3.3`, `5.2` |
| **Приемочный Decommission Drill** (канонический профиль) | Администратор заказчика (on-premise) | Однократно при приёмке on-premise версии | Полный цикл decommission на оборудовании заказчика в staging | **`2.4`**, `3.4`, `5.4` |
| **Периодический Enterprise Drill** (снимок prod) | Администратор заказчика | Ежегодно (рекомендовано) | Проверка DRP на собственной инфраструктуре | `5.2` |

### Обоснование разделения

1. **Закрытие лакуны `2.4`:** требование, что администратор заказчика (а не инженер VEDO) выполняет decommission drill, гарантирует проверку real-world human-factor. Процедура вывода из эксплуатации должна быть документирована, интуитивно понятна и выполнима без поддержки вендора.
2. **Разделение внутреннего и внешнего качества:** DevOps VEDO проверяет, что система не сломана технически; администратор заказчика проверяет документацию, удобство эксплуатации и автономность (критично для on-premise и air-gapped).
3. **Реализация урока vendor shutdown:** обязательный decommission drill силами заказчика перед приёмкой (`5.4`) гарантирует, что клиент не попадёт в безвыходную ситуацию при прекращении использования продукта.

## Decommission usability drill — Приемочный Decommission Drill (DUS-1)

Система должна иметь проверяемый сценарий вывода из эксплуатации, в котором администратор заказчика с базовой подготовкой выполняет полный экспорт tenant на каноническом профиле (1M аксиом / 100K индивидов) на собственном оборудовании в staging-окружении, проверяет manifest, checksums и импортирует данные в чистый тестовый экземпляр без обращения в поддержку.

### Критерий приёмки

- Успешность выполнения: 100% для минимум 3 независимых drill-прогонов.
- Максимальное время выполнения: ≤ 4 часов для канонического профиля; ≤ 30 минут для пустого tenant (CI/CD).
- Количество критических ошибок оператора: 0.
- Количество обращений к L2/L3 поддержке: 0.

### Метод проверки

- Staging drill на каноническом профиле.
- Наблюдатель заполняет чек-лист.
- Результат сохраняется как release evidence.

### Закрывает

- `2.4 Эргономика × Утилизация`
- Усиливает `1.3 Эксплуатация/Обслуживание × Среда`
- Усиливает `3.3 Эксплуатация/Обслуживание × Функции`
- Усиливает `5.2 Эксплуатация/Обслуживание × Тех. обеспеченность ЖЦ`

## Статусы и сообщения (DUS-2)

Система должна показывать человеку однозначный статус каждого этапа вывода из эксплуатации.

### Статусная модель

| Статус | Описание | Следующее действие |
|--------|----------|-------------------|
| `not_started` | Процедура decommission не начата | Запустить `vedo-cli decommission plan --tenant <id>` |
| `exporting` | Выполняется экспорт данных | Мониторинг прогресса |
| `export_verified` | Экспорт завершён, checksum и manifest проверены | Выполнить `vedo-cli decommission --verify` |
| `restore_verified` | Импорт в тестовый экземпляр подтверждён | Подтвердить decommission или продолжить хранение |
| `pending_retention_expiry` | Данные помечены к удалению, ожидание retention policy | Отменить или дождаться автоматического удаления |
| `crypto_erased` | Данные зашифрованы и ключи уничтожены | Подтвердить завершение |
| `failed` | Ошибка выполнения этапа | Выполнить `vedo-cli decommission --retry` после устранения причины |
| `completed` | Процедура успешно завершена | Проверить release evidence |

### Критерий приёмки

- Каждый статус имеет текстовое объяснение на русском языке.
- Каждый статус имеет следующее допустимое действие.
- Статус `failed` содержит причину отказа (`reason:`) и команду безопасного повтора (`vedo-cli decommission --retry`).
- В UI/CLI нет статуса, понятного только по цвету (все статусы дублируются текстом).

### Метод проверки

- CLI snapshot test.
- UX checklist.
- Accessibility review для текстового дублирования статусов.

### Закрывает

- `2.4 Эргономика × Утилизация`
- Усиливает `4.4 Аварии/Катастрофы × Утилизация`

## Dry-run и безопасное планирование (DUS-3)

Система должна поддерживать режим предварительной проверки вывода из эксплуатации без удаления данных.

### Критерий приёмки

- Команда `vedo-cli decommission plan --tenant <id>` не изменяет состояние данных.
- Команда выводит список экспортируемых объектов, предполагаемые форматы, оценку объёма, retention constraints, backup/cold archive ограничения и требуемые права.
- Dry-run завершается с ненулевым кодом, если отсутствует хотя бы один обязательный export target или невозможно создать manifest.

### Метод проверки

- Contract test для отсутствия state mutation.
- Integration test с неполной конфигурацией export target.

### Закрывает

- `2.4 Эргономика × Утилизация`
- Усиливает `3.4 Функции × Утилизация`
- Усиливает `4.4 Аварии/Катастрофы × Утилизация`

## Offline-доступность инструкций (DUS-4)

Документация вывода из эксплуатации должна позволять администратору выполнить export, verify и restore-check без внешней помощи.

### Критерий приёмки

- Документация доступна offline (в составе air-gapped deployment package).
- Все команды copy-paste ready, кроме явно обозначенных placeholders (например, `<tenant-id>`, `<output-dir>`).
- В usability test минимум 3 администратора выполняют сценарий без обращения в поддержку.
- Не менее 95% шагов чек-листа выполняются без уточняющих вопросов наблюдателю.

### Метод проверки

- Docs usability test (staging drill с наблюдателем).
- Link checker (проверка битых ссылок в offline-документации).
- Проверка команд в безопасном staging окружении.

### Закрывает

- `2.4 Эргономика × Утилизация`
- Усиливает `5.4 Тех. обеспеченность ЖЦ × Утилизация`

## Staging-кластер для внутренних drill

Внутренний P0/P1 Drill (исполнитель — DevOps VEDO) должен проводиться в отдельном staging-кластере, полностью изолированном от production.

### Требования к staging-кластеру

| Характеристика | Требование |
|----------------|------------|
| **Инфраструктура** | Аналогична production по типам узлов, объёму дисков и сетевым политикам |
| **Версия ПО** | Строго идентична production-релизу, на котором планируются учения |
| **Данные** | Содержит предварительно развёрнутый канонический профиль нагрузки (1M аксиом / 100K индивидов) |
| **CI/CD** | Развёртывается из того же pipeline, что и production, но с собственным набором `values.yaml` |
| **Изоляция** | Полная физическая или логическая изоляция от production на уровне сети, БД и учётных данных |

### Что запрещено

- Проведение drill на production-кластере или кластере, разделяющем ресурсы с production.
- Проведение drill в окружении, версия ПО которого отличается от целевого production-релиза.

### Что проверяется

- P0 restore runbook.
- Major version migration runbook.
- Decommission export runbook.
- Инструменты: `vedo-cli restore`, `vedo-cli diagnose`, `vedo-cli migrate`.
- Человеческий фактор: DevOps VEDO выполняет процедуры по runbook в условиях, приближенных к реальным.
- Метрики: замер RTO и RPO, проверка false-positive rate алертов.

### Обоснование

Основано на недопущении класса инцидентов из кейса GitLab DB incident (2017), когда администратор по ошибке применил разрушительную команду к production БД вместо intended staging. Совмещение окружений для учений и реальной работы создаёт неприемлемый риск:

1. **Предотвращение катастрофических ошибок:** drill включает сценарии отказа, восстановления и rollback; ошибка на общем кластере ведёт к потере production-данных.
2. **Изоляция нагрузки:** P0 drill создаёт значительную нагрузку (восстановление дампов, переключение трафика), которая не должна влиять на production.
3. **Чистота эксперимента:** изолированный staging исключает искажение результатов drill фоновой production-нагрузкой.

## Окружение для приемочного Decommission Drill (администратор заказчика)

### Предпочтительный сценарий (рекомендация)

VEDO рекомендует заказчику использовать отдельный, изолированный экземпляр VEDO для приёмочных drill. Это полностью исключает риск аварийного воздействия на production-данные.

- **On-premise:** заказчик развёртывает временный экземпляр VEDO через Helm-чарт на тех же серверах, но в отдельном namespace/Kubernetes-кластере.
- **Air-gapped:** заказчик использует заранее подготовленный `air-gap package` для временного тестового экземпляра.

### Допустимый сценарий (drill на production-оборудовании)

Если отдельные ресурсы недоступны, drill на той же инфраструктуре, что и production, **допускается** при соблюдении всех условий:

| № | Условие | Описание |
|---|---------|----------|
| 1 | **Полный верифицированный backup** | `vedo-cli backup create --full` + `vedo-cli backup verify` перед drill; без успешной верификации drill не начинается |
| 2 | **Изоляция данных** | Drill выполняется только на тестовом tenant, созданном для учений; production-данные не используются |
| 3 | **Инфраструктурная изоляция** | Сценарии, влияющие на инфраструктуру (restore), — только в изолированном namespace; decommission export (read-only) может выполняться на production-инфраструктуре с явным указанием target-tenant |
| 4 | **Явное предупреждение CLI** | `vedo-cli` проверяет маркировку окружения; на production-окружении требует дополнительного подтверждения с указанием имени окружения |
| 5 | **Read-only mode для production** | На время опасных фаз drill (restore) production переводится в `read-only mode` согласно runbook |

### Обязанности VEDO Core

| Обязанность | Описание |
|-------------|----------|
| **Документация** | Пошаговый `decommission-drill-runbook.md` для обоих сценариев (отдельный кластер / production-оборудование) |
| **Инструментарий** | `vedo-cli` с поддержкой явного указания target-окружения и tenant; guardrails: `backup verify`, `environment == 'production'` |
| **Air-gap совместимость** | Полный пакет для развёртывания тестового экземпляра в изолированном контуре |

Ответственность за выбор безопасного сценария лежит на заказчике, но VEDO Core гарантирует, что инструментарий не позволит выполнить опасные действия без явного информирования о рисках. Закрывает требования ячеек `2.3` (защитные guardrails) и `5.3` (план реагирования на инциденты инфраструктуры).

## Эталонный профиль для тестового tenant

VEDO Core обязан предоставлять скрипт или инструмент для развёртывания канонического профиля в тестовом tenant. Это неотъемлемая часть поставки, обеспечивающая воспроизводимость и измеримость приёмочных испытаний.

### Обоснование

1. **Единый стандарт приёмки:** результаты RTO/RPO и успешность decommission export должны быть сопоставимы; генерация данных каждым заказчиком делает drill несопоставимым.
2. **Воспроизводимость условий:** идентичные данные позволяют команде VEDO диагностировать проблемы, зная точную структуру и размер графа.
3. **Снижение порога входа:** требование к заказчику разработать генератор профиля создаёт барьер, противоречащий цели закрытия лакуны `2.4`.

### Что входит в поставку

| Компонент | Формат | Назначение |
|-----------|--------|------------|
| **Скрипт генерации профиля** | `vedo-cli tenant seed --profile canonical` | Разворачивает в указанном tenant строго детерминированный набор данных (1M аксиом / 100K индивидов) |
| **Дамп канонического профиля (опционально)** | `.ttl.gz` / `.dump` | Для air-gapped сред; восстанавливается через `vedo-cli restore` |
| **Манифест эталонного профиля** | `canonical-profile-manifest.yaml` | Контрольные суммы, количество сущностей по типам, ожидаемое время выполнения |

### Поведение `vedo-cli tenant seed --profile canonical`

1. **Проверка окружения:** отказ, если tenant уже содержит данные (защита от перезаписи) или окружение маркировано как `production`.
2. **Создание данных:** иерархия классов (глубиной до 7 уровней), ObjectProperty и DatatypeProperty, индивиды с заполненными значениями, несколько Git-коммитов в истории версионирования.
3. **Верификация:** вывод статистики, сверка с `canonical-profile-manifest.yaml`; при несовпадении — ошибка.

## Decommission Drill Runbook

Автор и владелец runbook `decommission-drill-runbook.md` — команда VEDO Core. Runbook является неотъемлемой частью поставки продукта, а не эксплуатационной документацией заказчика.

### Модель владения

| Аспект | Владелец | Комментарий |
|--------|----------|-------------|
| **Авторство и разработка** | Команда VEDO Core | Пишут инженеры на основе архитектуры продукта и лучших практик восстановления |
| **Версионирование и поставка** | Команда VEDO Core | Входит в релиз, собирается Antora, доступен в offline-пакете для air-gapped |
| **Валидация и тестирование** | Команда VEDO Core | Проходит внутренний drill с каноническим профилем перед каждым релизом |
| **Адаптация под инфраструктуру** | Заказчик | Заказчик создаёт дочерний документ с конкретными хостами, путями, учётными данными; базовый алгоритм и меры безопасности не меняются |

### Содержание runbook

1. **Pre-flight checklist:** полный верифицированный backup, изоляция tenant, статус окружения.
2. **Сценарий для изолированного staging-кластера:** полный цикл от развёртывания канонического профиля до проверки импорта.
3. **Сценарий для production-оборудования:** инструкция с guard (`environment == 'production'`), требования к backup и read-only mode.
4. **Процедура верификации:** проверка manifest, checksums, семантической целостности данных в целевой системе.
5. **Критерии успеха:** RTO decommission export, количество ручных шагов (≤ 5), общее время (≤ 4 ч).

### Обоснование

- **Ответственность за функциональность:** документирование безопасного использования инструмента лежит на его создателях.
- **Закрытие лакуны `2.4`:** готовый протестированный runbook от вендора делает процедуру измеримо удобной и безопасной. Если бы runbook писал заказчик, vendor не мог бы гарантировать корректность.
- **Lessons learned:** GitLab, Knight Capital — полагаться на эксплуатационную документацию, созданную пользователем «на лету», недопустимо.

## Обоснование выбора канонического профиля

Канонический профиль нагрузки (1M аксиом / 100K индивидов) является базовым и обязательным для валидации всех критических (P0/P1) эксплуатационных runbook.

- **Релевантность:** Только на каноническом профиле можно проверить реальное время выполнения (RTO), целостность данных, устойчивость под нагрузкой и способность администратора без ошибок выполнить сложную многошаговую процедуру.
- **Объективная оценка:** Drill на пустом tenant не выявляет проблем производительности, таймаутов, ошибок в сложных транзакциях или неполноты данных в экспортных манифестах. Это делает проверку human-factor несостоятельной, так как оператор не сталкивается с реальной когнитивной нагрузкой.

## Two-person approval для destructive tenant операций

Следующие destructive операции требуют подтверждения двумя администраторами (через `vedo-cli --require-peer-approval`; второй администратор подтверждает через `vedo-cli approval approve <request-id>`).

| Операция | Два администратора | Порог включения |
|----------|-------------------|-----------------|
| Tenant delete | Да | Всегда (любой tenant) |
| Tenant purge (decommission --purge-data) | Да | Всегда |
| Backup delete (последняя копия) | Да | Если остаётся < 3 копий |
| Ontology delete (единственная в tenant) | Да | Tenant содержит < 5 онтологий |
| Mass ontology delete (bulk) | Да | > 10 онтологий за одну операцию |
| Restore production из backup | Нет | Одобрение Lead Engineer |

**Лимиты без двух администраторов:**
- Tenant с < 10 пользователями и < 1000 триплетов — удаляется одним администратором с MFA.
- Tenant с > 10 пользователями ИЛИ > 1000 триплетов — требует двух администраторов.

## Бизнес-правила

- CI/CD Smoke Drill (пустой tenant) выполняется DevOps VEDO после каждого коммита в `main`; валидирует pipeline, но не заменяет drill на каноническом профиле.
- Внутренний P0/P1 Drill (канонический профиль) выполняется DevOps VEDO перед каждым production-релизом; провал блокирует релиз.
- Приемочный Decommission Drill (канонический профиль, on-premise staging) выполняется администратором заказчика как условие приёмки on-premise версии; провал блокирует приёмку.
- Приемочный Decommission Drill считается проваленным при любой эскалации на L2/L3 или критической ошибке оператора.
- Периодический Enterprise Drill (снимок prod) выполняется администратором заказчика ежегодно (рекомендовано, не блокирует релиз).
- Dry-run (`vedo-cli decommission plan`) не требует прав на удаление данных и доступен read-only ролям.
- Статус `failed` всегда содержит машиночитаемый код причины (`reason:`) и команду безопасного повтора.
- Документация decommission должна собираться в offline-пакет (Antora build) и проверяться link checker.
- Результат каждого drill сохраняется как release evidence: лог команд, observer checklist, замеры времени, подпись исполнителя.

## Bulk decommission drill покрытие

### Параметры

| Параметр | Значение |
|----------|----------|
| Минимум tenant в drill | 3 tenants с каноническим профилем (1M/100K) + 1 tenant с реальными анонимизированными данными (если доступно) |
| Требуемый success rate | 100% для полного экспорта и purge; 95% для проверки целостности после восстановления |
| Допустимое влияние на соседних tenant | 0 (zero) — никакого влияния |
| Частота drill | Одновременно с restore drill (раз в 30 дней) |

### Проверки

- Экспорт всех tenants завершился без ошибок.
- Purge не затронул данные других tenants.
- Восстановление из backup в изолированной среде дало идентичные checksums.

### Failure action

При failure drill блокируется следующий production-релиз до исправления.

## CLI Usability Requirements (дополнение)

### Прогресс при decommission

`vedo-cli decommission tenant` должна отображать:

```bash
$ vedo-cli decommission tenant --id tenant-456

⚠  ВНИМАНИЕ: Это действие необратимо. Все данные tenant-456 будут удалены.

Пожалуйста, подтвердите удаление, введя название tenant: tenant-456
✅ Подтверждено.

Выполнение decommission (tenant: tenant-456):
  [✓] Шаг 1/5: Проверка прав доступа
  [✓] Шаг 2/5: Экспорт данных (2.3 MB)
  [⠙] Шаг 3/5: Создание финального бэкапа... (осталось ~5 сек)
  [ ] Шаг 4/5: Purge Neo4j
  [ ] Шаг 5/5: Удаление метаданных

✅ Decommission завершён. Теневые файлы бэкапа: /var/backup/tenant-456-20260523.tar.gz
```

### Rich feedback для административных операций

| Операция | Требования к выводу |
|----------|---------------------|
| `decommission` | Пошаговая индикация, подтверждение удаления, итоговый путь к бэкапу |
| `backup create` | Прогресс-бар (dump → upload → verify), оценка времени |
| `restore` | Прогресс-бар, проверка целостности после восстановления |
| `migrate` | Поэтапная индикация с указанием времени выполнения каждого этапа |

### Поддержка `--dry-run`

Все destructive операции должны поддерживать `--dry-run`:

```bash
$ vedo-cli decommission tenant --id tenant-456 --dry-run

⚠  DRY-RUN MODE: Никакие изменения не будут применены.

Что будет удалено:
  - Онтологии: 3 шт. (450 000 триплетов)
  - Комментарии: 1 234 шт.
  - История коммитов: 567 коммитов
  - Бэкапы: 12 шт. (45 GB)

Общий размер данных: 47 GB

Для реального удаления выполните команду без --dry-run.
```

### Graceful shutdown

При прерывании decommission через Ctrl+C:
1. Завершить текущий этап (не оставлять данные в неконсистентном состоянии).
2. Сохранить прогресс в `/var/log/vedo/decommission-tenant-456.state`.
3. Вывести сообщение: `⚠ Decommission прерван. Для возобновления используйте: vedo-cli decommission resume --state-file ...`
