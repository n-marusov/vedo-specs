# UC-org.groups.manage-group-lifecycle: Manage group lifecycle

| Атрибут | Значение |
|---------|----------|
| **ID** | UC-org.groups.manage-group-lifecycle |
| **Уровень** | P0 |
| **Актор** | Аутентифицированный пользователь с ролью Owner |
| **Источник** | US-org.groups.create |

## Описание

Пользователь управляет жизненным циклом групп: создаёт группы и подгруппы, просматривает иерархический список, настраивает видимость, приглашает участников, обновляет атрибуты и удаляет группы. Группы служат контейнерами для проектов и обеспечивают наследование прав доступа.

## Предусловия

1. Пользователь аутентифицирован в системе.
2. Пользователь имеет роль Owner (для создания/удаления групп) или Maintainer (для обновления атрибутов).
3. Для создания подгруппы: родительская группа существует.
4. Система готова к записи (PostgreSQL/B-дерево доступно).

## Основной поток

1. Пользователь открывает страницу Groups (`/dashboard/groups`).
2. Система отображает список существующих групп с иерархией (родительские + дочерние группы).
3. Пользователь нажимает «New group».
4. Система открывает диалог «Create group» с полями: name, slug (авто-генерация из name), visibility (Private/Internal/Public), usage (team/solo), опциональный invite members.
5. Пользователь заполняет name, выбирает visibility, опционально указывает email для приглашения.
6. Пользователь нажимает «Create group».
7. Система валидирует ввод:
   - name — обязателен, не пуст
   - slug — генерируется из name, уникален в рамках родителя
   - visibility — одно из: Private, Internal, Public
8. Система создаёт ScopeNode типа `group`:
   - `id` = UUID v4
   - `name` = из запроса
   - `visibility` = из запроса (по умолчанию Private)
   - `parent_id` = ID родительской группы (если подгруппа)
   - `tenant_id` = tenant текущего пользователя
9. Система назначает пользователя Owner созданной группы (запись OrgMembership).
10. Система возвращает `201 Created` с объектом группы.
11. Диалог закрывается. Список групп обновляется.
12. Пользователь видит новую группу в иерархии.
13. Пользователь может раскрыть/свернуть группу, чтобы увидеть подгруппы.

## Альтернативные потоки

**7a. name пуст:**
- Система возвращает ошибку валидации «Group name is required».
- Группа не создаётся.
- Пользователь остаётся в диалоге.

**7b. slug не уникален (коллизия):**
- Система отклоняет запрос с кодом `SCOPE_DUPLICATE`.
- Пользователю показывается сообщение «Group with this name already exists».

**8a. ParentID указывает на несуществующую группу:**
- Система возвращает `SCOPE_NOT_FOUND`.
- Группа не создаётся.

**8b. Глубина иерархии превышает 5 уровней:**
- Система возвращает `HIERARCHY_DEPTH_EXCEEDED`.
- Группа не создаётся.

**8c. Обнаружен циклический parent_id:**
- Система возвращает `CYCLE_DETECTED`.
- Группа не создаётся.

**8d. gRPC-сервер auth-service недоступен:**
- API Gateway возвращает `503 Service Unavailable`.
- Группа не создаётся.
- Клиенту рекомендуется повторить запрос.

**9a. Недостаточно прав:**
- Пользователь с ролью ниже Owner пытается создать группу.
- Система возвращает `FORBIDDEN_INSUFFICIENT_ROLE`.

## Постусловия

- Новая группа (ScopeNode типа `group`) создана и сохранена в БД (PostgreSQL или MemStore).
- Пользователь назначен Owner группы.
- Аудиторское событие `org.group.created` зафиксировано.
- Группа видна в `/dashboard/groups` при следующем запросе `GET /api/v1/groups`.
- Если указан parent_id — группа отображается как дочерняя при раскрытии родителя.

## Исключения

- Создание группы с именем, содержащим только пробелы → эквивалентно пустому имени (валидация `trim`).
- Создание группы при отсутствии `Idempotency-Key` → `400 Bad Request` per idempotency middleware (если эндпоинт защищён).
- Повторный запрос с тем же `Idempotency-Key` → возвращает существующую группу (идемпотентность).
- Удаление родительской группы → каскадное удаление дочерних групп и проектов (cascade).
