# UC-org.groups.manage-group-lifecycle: Управление жизненным циклом групп

| Атрибут | Значение |
|---------|----------|
| **ID** | UC-org.groups.manage-group-lifecycle |
| **Уровень** | P0 |
| **Актор** | Аутентифицированный пользователь с ролью Owner |
| **Источник** | US-org.groups.create |

## Описание

Пользователь управляет жизненным циклом групп: создаёт группы и подгруппы через страницу создания группы, просматривает иерархический список, настраивает видимость, обновляет атрибуты и удаляет группы. Группы служат контейнерами для проектов и обеспечивают наследование прав доступа.

## Предусловия

1. Пользователь аутентифицирован в системе.
2. Пользователь имеет роль Owner (для создания/удаления групп) или Maintainer (для обновления атрибутов).
3. Для создания подгруппы: родительская группа существует.
4. Система готова к записи (PostgreSQL доступно).

## Основной поток (создание группы верхнего уровня)

1. Пользователь открывает страницу Groups (`/dashboard/groups`).
2. Система отображает список существующих групп с иерархией (родительские + дочерние группы) и человеко-читаемыми именами.
3. Пользователь нажимает «New group».
4. Система перенаправляет на страницу создания группы `/dashboard/groups/new`.
5. Система отображает страницу «New group» с полями: name, slug (авто-генерация из name, только чтение), visibility (Private/Internal/Public, выбор radio-кнопками, по умолчанию Private).
6. Пользователь заполняет name, выбирает visibility.
7. Пользователь нажимает «Create group».
8. Система валидирует ввод:
   - name — обязателен, не пуст (после trim)
   - slug — генерируется из name, уникален в рамках родителя
   - visibility — одно из: Private, Internal, Public
9. Система отправляет `POST /api/v1/groups` с телом: `{ name, slug, visibility, description? }`.
10. Система создаёт ScopeNode типа `group`:
    - `id` = UUID v4
    - `name` = из запроса
    - `visibility` = из запроса (по умолчанию Private)
    - `parent_id` = null (группа верхнего уровня)
    - `tenant_id` = tenant текущего пользователя
11. Система назначает пользователя Owner созданной группы (запись OrgMembership).
12. Система возвращает `201 Created` с объектом группы.
13. Фронтенд отображает Toast-уведомление об успехе: "Group \"{name}\" was successfully created."
14. Фронтенд перенаправляет на страницу группы `/dashboard/groups/:id`.
15. Пользователь видит страницу созданной группы с именем, видимостью, количеством участников.

## Основной поток (создание подгруппы)

1. Пользователь открывает страницу Groups и выбирает родительскую группу.
2. Пользователь нажимает «New group» (или «Add subgroup») — система перенаправляет на `/dashboard/groups/new?parent_id=<uuid>`.
3. Система отображает страницу «New group» с информацией о родительской группе.
4. Поле видимости заблокировано (readonly) — отображается унаследованная видимость родителя с пометкой «Inherited from parent group».
5. Пользователь вводит name подгруппы.
6. Пользователь нажимает «Create group».
7. Система отправляет `POST /api/v1/groups` с телом: `{ name, slug, visibility: <унаследованное>, parent_id: <uuid-родителя> }`.
8. Бэкенд проверяет, что видимость подгруппы не превышает видимость родителя (правило наследования принудительно применяется).
9. Система создаёт ScopeNode типа `group` с `parent_id` = ID родительской группы.
10. Система возвращает `201 Created`.
11. Фронтенд отображает Toast и перенаправляет на страницу подгруппы.
12. При раскрытии родительской группы в списке, подгруппа отображается как дочерняя.

## Альтернативные потоки

**8a. name пуст:**
- Система возвращает ошибку валидации `400 Bad Request` с сообщением «Group name is required».
- Группа не создаётся.
- Пользователь остаётся на странице создания.

**8b. slug не уникален (коллизия):**
- Система отклоняет запрос с кодом `POLICY_CONFLICT` (HTTP 409).
- Пользователю показывается Toast-уведомление «Group with this name already exists in this path.».

**10a. parent_id указывает на несуществующую группу:**
- Система возвращает `SCOPE_NOT_FOUND` (HTTP 404).
- Группа не создаётся.
- Пользователю показывается Toast с соответствующим сообщением.

**10b. Глубина иерархии превышает 5 уровней:**
- Система возвращает `HIERARCHY_DEPTH_EXCEEDED` (HTTP 400).
- Группа не создаётся.

**10c. Обнаружен циклический parent_id:**
- Система возвращает `CYCLE_DETECTED` (HTTP 400).
- Группа не создаётся.

**10d. Видимость подгруппы превышает видимость родителя:**
- Система возвращает `POLICY_CONFLICT` (HTTP 409) или `VISIBILITY_VIOLATION`.
- Группа не создаётся.
- Правило: подгруппа не может быть более публичной, чем родитель (Private > Internal > Public).

**10e. gRPC-сервер auth-service недоступен:**
- API Gateway возвращает `503 Service Unavailable`.
- Группа не создаётся.
- Клиенту рекомендуется повторить запрос.

**11a. Недостаточно прав:**
- Пользователь с ролью ниже Owner пытается создать группу.
- Система возвращает `FORBIDDEN_INSUFFICIENT_ROLE` (HTTP 403).

**14a. Ошибка при загрузке страницы группы:**
- Если `GET /api/v1/groups/:id` возвращает ошибку, отображается состояние ошибки с кнопкой «Retry».
- Для 404 — сообщение «Group not found».

## Постусловия

- Новая группа (ScopeNode типа `group`) создана и сохранена в БД (PostgreSQL).
- Пользователь назначен Owner группы.
- Аудиторское событие `org.group.created` зафиксировано.
- Группа отображается в `/dashboard/groups` с человеко-читаемым именем.
- Подгруппы отображаются как вложенные children при раскрытии родителя.
- Если указан parent_id — видимость подгруппы соответствует родительской (правило наследования).
- Toast-уведомление об успешном создании показано пользователю.
- Пользователь перенаправлен на страницу группы `/dashboard/groups/:id`.

## Исключения

- Создание группы с именем, содержащим только пробелы → эквивалентно пустому имени (валидация `trim`).
- Создание группы при отсутствии `Idempotency-Key` → `400 Bad Request` per idempotency middleware (если эндпоинт защищён).
- Повторный запрос с тем же `Idempotency-Key` → возвращает существующую группу (идемпотентность).
- Удаление родительской группы → каскадное удаление дочерних групп и проектов (cascade).
