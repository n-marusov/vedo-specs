# Пользовательские истории VEDO Core

В этой директории находятся пользовательские истории (User Stories) проекта VEDO Core, оформленные в формате Gherkin.

## Структура

- `README.md` — данный файл с описанием требований к разработке пользовательских историй
- `_matrix.md` — матрица связей пользовательская история → прецедент использования
- `US-<domain>.<feature>.md` — отдельные файлы пользовательских историй с семантическими идентификаторами
- `E2E-<domain>.<feature>.md` — сквозные сценарии с семантическими идентификаторами

## Семантическая классификация US

Идентификаторы пользовательских историй и сквозных сценариев построены по иерархическому принципу, аналогично UC/ADR/REQ:

```
US-<domain>.<subdomain>.<action>
E2E-<domain>.<subdomain>.<action>
```

Домен соответствует прецеденту использования (UC), что облегчает навигацию и трассировку:

| Домен | Описание | Примеры |
|-------|----------|---------|
| `US-editor.*` | Редактор онтологий (классы, свойства, аннотации, правила) | `US-editor.classes.create-parents` |
| `US-abox.*` | Управление индивидами (ABox) | `US-abox.individuals.create` |
| `US-browse.*` | Просмотр и навигация (дерево, граф, поиск, публичный доступ) | `US-browse.search.fulltext` |
| `US-git.*` | Версионирование (коммиты, ветки, сравнение) | `US-git.commits.create` |
| `US-team.*` | Коллаборация (ревью, комментарии, лента) | `US-team.reviews.approve` |
| `US-api.*` | REST API (классы, авторизация, webhooks, документация) | `US-api.auth.jwt` |
| `US-admin.*` | Администрирование (доступ, backup, миграции, airgap) | `US-admin.backup.daily` |
| `US-diagnostics.*` | Диагностика и observability | `US-diagnostics.trace.diagnose` |
| `US-io.*` | Импорт/экспорт (Turtle, XLSX, DOCX, публикация) | `US-io.import.turtle` |
| `US-metrics.*` | Метрики и аналитика | `US-metrics.analytics.complexity` |
| `US-support.*` | Поддержка пользователей (тикеты, feedback, roadmap) | `US-support.tickets.create-track` |
| `US-a11y.*` | Доступность (screen reader, keyboard-only навигация) | `US-a11y.navigation.tree-reader` |

## Формат описания

Все пользовательские истории оформлены единым Gherkin-шаблоном:

```gherkin
@US-<domain>.<subdomain>.<action> @UC-... @P...
Feature: US-<domain>.<subdomain>.<action> <краткое название>

  Background:
    Given <общие предусловия>

  Scenario: <основной пользовательский результат>
    Given <контекст>
    When <действие пользователя или системы>
    Then <ожидаемый результат>
```

### Теги

Каждая история содержит теги:
- `@US-<domain>.<subdomain>.<action>` — семантический идентификатор пользовательской истории
- `@UC-...` — идентификатор связанного прецедента использования
- `@P0`/`@P1`/`@P2` — приоритет (P0 — критический, P1 — важный, P2 — желательный)
- Дополнительные теги для фильтрации: `@accessibility`, `@api`, `@versioning`, `@abox`, и т.д.

## Требования к разработке пользовательских историй

### 1. Структура и именование

- Каждый файл содержит одну пользовательскую историю или один сквозной сценарий.
- Имя файла соответствует семантическому идентификатору: `US-<domain>.<subdomain>.<action>.md`.
- Файл начинается с заголовка первого уровня (`#`) с полным идентификатором и названием.
- Теги Gherkin указываются в первой строке сценария.
- Идентификатор вешается якорем (`<a id="us-<domain>.<subdomain>.<action>"></a>`) перед заголовком для кросс-ссылок.

### 2. Содержание

- **Background** описывает общие предусловия для всех сценариев истории.
- **Scenario** описывает один конкретный пользовательский результат.
- Шаги `Given` задают контекст и предварительные условия.
- Шаги `When` описывают действие пользователя или системы.
- Шаги `Then` проверяют ожидаемый результат.
- Для проверки альтернативных потоков (негативные сценарии) используется отдельный Scenario.

### 3. Язык

- Все пользовательские истории пишутся на русском языке.
- Названия сущностей, свойств и технические идентификаторы могут быть на английском.
- Сообщения об ошибках, возвращаемые системой, указываются в кавычках на языке системы.

### 4. Приоритеты

- **P0** — критические сценарии, без которых продукт не может быть выпущен.
- **P1** — важные сценарии, закрывающие ключевые потребности пользователей.
- **P2** — желательные сценарии, улучшающие пользовательский опыт.

### 5. Связи

- Каждая история должна быть связана с прецедентом использования (Use Case) через матрицу связей.
- Каждая история должна иметь назначенный приоритет.
- Сквозные сценарии (E2E) проверяют работу нескольких историй подряд.

### 6. Accessibility (доступность)

- Истории с тегами `@accessibility` описывают сценарии для пользователей, использующих screen reader (NVDA / VoiceOver) или keyboard-only навигацию.
- Все сценарии доступности должны быть реализованы в соответствии с WCAG MVP.
